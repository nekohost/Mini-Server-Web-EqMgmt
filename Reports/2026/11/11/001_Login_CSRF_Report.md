## Staging 결과

운영과 개발 PC의 기준 커밋은 `30601ee`다. 승인된 패치의 SHA-256은 `d328c0bfa5a2d3d8845621ebf34b74289b0f7f4b34bfafe0527758aff593744d`다. 운영 서버의 비공개 배포 백업에 원본 패치와 변경 전 소스를 보존했다.

로그인을 누르면 브라우저가 같은 출처의 `GET /login`에 JSON을 요청한다. 유효한 세션이면 기존 토큰을 받고, 만료된 세션이면 새 토큰과 쿠키를 받는다. 화면의 입력값을 유지한 채 로그인 POST를 한 번 보낸다. 기존 로그인 세션이 있으면 서버의 이동 경로를 따른다. 일반 HTML 요청과 JSON 요청 모두 응답을 저장하지 않으며 `Vary: Accept`로 표현 형식을 구분한다.

[Chromium 재현 시험](../../../../tests/verify_login_browser.py)은 프로젝트의 기존 ChromeDriver 도구와 임시 SQLite 계정을 사용했다. 애플리케이션은 Linux의 전용 임시 디렉터리와 루프백 포트에서 실행했다.

사용자가 Staging 결과를 확인하고 운영 반영과 검증을 승인했다. 배포 전에 이미 열려 있던 로그인 탭은 새 동작을 받으려면 한 번 새로고침해야 한다.

## 운영 배포 및 검증

2026-11-11에 운영 서버 `nkhst-pentium`의 웹 애플리케이션을 `30601ee`에서 `6d089a9`로 갱신했다. 배포 직전 장비 DB와 AI DB를 SQLite 온라인 백업으로 보관하고 두 사본의 무결성과 외래 키를 확인했다. 복구용 소스와 패치, 서버 검증 기록은 운영 프로젝트의 비공개 디렉터리 `instance/releases/login-csrf-20261111T031522Z/`에 있다.

| 검증 항목 | 관측 결과 |
|---|---|
| 배포 커밋 재검증 | 운영 서버의 격리 디렉터리에서 해당 Git 커밋의 회귀·보안 검사 30건과 Chromium 두 화면 크기 시험이 통과했다. |

| 로그아웃 | 두 화면 모두 포털에서 유효한 세션을 확인하고 로그아웃했다. 로그아웃 후 세션 확인 API는 401을 반환했고, 시험 계정의 활성 세션 값이 비어 있는지 확인했다. |

브라우저에서 로그인 요청의 메서드와 응답 코드를 확인하고, 운영에서는 접근 로그와 감사 로그를 대조했다. 이 서버의 접근 로그에는 해당 요청의 User-Agent가 비어 있어 그 필드로 식별할 수 없었다. 시험용 브라우저 표식은 감사 로그에서 확인하고, 해당 주소·시각의 로그인 POST와 대조했다. 시험 계정은 확인 직후 로그아웃했다.
