# 로그인 폼 갱신 검증

work_id: 20261111-001-login-csrf

## 구현 전 검토

| 순서 | 확인 사항 | 설계에 반영한 내용 |
|---|---|---|
| 1 | 작업 범위 | 기록기와 규칙 검증을 통과했다. 현재 턴 모델 식별 결과가 `runtime-session-mismatch`여서 저장소의 legacy 절차를 적용한다. Staging에서 로그인 경로만 수정한다. |
| 2 | 사용자 경험 | 만료된 쿠키로 열린 폼에서 다시 입력하거나 페이지를 새로고침할 필요가 없어야 한다. |
| 3 | 요청 순서 | 누르자마자 전송을 잠그고, 로그인 상태 확인과 자격 증명 전송을 순서대로 실행한다. |
| 4 | 운영 영향 | 로그인 시 작은 GET 응답 하나가 추가된다. 업무 테이블과 인증 설정의 변경은 필요하지 않다. |
| 5 | 보안 | 같은 출처의 캐시되지 않는 응답과 서버가 발급한 세션 토큰을 사용한다. 토큰·비밀번호를 URL, 웹 저장소, 시험 기록에 넣지 않는다. |
| 6 | 복구 | 애플리케이션 변경만 되돌릴 수 있다. 기존 HTML 요청 및 로그인 POST 계약을 유지한다. |
| 7 | 사용자 조작 | 중복 클릭·Enter, 다른 탭 로그인, 비밀번호 오류, 연결 실패 후 재시도를 시험한다. |
| 8 | 근거의 범위 | 운영에서 발견한 원인과 격리 환경에서 검증한 개선 결과를 구분한다. 실사용자의 비밀번호와 세션을 시험에 사용하지 않는다. |

## Staging 결과

운영과 개발 PC의 기준 커밋은 `30601ee`다. 승인된 패치의 SHA-256은 `d328c0bfa5a2d3d8845621ebf34b74289b0f7f4b34bfafe0527758aff593744d`다. 운영 서버의 비공개 배포 백업에 원본 패치와 변경 전 소스를 보존했다.

로그인을 누르면 브라우저가 같은 출처의 `GET /login`에 JSON을 요청한다. 유효한 세션이면 기존 토큰을 받고, 만료된 세션이면 새 토큰과 쿠키를 받는다. 화면의 입력값을 유지한 채 로그인 POST를 한 번 보낸다. 기존 로그인 세션이 있으면 서버의 이동 경로를 따른다. 일반 HTML 요청과 JSON 요청 모두 응답을 저장하지 않으며 `Vary: Accept`로 표현 형식을 구분한다.

| 시험 | 확인한 결과 |
|---|---|
| 2시간 22분 26초 된 로그인 화면 | 실제 서명 발급 시각만 시험 프로세스에서 과거로 설정했다. 새 토큰으로 같은 폼에서 로그인하고 포털에 도달했다. |
| 버튼 클릭과 중복 제출, Enter | Chromium 390×844 및 1440×900에서 연속 제출 시 폼 확인 GET 1회, 로그인 POST 1회였다. Enter로 잘못된 비밀번호를 보내면 기존 오류가 표시되고 두 입력값과 재시도 버튼이 유지됐다. |
| 연결 장애 | 토큰 확인 응답을 503으로 만들었을 때 비밀번호 전송은 0회였다. 로그인 성공 직후 응답이 유실된 경우, 다시 누르면 이미 성립한 세션으로 포털에 들어가고 추가 POST는 0회였다. |
| 다른 탭·다른 기기 | 다른 탭이 먼저 로그인한 뒤 이전 탭에서 다른 계정으로 제출해도 추가 POST는 0회였다. 두 계정의 세션 값을 대조했다. 별도 클라이언트에서 먼저 로그인해 무효화된 세션은 로그인용 JSON으로 정상 복귀했다. |
| 쿠키·권한·점검 | 오래된 토큰과 쿠키 없는 요청은 403, 일반 사용자의 점검 중 로그인은 503, 시도 제한은 429 및 `Retry-After`였다. 탈퇴 유예 계정은 전용 안내 화면으로 이동했다. |
| 정적 검사와 회귀 | Python과 Jinja 구문, 인라인 JavaScript의 Node 구문, Git 패치 검사를 통과했다. Linux에서 기존 로드맵·릴리스 API 시험과 새 회귀 시험을 합쳐 27건, 계정·감사·재설정 보안 검사 3건을 통과했다. |
| 되돌리기 | 격리 소스 4개 파일에 역패치를 적용해 기존 커밋과 바이트 단위로 일치하는지 확인했다. 정방향 재적용 후 검증한 후보와 해시가 일치했다. |

[Chromium 재현 시험](../../../../tests/verify_login_browser.py)은 프로젝트의 기존 ChromeDriver 도구와 임시 SQLite 계정을 사용했다. 애플리케이션은 Linux의 전용 임시 디렉터리와 루프백 포트에서 실행했다.

사용자가 Staging 결과를 확인하고 운영 반영과 검증을 승인했다. 배포 전에 이미 열려 있던 로그인 탭은 새 동작을 받으려면 한 번 새로고침해야 한다.
