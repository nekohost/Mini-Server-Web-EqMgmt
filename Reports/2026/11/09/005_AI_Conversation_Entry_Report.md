# AI 도우미 첫 화면과 첫 전송 계획 검토

검토 대상은 현재 소스와 [개선 계획](../../../../Plans/2026/11/09/005_AI_Conversation_Entry_Plan.md)이다. 화면과 제품 API의 동작 검증은 계획서에 명시한 Staging 합격 기준으로 남겼다.

| 단계 | 확인한 근거와 구현 시 점검할 사항 |
|---|---|
| 1. 거버넌스 | 계획·검토 작업으로 분류했다. 기록기 및 정책 검증을 통과했고 실행 프로필은 `runtime-session-mismatch`에 따라 legacy로 선택됐다. 이번 산출물은 Plan·Task·Report다. |
| 2. 사용자 의도 | 최초 HTML의 노출과 비동기 초기화 완료 시점이 다르고, 새 대화 버튼이 서버 생성 요청을 직접 호출한다. 초기 목록이 비었을 때와 버튼으로 진입했을 때를 같은 미저장 상태로 정했다. |
| 3. 정적 논리 | 현재 대화 생성과 큐 접수는 각각 쓰기 트랜잭션을 연다. 첫 접수에서 같은 연결을 공유하고 일괄 롤백하는 방식이 필요하다. 기존 중복 판정은 `UNIQUE(owner,client_key)`와 대화 ID가 들어간 지문을 쓰므로 첫 전송의 재시도는 기존 접수 키를 먼저 확인해야 한다. |
| 4. 운영 영향 | 후속 전송과 관리자 모델 시험은 기존 계약을 유지한다. 구현 시 첫 전송 API를 먼저 제공하고 새 화면을 연결한다. 기존 빈 대화는 삭제하거나 변환할 필요가 없다. |
| 5. 보안·예외 | 목록과 재시도에서 사용자·계정 식별을 함께 검증한다. 이미 휴지통으로 간 대화나 전용 시험 기록은 접수 키만으로 열지 않는다. 인증이 바뀌면 기존 계정의 화면을 지우는 현행 처리를 보존한다. |
| 6. 롤백 | 계획은 기존 대화·메시지·작업 구조를 사용한다. 구현 후 문제가 생기면 서버에 첫 전송 API를 유지한 채 이전 화면을 먼저 복구할 수 있다. 이미 접수한 질문과 작업은 일반 대화 이력으로 다시 열 수 있어야 한다. |
| 7. 사용자 조작 | 기존 시험은 새 버튼 직후의 저장과 초기 목록 도착 전 Enter 전송을 기대한다. 명시적 새 대화에서의 즉시 작성, 접수 대상 결정 후 전송, 연타·한글 조합·후속 입력 보존으로 기대값을 바꾸고 휴지통 이동 경합도 재검증한다. |
| 8. 검토 범위 | 원본 소스 대조와 아래의 메모리 DB 시험을 수행했다. 실제 브라우저의 첫 프레임과 새 API의 동시 접수는 구현 후 검증할 항목이다. |

합성 SQLite 데이터에서 정상 대화보다 최근인 빈 대화 52개, 휴지통 대화, 관리자 시험, 다른 사용자 및 같은 사용자 번호의 다른 계정 데이터를 함께 배치했다. 자동 복원 후보 조회는 첫 페이지 밖의 정상 대화를 선택했고 그 대화를 휴지통으로 옮긴 뒤에는 후보를 반환하지 않았다. 실제 운영 데이터는 사용하지 않았다.

교차 시나리오로 초기 목록 조회 중 ‘새 대화’를 누르고 첫 메시지를 보낸 직후 접수 응답이 유실되는 순서를 대조했다. 화면 선택 순서와 서버 접수 키는 별도 역할을 한다. 늦은 목록은 새 화면을 바꾸지 않아야 하고, 같은 요청의 재시도는 원래 대화와 작업을 돌려줘야 한다. 실제 Staging에서 두 조건을 함께 확인하도록 했다.
