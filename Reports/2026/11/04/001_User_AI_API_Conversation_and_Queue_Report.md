# 일반 사용자 AI API·대화 저장·단일 처리 큐 계획 검토

대상은 [계획](../../../../Plans/2026/11/04/001_User_AI_API_Conversation_and_Queue_Plan.md)이다. [Task](../../../../Tasks/2026/11/04/001_User_AI_API_Conversation_and_Queue_Task.md)를 먼저 생성한 뒤 계획 수립과 검토를 진행했다. 이 보고서는 1~8단계를 순서대로 누적한다. 검토 통과는 구현·실제 모델·운영 배포 통과를 의미하지 않는다.

사용자 후속 정정: 큐는 장비관리 내부 요청만 제어하며 외부 서비스 요청은 관리하지 않는다. 새 대화 화면은 기존 Strata 시험 화면과 별도로 작성한다. 초기 검토에서 공통 진입점/전용 운영과 `/ai` 교체를 요구한 판단은 범위 확장이므로 철회했다. 관련 항목을 정정하고 아래 후속 재검토를 누적한다.

## 1. 거버넌스 준수성

- 근거: 기록기 `ensure --platform all --workspace . --json` 정상, 기존 watcher PID 16864 유지. `profile` 결과는 `legacy`, 사유 `runtime-session-mismatch`이며 모델명 확인 불가를 독립 profile로 대체하지 않았다. `governance-tool validate`는 v1.8.1/44노드/오류 0/경고 0으로 통과했다. plan·architecture·인증·권한·세션·CSRF·보안·프론트엔드·migration intent와 3개 산출물 경로의 전체 context pack을 적용했다.
- 긍정적 결과: Task/Plan/Report를 공통 work_id로 분리했다. 계획 범위를 문서로 한정하고 프론트엔드/모델/업무 실행 책임, 비파괴 migration·기존 UI 보존, Linux Staging 선행을 명시했다. 초기 큐는 기존 sqlite3/requests 기반으로 제안하여 새 의존성을 자동 도입하지 않았다.
- 위험·차단 조건: API 키·운영 DB·실제 배포본 호환성을 이번 계획으로 검증한 것으로 보고할 수 없다. 구현·운영 병합은 별도 범위이며 Windows 앱 실행 금지와 기존 검증 경로를 유지한다.
- 추가 발견: 영구 큐 DB 분리는 업무 DB 잠금과 보존 관리를 줄이지만 두 DB 원자성을 제공하지 않는다. 업무 영수증/확인 소비/outbox는 장비 DB transaction에 함께 두는 설계를 채택했다.
- 판단: 문서 계획 범위의 준수성 확인. 실제 구현 진입 조건은 미충족 상태로 분리.

## 2. 사용자 의도 달성도

- 근거: 사용자 요청의 API 직접 연동, 본인별 대화 보관, 일반 사용자 기능, 삭제 차단, 단일 동시 추론/장비관리 측 큐, 계획 우선·표 보고를 계획 1~12절과 대조했다. 현재 일반 사용자 소스의 장비/임시저장/상태/카탈로그 신청/옵션 신청/내 신청 조회/파일/CSV/개인 설정을 기능 표에 대응시켰다.
- 긍정적 결과: 시험용 관리자 iframe을 일반 사용자에게 개방하지 않고 본인 장비 등록·수정과 카테고리·제조사 신청을 핵심 변경 단계에 포함했다. 정정안은 독립 대화 화면과 서버 대화 저장, 장비관리 발신의 진행 중 모델 요청 최대 1개를 구분한다. 외부 서비스 요청 수·순서는 관리하지 않는다.
- 위험·차단 조건: 비밀번호·이메일 인증/계정 변경은 초기 AI 자동 실행에서 제외하고 수동 화면으로 안내한다. 폐기 상태 전이도 초기 범위에서 제외하는 보수적 제안이다. 첨부/CSV/설정은 후속 단계지만 완료 기준과 기존 제한을 명시했으므로 처음부터 모든 일반 기능을 구현했다고 말할 수 없다.
- 추가 발견: 신규 카탈로그·옵션이 들어가는 장비 생성은 승인 대기/임시저장 부작용이 있다. 접수 성공과 정식 등록·승인 완료를 다른 결과로 표시하도록 했다. 존재하지 않는 신청 취소/수정/재상신 API를 기존 기능으로 만들지 않았다.
- 판단: 요청한 계획 범위와 일치. 기능 제외·단계 도입의 차이를 사용자 보고에 드러낸다.

## 3. 논리적 구동 가능성

- 근거: 계획의 입력 접수→영구 저장→원자적 claim→모델 호출→도구 검증→재진입/확인 대기→확정/종료 흐름을 정적으로 추적했다. 기존 `require_equipment`/`change_status`의 소유권·revision, v3 revision trigger, `catalog_request_service`의 transaction 내 승인 요청, CSV preview/commit 계약과 비교했다. 실제 DB 연결이나 앱 import는 하지 않았다.
- 긍정적 결과: 추론 동안 DB writer transaction을 유지하지 않는다. 본인별 순서와 step별 재진입, 확인 대기 중 내부 점유 해제, 짧은 polling으로 긴 웹 요청을 피한다. 업무 변경/감사/확인 소비/영수증은 같은 DB transaction이며 대화 반영은 outbox로 복구한다. 정정안은 자체 worker·발신 요청의 완료/취소·상관 ID로 관리하며 전체 upstream idle을 요구하지 않는다.
- 위험·차단 조건: SQLite writer 경합·디스크 용량, 공개 조회와 대화 증가, 장비관리 내부 순차 처리 병목은 남는다. 설정 상한은 제안 수치이며 공유 Strata 응답 시간을 보장하지 않는다. 자체 요청의 종료/결과가 불명확하면 내부 재전송을 보류하고 복구 조건을 확인한다. 외부 요청/서버를 중단하는 방식은 제외한다.
- 추가 발견 및 반영: 토큰별 저장은 불필요한 쓰기 경합을 만들 수 있어 생성 조각의 시간/크기 묶음 저장과 최종 경계 즉시 저장, cursor 조회를 4절에 보완했다. 이는 1~2단계의 권한/범위 판단에 영향을 주지 않는다. 불완전한 도구 JSON은 복구 시 명령으로 재사용하지 않는다.
- 판단: 설계의 정상 흐름과 종료 가능한 오류 경로 확인. 실제 claim 경합·정합성·처리량은 Linux Staging 검증 조건.

## 4. 운영 병합 영향

- 근거: 현재 `/ai`는 `strata_integration` Blueprint에 이미 등록되어 있고 `/api/ai/*`는 제안 경로다. `app.py`에는 module import 시 `init_db()`와 별도 logger thread, 프로세스 내부 DB/복원 잠금이 있다. `database_contract.assert_contract_version`은 알 수 없는 버전을 거부한다. 실제 운영 서버/DB는 조회하지 않았다.
- 긍정적 결과: 초기 `/ai` 교체 제안은 사용자 정정으로 철회했다. 현재안은 신규 `/assistant`·`equipment_ai` 메뉴·템플릿/JS로 독립 작성하고 기존 `/ai`, `/ai/console`, 관리자 프록시를 보존한다. worker의 app import·장비 DB 직접 쓰기·웹 프로세스 무단 증설을 피하고 기존 유지보수 gate를 적용한다. migration 이전 호환 릴리스와 AI 읽기/쓰기 독립 flag가 있다.
- 위험·차단 조건: 새 테이블만 추가했다고 구버전 앱이 기동된다고 보장할 수 없다. source/DB 계약/서비스 인증/네트워크/flag가 부분 적용되면 공개/쓰기 오류가 생긴다. 실제 버전 확인·일관된 백업·Linux Staging·배포 순서가 완료되기 전 운영 반영은 차단한다.
- 추가 발견: 기존 파일명/주석에 candidate라는 문구가 있어도 실제 Blueprint가 앱에 등록되어 있다. 파일 존재/주석만으로 활성 여부를 판정하지 않고 연결 지점을 확인했다. old 관리자 시험의 최종 배포 미확인과 새 일반 사용자 설계는 별개다.
- 판단: 운영 영향과 기존 구조의 위험을 계획에 반영. 이번 작업의 운영 변경은 없음.

### 세션 경계 보완 후 3→4단계 영향 재검토

- 추가 소스 확인: `static/js/session_timer.js`의 fetch wrapper는 성공한 요청마다 화면 세션 타이머를 리셋한다. `app.py`는 30분 permanent session을 사용한다. Flask 공식 3.1 문서의 `SESSION_REFRESH_EACH_REQUEST` 기본값도 확인했다. 단순 polling 추가만으로는 "자동 연장 없음"이라는 설계 조건을 지킬 수 없다.
- 3단계 재검토: AI 자동 조회와 사용자 활동을 구분하고 서버 기록의 위임 만료를 별도 검사하도록 6절을 보완했다. 로그아웃의 cookie 삭제는 유지한다. 만료/중단 흐름은 여전히 종료 가능하고 worker가 세션을 연장하지 않는다.
- 4단계 재검토: 공통 타이머·Flask 세션 저장 경계가 미래 구현 영향 대상이다. AI 자동 조회만 예외로 처리하고 기존 화면 연장·check_session 동작을 Linux Staging에서 회귀 확인하도록 했다. 현재 JS/앱 설정은 변경하지 않았다. 1~2단계의 범위·권한 판단 변화는 없다.

## 5. 보안과 예외 엣지 케이스

- 근거: A/B 사용자 ID 교환, 공개 장비의 타인 수정, 모델이 관리자/삭제 도구 이름을 조작, 장비 메모에 프롬프트 주입, 확인 만료/재사용, 대기 중 로그아웃·강제 로그아웃·권한 변경, commit 후 응답 유실, worker 사망 후 모델 생성 지속을 교차 시나리오로 정적 검토했다. 실제 요청·침투 시험은 하지 않았다.
- 긍정적 결과: AI 메뉴만 허용해도 업무 권한이 자동 허용되지 않는다. 도구와 서버 실행 경계에서 허용 목록·현재 소유권/메뉴·위임·타입/크기·CSRF·현재 revision을 검사한다. 대화/job/event/proposal 소유자 검사를 일관 적용하고 모델에 인증 key·원문 cookie·SessionToken·SQL·임의 URL/경로 실행 기능을 제공하지 않는다. 완료된 호출만 해석하고 실제 영수증으로 성공 여부를 결정한다.
- 위험·차단 조건: 내부 실행 API는 새 공격면이므로 loopback만으로 신뢰하지 않고 서비스 인증과 사용자별 제한 위임을 함께 검증해야 한다. 자체 요청의 전송 보호·데이터 취급은 연동 계약으로 확인한다. 공식 main의 tool/개별 취소 기능이 설치본에도 있다고 가정할 수 없으며 타인 요청을 취소할 수 있는 광역 관리 기능으로 대체하지 않는다.
- 추가 발견·정정: 초기안에서 전역 단일 실행 보장을 위한 전용 upstream/공통 admission을 필수로 둔 것은 사용자 범위보다 넓었다. 후속 지시에 따라 이 조건을 철회하고 자체 요청만 제어하도록 수정했다. 전체 busy/idle은 자체 요청의 소유권/완료 증거가 아니며 외부 트래픽 통제 근거로 쓰지 않는다.
- 판단: 요구되는 보안 경계를 계획에 포함. 실제 API 호환·사용자 격리·권한/취소 경합 시험 전 쓰기 기능 활성화는 차단.

## 6. 롤백과 역방향 파급

- 근거: 계획 10절의 호환 릴리스→추가 schema→AI flag 단계 적용과 반대 흐름을 검토했다. 기존 v3 계약의 미래 버전 거부, 장비 DB 복원과 독립 AI DB의 과거 기록, 계정/장비 ID 재사용, 확정 후 대화 반영 전 장애를 함께 고려했다.
- 긍정적 결과: 장비관리 기능 중지 후 수동 UI를 유지하고, 자체 발신 요청 정리·미확정 위임 무효화·실행 영수증 대조로 복구한다. 공유 Strata/외부 클라이언트/기존 시험 UI는 중지·변경하지 않는다. 신규 기록 삭제 down이나 이미 확정된 업무를 잃는 복귀를 기본으로 삼지 않았다. 두 DB 백업과 공통 세대·outbox가 있다.
- 위험·차단 조건: 호환 릴리스가 없으면 기존 commit으로 소스만 되돌려도 신규 DB에서 실패할 수 있다. 운영 백업·복원 실증 없이 복구 가능하다고 주장할 수 없다. 복원한 DB와 오래된 큐를 자동 재결합하면 중복/다른 대상 변경이 발생할 수 있으므로 재실행을 차단한다.
- 추가 발견: AI 대화의 과거 성공 메시지는 복원 후 현재 장비 상태의 증거가 아니다. 과거 기록 라벨과 최신 조회 재구성, 확인 만료/DB 세대 검사로 분리한다. 대화 보관과 업무 감사의 보존 목적도 다르다.
- 판단: 무손실 복귀 방향과 필요한 선행 검증을 명시. 실제 migration/down 또는 restore rehearsal은 이번 계획 작업에서 미실행.

## 7. 휴먼 에러와 UX 방어

- 근거: 나의 과거 대화 재개→장비 식별→부족한 입력 질문→확인 카드→실제 결과 표시 흐름을 점검했다. 동일 장비명/누락 사양, 공개 여부 변경, 신청 접수와 승인 대기, 여러 항목의 부분 성공, 확인 대기 중 다른 사용자 처리, 새로고침·중복 클릭·취소·재로그인을 검토했다.
- 긍정적 결과: 서버가 만든 변경 전후 카드에 장비 ID·공개 여부·부작용·만료·작업 수가 표시된다. 확인 전 업무 쓰기 없고, 삭제는 확인으로도 허용하지 않는다. 이미 확정한 결과는 모델 후속 답변 실패와 구분된다. 대기 순서·생성/확인 상태는 본인에게만 보이며 근거 없는 완료 시각을 약속하지 않는다. 첨부는 사용자 선택 파일만 사용한다.
- 위험·차단 조건: 매 변경 확인은 번거로울 수 있으나 초기 일반 사용자 쓰기의 필수 조건으로 유지한다. 큰 CSV/다중 변경은 검토 가능한 묶음과 선택이 필요하다. 모바일 확인 카드, 키보드/스크린리더, 장시간 대기, 취소 정리·만료 안내는 실제 UI 구현 후 검증해야 한다.
- 추가 발견: 대화의 단순 "예"를 과거 제안 승인으로 처리하면 다른 제안/탭과 혼동된다. 서버 proposal ID에 묶인 실행 버튼과 재로그인 후 새 미리보기로 제한했다. 대기 작업 취소와 이미 적용된 업무 되돌리기도 다른 동작으로 안내한다.
- 판단: 계획 단계 동선·오해 방지 조건 확인. 실제 화면/접근성/사용성 시험은 미실행.

## 8. AI 메타 거버넌스

- 근거: 현재 작업자의 mode는 Codex의 plan/review이며 기능 구현 승인을 받은 것으로 해석하지 않았다. Plan/Task/Report만 구조화 편집했다. 문서의 UTF-8 읽기·공통 work_id·상대 링크 대상 존재·코드 fence 균형을 확인했다. 기존 추적 변경 9개는 기준 SHA-256과 전부 동일함을 확인했다.
- 긍정적 결과: 소스·DB·기존 사용자 변경·운영 설정·외부 저장소를 수정하지 않았고 별도 agent에게 위임하지 않았다. Strata 공식 main의 설명과 로컬 사본/실제 설치본을 구분했으며 runtime 시험·성능·도구 품질을 실행했다고 주장하지 않았다. 비밀 파일/운영 DB를 읽거나 모델을 호출하지 않았으며 scratch 파일을 만들지 않았다.
- 위험·차단 조건: 실제 배포본의 자체 요청 식별/완료/취소 계약, 사용자 대화 보존 정책, 모델 도구 품질·응답 시간, DB migration/복원, 독립 사용자 UI는 아직 확인되지 않았다. 외부 서비스의 공통 큐 편입이나 single-consumer 운영은 구현 조건에서 제외한다.
- 추가 발견·정정: 외부 서비스의 직접 요청은 정상적인 별도 사용이며 "우회 진입"으로 분류하지 않는다. 장비관리의 내부 큐·세션 만료·자체 요청 복구만 구현 검증 범위로 둔다. 기존 Strata 화면과 신규 업무용 대화 UI도 별개로 구분한다.
- 판단: 1~8단계 순서 검토 완료. 문서 계획으로 보고 가능하며 구현/실행/배포는 미실행.

## 종합 판단과 미해결 조건

기존 Strata 시험 화면과 별도로 신규 작성하는 `/assistant` → 장비관리 서버 대화·내부 영구 큐 → worker 1개 → Strata API와, 권한을 재검사하는 업무 실행 경계를 권장한다. 동시성·공정성·취소·복구는 장비관리에서 보낸 요청에만 적용한다. 변경은 내용 고정 확인 후 원자적 업무/감사/영수증으로 확정하고 삭제·관리자 기능을 제공하지 않는다.

구현 선행 조건은 설치 Strata의 tool/stream/자체 요청 식별·완료·개별 취소/복구 계약, 실제 모델 품질/자체 응답 시간 예산, 운영 DB 계약/호환 migration·복원, 내부 보호 채널, 대화 보존·용량 정책이다. 공용 진입점이나 전용 Strata 운영, 외부 요청 제어는 요구하지 않는다. 일반 사용자 범위·삭제 차단·독립 대화 화면·장비관리 내부 제어를 유지한다.

검증에서 실행한 것은 거버넌스 검사·읽기 전용 소스/문서 조사·문서 구조와 기존 변경 해시 점검이다. 모델 응답, 다중 사용자 동작, 브라우저, Linux 앱/부하, 실제 DB migration/복원 시험은 실행하지 않았다. 이 작업의 산출물은 Plan/Task/Report 3개이며 후속 정정도 이 문서들만 갱신했다. commit/push·운영 반영은 하지 않았다.

## 사용자 정정 이후 순차 재검토

### 정정 검증 1. 거버넌스와 계획 범위

- 근거·긍정: 이 턴도 recorder 정상/기존 watcher 유지, profile은 `legacy(runtime-session-mismatch)`, governance validate는 오류·경고 0. 계획·구조·권한·화면·세션·보안 intent의 전체 pack을 적용하고 기존 Task를 먼저 재개했다. 수정 대상은 같은 Plan/Task/Report 3개다.
- 위험·조건·추가 발견: 계획 정정은 구현/배포나 다른 서비스 관리 권한이 아니다. 공통 진입점·전용 운영·기존 화면 교체 조건을 철회했다. 정책과 신규 의존성 변경은 없으며 계획 범위의 규칙 준수로 판단한다.

### 정정 검증 2. 사용자 의도

- 근거·긍정: 사용자 정정 두 항목을 계획 1·2·4·5·8·10~12절과 대조했다. 장비관리의 발신 요청만 제한하고 외부 클라이언트는 기존 방식으로 사용한다. 독립 `/assistant`·`equipment_ai` 메뉴·신규 템플릿/JS로 화면을 작성하며 서버 대화 저장을 유지한다.
- 위험·조건·추가 발견: 공유 Strata 전체 동시성/대기 순서는 이 설계의 보장 대상이 아니다. 이를 앱 내부의 동시 요청 최대 1개와 구분했다. 일반 사용자 한정·삭제 차단·기존 쓰기 확인 절차는 유지하여 요청과 일치한다고 판단한다.

### 정정 검증 3. 내부 큐 논리와 자체 요청 복구

- 근거·긍정: 자체 job claim→발신 1개→응답/도구 처리→내부 재진입 흐름과 외부 클라이언트 동시 호출을 교차 검토했다. 전체 idle을 검사하지 않고 자체 요청의 상관 ID와 완료/개별 취소만 관리한다. 429/503·응답 대기는 자체 backoff로 처리하며 타 서비스 순서는 건드리지 않는다.
- 위험·조건·추가 발견: 개별 취소 미지원이면 후속 업무를 차단하고 자체 응답을 정리해야 한다. crash 후 자체 요청의 종료가 불명확하면 내부 중복 전송을 보류한다. 설치 API에서 해당 복구 계약을 확인하는 조건은 남지만 외부 서비스를 제어하는 대체 복구는 제외했다. 정적 흐름 검토 완료, 실행 시험 미실행.

### 정정 검증 4. 기존 화면과 운영 영향

- 근거·긍정: 관련 소스 경로에서 `/assistant`·`equipment_ai`를 검색한 범위에는 기존 식별자가 없었다. 신규 메뉴·템플릿/JS가 기존 `/ai`, `/ai/console`, Strata vendor UI·iframe·bridge와 별도로 구성되도록 명시했다. 기존 관리자 메뉴/권한과 화면 교체는 제외했다.
- 위험·조건·추가 발견: 경로명은 제안이며 구현 시 전체 route와 회귀 검증이 필요하다. 장비관리 공통 로그인·테마·내비게이션은 재사용하되 Strata 대화 저장소나 UI 모듈에 의존하지 않도록 분리한다. 지금 운영 소스·메뉴 DB·Nginx를 변경한 것은 아니다.

### 정정 검증 5. 보안과 제어 권한

- 근거·긍정: 취소/로그아웃/장애 복구가 자체 job과 위임에 묶였는지 대조했다. 다른 서비스의 요청 ID 취소, 전역 stop/unload/restart, 외부 로그 감시·진입점 변경을 제외했다. 사용자별 대화·장비·확인 권한 검사는 유지한다.
- 위험·조건·추가 발견: 전체 busy/idle은 특정 요청의 소유권 증거가 아니다. 설치본의 개별 요청 계약과 내부 권한 검사로 확인해야 한다. 자체 API 시험 전 안전한 개별 취소를 구현했다고 볼 수 없다. 정정 후 권한 범위의 정적 일치 확인.

### 정정 검증 6. 복귀 범위

- 근거·긍정: 장비관리 신규 접수/쓰기 중지→자체 요청 정리/불명 결과 격리→업무 영수증 확인→수동 UI 유지 순서를 재검토했다. 공유 Strata와 기존 시험 화면을 종료/변경하지 않으며 새 UI flag도 별도로 둔다.
- 위험·조건·추가 발견: 자체 응답 연결 유실은 임의 재시작으로 해결하지 않는다. 미확정 제안 무효화·확정 결과 보존·DB 세대 검사는 유지된다. 실제 복구/rollback 시험은 후속 구현 조건이며 이번 문서 변경은 되돌릴 수 있는 범위다.

### 정정 검증 7. 사용자 화면과 대기 안내

- 근거·긍정: 독립 화면에 본인 대화 목록/입력/진행/확인 카드/업무 결과를 배치하고 장비관리 내부 대기 순위와 Strata 응답 대기를 구분했다. 외부 전체 대기 순위·다른 서비스 이름/작업 내용·확정되지 않은 완료 시간을 표시하지 않는다.
- 위험·조건·추가 발견: 내부 순서가 앞이어도 공유 서비스의 응답이 늦을 수 있다. 자체 응답으로 원인을 확인할 수 없다면 "응답 대기"로 표시하고 임의 원인 추정을 하지 않는다. 실제 UI·접근성 검증은 미실행이며 신규 화면 구현 후 확인한다.

### 정정 검증 8. 문서 정합성과 작업 범위

- 근거·긍정: 3개 문서의 UTF-8·공통 work_id·상대 링크 대상·fence 균형을 확인했다. 업무/Strata 연동 소스 4개와 선행 변경 9개, 총 13개 파일의 SHA-256은 이번 정정 전후 모두 일치했다. 계획 본문·도입 단계·검증 기준과 보고서의 공통 진입점/전용화/기존 UI 교체 조건을 현재 사용자 지시로 정정했다.
- 위험·조건·추가 발견: 신규 화면/경로와 내부 큐는 아직 설계다. 실제 API 호환성·자체 요청 취소/복구·화면 동작을 실행했다고 보고하지 않는다. 다른 서비스의 설정/요청/로그와 공유 Strata 운영에는 조치하지 않았다. 분석용 scratch와 외부 메시지 전송은 없다.
- 판단: 정정 검증 1~8 완료. 장비관리 내부 제어와 기존 Strata 화면에 독립적인 신규 UI를 현재 계획으로 보고한다. 구현·실행·배포는 미실행이다.
