# Staging Rule 도구 정책 동기화 종합 검증 보고서

> [!NOTE]
> 이 문서는 `0.3.0-staging` 시점의 과거 검증 기록입니다. 현재 운영 판단에는 최신 manifest 버전과 후속 Terra·Gemini 보완 검증 보고서를 사용해야 합니다.

## 0. 범위와 결론

- 대상: `Staging/Rule.md`, 관련 실행 노드·capability·제품별 진입점·추적성·manifest
- 거버넌스 버전: `0.3.0-staging`
- 결론: Staging 정적 검증 통과
- 운영 상태: `staging-only`; 루트 운영 규칙 반영은 수행하지 않음
- 보류: `[제안-013]` 구현 전 실제 DB와 `3-1-1` 운영 스키마를 확인하지 않음
- 잔여 조건: 운영 전환 전 실제 YAML 파서와 제품별 로더에서 파싱·route 로딩 실측 필요

## 1단계: 거버넌스 준수성

근거와 긍정적 결과:

- 사용자 요청에 따라 Staging 통합 Rule과 노드만 변경하고 루트 운영 규칙·소스·DB는 변경하지 않았다.
- 실제 작업 전에 영구 Plan과 순차 Task를 작성했다.
- 파일 쓰기는 구조화된 패치 수단만 사용했다.
- 사용자 직접 추가 정보의 운영 병합 보존 원칙을 `governance.human-reference`와 `workflow.staging-merge`에 반영했다.

위험과 차단 조건:

- 실제 YAML 파서 검증이 되지 않았으므로 현재 결과를 운영 활성화 승인으로 간주할 수 없다.

판정: Staging 범위 통과.

## 2단계: 사용자 의도 달성도

근거와 긍정적 결과:

- 백업 서버 IP `192.168.0.24`가 `Staging/Rule.md`와 `context.deployment-topology`에 동일하게 존재한다.
- 운영 병합 시 사용자 직접 추가·승인 정책을 누락하거나 이전 초안으로 덮어쓰지 않도록 명시했다.
- Antigravity의 대화 오기입 경험을 플랫폼별 위험으로 한정하고, Codex 등 신뢰 가능한 구조화 편집 도구가 있는 환경에서는 그 도구를 우선하도록 했다.
- 일반 파일의 터미널 쓰기는 구조화 도구 실패, Diff·Undo 또는 동등 복구 검증, 사전 보고, 사용자 명시 승인이라는 조건을 모두 만족할 때만 대안으로 제시하게 했다.
- `[제안-013]` 이후로 보류된 DB 확인은 수행하지 않았고 `3-1-1` 문구도 변경하지 않았다.

위험과 판단:

- 각 IDE와 확장 도구의 실제 Undo 보장은 런타임별로 다르므로 capability 검증 없이 예외를 적용할 수 없다.

판정: 통과.

## 3단계: 논리적 구동 가능성

근거와 긍정적 결과:

- manifest와 human map의 39개 노드가 모두 존재하며 선언 ID와 경로가 일치한다.
- 관련 노드의 `human_rule_sections`와 human map 역포인터가 일치한다.
- 통합 Rule의 151개 포인터가 모두 존재하는 노드 파일을 가리킨다.
- manifest의 `human_reference.sha256`가 실제 Rule 해시와 일치한다.

해당 없음:

- DB 쿼리, 비동기 흐름, 캐시, 프론트엔드 런타임은 이번 문서 정책 변경에 포함되지 않는다.

위험과 판단:

- YAML 라이브러리 기반 구문 검증은 도구 부재로 미수행이다. PowerShell 구조 검사로 경로·ID·역포인터를 확인했으나 실제 소비기 파싱을 대체하지 않는다.

판정: Staging 정적 구조 통과, 실제 파서 검증 대기.

## 4단계: 운영 병합 영향

근거와 긍정적 결과:

- `status: staging-only`, `replaces_root_sources: false`, `human_reference.auto_load: false`를 유지했다.
- 백업 서버 정보와 사용자 승인 정책의 병합 보존 요건을 명시하여 부분 병합 위험을 줄였다.
- 세 제품 진입점과 capability가 동일한 기본 원칙을 참조한다.

위험과 차단 조건:

- 운영 병합 때 Rule만 복사하고 노드·human map·manifest·진입점을 누락하면 fail-closed 불일치가 발생한다.
- 운영 반영은 별도 Diff, 실제 파서 검증, 사용자 승인 없이는 진행할 수 없다.

판정: 현재 운영 영향 없음. 향후 원자적 병합 필요.

## 5단계: 보안 및 예외 엣지 케이스

근거와 긍정적 결과:

- 터미널 일반 쓰기는 기본 금지를 유지하며 예외의 전제와 승인 조건을 모두 명시했다.
- Undo 또는 동등 복구를 추정하지 않고 실제 capability 검증을 요구한다.
- 신규 비밀, 인증정보, 실행 코드, 외부 의존성을 추가하지 않았다.

위험과 판단:

- 백업 서버 IP는 운영 정보이므로 노드의 기존 규정대로 외부 문서·로그에 불필요하게 재전파하지 않아야 한다.
- “구조화 도구로 조치할 수 없음” 또는 “Undo 가능”을 AI가 자의적으로 선언하면 예외가 오용될 수 있다. capability 실측과 사용자 명시 승인이 차단 장치다.

판정: 통과.

## 6단계: 롤백 및 역방향 파급

근거와 긍정적 결과:

- DB와 운영 소스를 변경하지 않아 데이터 롤백은 해당 없다.
- 변경은 구조화된 Diff 단위로 적용되었고 Staging `0.3.0` 묶음을 채택하지 않으면 기존 운영 규칙은 유지된다.

위험과 판단:

- 개별 파일만 되돌리면 Rule·노드·추적성이 불일치한다. 롤백은 Rule, 관련 노드, capability, human map, manifest, 진입점을 같은 버전 단위로 수행해야 한다.

판정: 현재 롤백 가능.

## 7단계: 휴먼 에러 및 UX 방어

근거와 긍정적 결과:

- 사용자는 Rule에서 기본 도구, 조건부 예외, 사전 승인 조건을 한 번에 읽을 수 있다.
- “터미널 쓰기 금지”와 “무조건 허용” 사이의 모호성을 없애고 기본 금지와 조건부 제안을 분리했다.
- 사용자 직접 수정 정책을 병합 시 보존하도록 하여 덮어쓰기 실수를 방지한다.

위험과 판단:

- 플랫폼 capability 문구만 읽고 공통 노드를 생략하면 승인 조건을 놓칠 수 있다. bootstrap과 router가 관련 도구 노드를 함께 읽도록 유지해야 한다.

판정: 통과.

## 8단계: AI 메타 거버넌스

근거와 긍정적 결과:

- 현재 작업자를 Codex로 식별했고, 사용자 승인 범위를 Staging 정책 동기화로 제한했다.
- 하위 에이전트, 외부 네트워크, scratch 파일, DB 접근을 사용하지 않았다.
- Codex의 터미널 Undo 가능성을 사실로 단정하지 않고 capability 실측이 선행되어야 한다고 기록했다.
- 승인 재촉 없이 적용 결과와 잔여 검증 조건을 분리했다.

위험과 판단:

- Antigravity의 오기입은 사용자 경험에 근거한 플랫폼별 위험이며 모든 설치 환경에서 재현된다는 일반화는 하지 않았다.

판정: 통과.

## 종합 결론

요청된 세 정책은 Staging 통합 Rule, 실행 노드, capability, 제품별 진입점, human map에 동기화되었다. 정적 무결성 오류는 0개다. 실제 YAML 파서·제품 로더 검증 전에는 운영 활성화하지 않는 조건을 유지한다.
