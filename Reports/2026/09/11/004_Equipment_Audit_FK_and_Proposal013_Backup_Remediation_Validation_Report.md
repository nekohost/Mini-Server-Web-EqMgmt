# [검증 보고서] 장비 감사 로그 외래키 및 제안 013 백업 실패 개선

- 검증일: 2026-09-11
- 상태: 계획 Validation 1~8 완료 / 구현 미수행
- 판정: 기존 002와 분리한 스키마 migration 계획이 필요하며 Staging 구현 후보 작성 가능

## 검증 근거

운영 Linux에서 `equipment.db`의 `PRAGMA integrity_check`는 `ok`였고, `PRAGMA foreign_key_check`는 `equipments_audit_log` rowid 1~4가 삭제된 `equipments` 부모를 참조하는 위반을 반환했다. 소스의 삭제 API는 DELETE 감사 행을 추가한 뒤 장비를 물리 삭제하며, 감사 테이블은 같은 장비에 대한 NOT NULL 외래키를 선언한다. 제안 013은 생성한 백업에서 이 위반을 발견해 HTTP 500을 반환한다.

## Validation 1~8

### 1단계 — 거버넌스 준수성

- 근거: 실제 운영 증거를 읽기 전용으로 확인하고 운영 DB·코드를 변경하지 않았다.
- 긍정적 결과: 스키마 변경을 옵션 UI 계획에 묵시적으로 포함하지 않고 별도 Plan·Task·Report로 분리했다.
- 위험: 감사 테이블 재구축은 데이터 손실 가능성이 있는 고위험 작업이다.
- 차단 조건: 온라인 복구 사본, 행 보존 기준선, transaction rollback 시험 없이는 운영 migration을 수행하지 않는다.
- 판정: 통과.

### 2단계 — 사용자 의도 달성도

- 근거: 사용자의 직접 목적은 제안 013 백업 성공이며, 기존 장비 삭제·옵션 문제와 연결된 원인의 완전한 해소가 필요하다.
- 긍정적 결과: 백업 검사 우회가 아니라 감사 모델의 모순을 제거하므로 두 증상을 함께 해결한다.
- 위험: 옵션 관리나 전체 모델 경로 표시까지 같은 변경에 넣으면 범위가 커진다.
- 차단 조건: 이번 migration은 감사 외래키·백업 관측성·작업 경로 권한으로 한정한다.
- 판정: 통과.

### 3단계 — 논리적 구동 가능성

- 근거: 감사 행은 삭제된 객체를 기록하므로 살아 있는 장비 부모의 존재를 영구 요구할 수 없다.
- 긍정적 결과: 외래키만 제거하고 ID와 스냅샷을 보존하면 기존 조회·감사 의미와 하드 삭제 정책이 양립한다.
- 위험: SQLite 테이블 재구축 중 행·인덱스·AUTOINCREMENT 상태가 누락될 수 있다.
- 차단 조건: 명시적 컬럼 복사, 행 수·ID·내용 지문·sequence·인덱스 비교 중 하나라도 실패하면 rollback한다.
- 판정: 통과.

### 4단계 — 운영 병합 영향

- 근거: `app.py` 초기 스키마, 기존 DB migration, `db_migration.py`, 제안 013 백업 예외 처리에 파급된다.
- 긍정적 결과: API 응답 계약과 장비 삭제 정책은 유지할 수 있다.
- 위험: 코드만 병합하고 migration이 누락되면 기존 운영 DB의 백업 실패가 계속된다.
- 차단 조건: 신규 설치 정의·기존 DB migration·회귀 시험을 같은 릴리스 단위로 전달한다.
- 판정: 통과.

### 5단계 — 보안과 예외 엣지 케이스

- 근거: DB 백업에는 계정·장비·로그가 포함되고 현재 작업 디렉터리 권한은 `0775`로 확인됐다.
- 긍정적 결과: 응답의 내부 오류 비노출을 유지하며 제한된 서버 로그에만 상관관계 정보를 남긴다.
- 위험: 오류 원문이나 DB 경로가 브라우저·access log에 노출될 수 있고 작업 디렉터리 목록이 다른 계정에 보일 수 있다.
- 차단 조건: UI에는 불투명 오류 ID만 제공하고 디렉터리·하위 경로를 `0700`으로 검증한다.
- 판정: 통과.

### 6단계 — 롤백과 역방향 파급

- 근거: 기존 백업 API가 알려진 외래키 위반 때문에 복구 사본 다운로드도 거부하는 순환 문제가 있다.
- 긍정적 결과: migration 전 온라인 사본은 `integrity_check`, SHA-256, 알려진 위반 목록을 별도 기준으로 검증해 보존할 수 있다.
- 위험: 외래키를 다시 추가하는 자동 Down migration은 동일 결함을 재생성한다.
- 차단 조건: transaction rollback을 우선하고 파일 복구는 검증된 사본으로만 수행하며 자동 Down은 제공하지 않는다.
- 판정: 통과.

### 7단계 — 휴먼 에러와 UX 방어

- 근거: 현재 UI 문구만으로 권한·공간·DB 불일치를 구분할 수 없다.
- 긍정적 결과: 오류 ID가 있으면 내부 정보를 공개하지 않고 서버 로그와 대조할 수 있다.
- 위험: 사용자가 실패 버튼을 반복 클릭하거나 정상 `integrity: ok`만 보고 외래키 위반을 놓칠 수 있다.
- 차단 조건: 실패 단계 기록, 중복 요청 방지 유지, `integrity_check`와 `foreign_key_check`를 별도 결과로 검증한다.
- 판정: 통과.

### 8단계 — AI 메타 거버넌스

- 근거: 사용자 제공 운영 출력과 현재 소스를 교차검증했고 추정했던 권한·용량 원인을 증거에 따라 제외했다.
- 긍정적 결과: 기존 계획의 예고 문구를 완료로 오인하지 않고 실제 운영 증거로 신규 범위를 확정했다.
- 위험: 4건이라는 현재 표본을 전체 운영 스키마의 영구 사실로 일반화할 수 있다.
- 차단 조건: 운영 migration 직전 동일 read-only 기준선을 다시 수집하고 차이가 있으면 계획을 재검토한다.
- 판정: 통과.

## 종합 판정

이번 결함은 기존 002의 옵션 관리 구현에 단순 병합할 문제가 아니다. 실제 DB 스키마와 영구 감사 데이터에 영향을 주고 제안 013의 백업 가용성을 차단하므로 별도 migration 계획이 타당하다. 계획은 기존 감사 데이터 삭제 없이 모순을 제거하고 백업 검증을 정상화할 수 있다. 현재 단계에서는 코드·운영 DB·서버 권한을 변경하지 않았으며, 다음 단계는 모의 DB 기반 Staging 구현과 실패 주입 검증이다.
