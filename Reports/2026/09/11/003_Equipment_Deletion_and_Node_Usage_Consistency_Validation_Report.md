# [검토 보고서] 장비 삭제·옵션 관리·노드 사용량 정합성 Validation 1~8

## 결론

모델 전체 경로 계획과는 별도로 유지하되, 앞서 작성한 장비 삭제·노드 사용량 계획에는 병합하는 것이 적절하다. 장비 삭제 후 옵션 보존이 원인으로 확정됐고, 관리자 옵션 관리가 그 기능 공백의 직접 해결책이기 때문이다. 제안 047의 노드 관리 완성도에 속하므로 새 제안 번호를 만들지 않는다.

현재 소스에는 장비 소프트 삭제 컬럼이 없고 삭제 API는 하드 DELETE를 수행한다. 장비 삭제 후 카탈로그 옵션이 의도적으로 보존되며, 관리자 화면은 옵션 수를 표시하지만 옵션을 관리하는 UI가 없다. 생성·삭제 API 일부는 이미 있으므로 서비스 계층 검증과 목록·수정 API·통합 UI를 보강하는 방향이 타당하다.

## Validation 1~8

1. 거버넌스: recorder·governance 검증 후 계획·스키마·문서 노드를 적용했다. 운영 코드와 DB는 변경하지 않았다. 다른 세션의 기존 dirty 변경을 보존했다.
2. 사용자 의도: 장비 삭제 후 남은 옵션을 관리자가 직접 관리해 노드 정리를 완료할 수 있게 한다. 자동 연쇄 삭제로 확대하지 않는다.
3. 정적 논리: delete_equipment는 장비만 삭제하고 옵션을 남긴다. 노드 삭제는 option_count가 있으면 차단된다. 따라서 노드별 옵션 CRUD와 참조 0 조건부 삭제가 닫힌 해결 경로다.
4. 운영 영향: 옵션 생성·수정·삭제 API, 관리자 스냅샷, 라인업 관리 화면, 감사 로그가 영향 대상이다. 예상 DB migration은 없으며 운영 스키마 확인 전 임의 컬럼 추가는 금지한다.
5. 보안·예외: 관리자 권한과 CSRF를 유지하고, 옵션 삭제 직전 정식·임시저장 장비 참조를 transaction 안에서 재검증한다. 승인 대기 옵션은 결재 절차를 우회하지 않는다.
6. 롤백: 집계 및 UI 문구는 코드 역패치로 복구 가능하다. 스키마 변경이 필요하면 별도 백업·Up/Down 계획 없이는 진행하지 않는다.
7. 휴먼 에러·UX: 노드 카드 안에서 옵션을 펼쳐 계층 맥락을 유지하고, 장비 참조 수와 삭제 차단 이유를 명시한다. 장비 삭제가 옵션·노드 자동 삭제로 오해되지 않게 한다.
8. AI 메타: 옵션 잔존이라는 사용자 확인을 반영해 이전 가설 목록을 정정했다. 로컬 equipment.db가 0바이트인 한계를 유지하며 실데이터 검증 완료를 주장하지 않는다.

## 판정

기존 002 계획으로의 병합과 관리자 옵션 관리 범위 확정은 타당하다. 현재 요청은 계획에 한정되므로 Staging·운영 코드·DB 변경은 수행하지 않는다.
