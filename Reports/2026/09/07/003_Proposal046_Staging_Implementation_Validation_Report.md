# [Staging 구현 검증 보고서] 제안-046 서버 점검 모드

작성일: 2026-09-07
범위: `Staging/` 복사본의 점검 모드 구현. 운영 `app.py`, 운영 템플릿, 운영 DB와 서버는 변경하지 않았다.

## 구현 결과

- `Staging/app.py`에 DB 외부 점검 상태 파일의 원자적 저장·읽기, 상태 파일 손상 시 `RECOVERY` 처리, 중앙 `before_request` 게이트를 추가했다.
- 점검 활성화 시 `Role != 'admin'` 계정의 `SessionToken`을 일괄 갱신한다.
- 일반 사용자는 HTML에서 점검 안내를 받고 API에서 503을 받는다. 관리자는 `DRAINING`과 `RECOVERY` 상태에서 계속 접속한다.
- 관리자 센터에 `maintenance_admin` 메뉴·권한·화면과 점검 활성화·해제 API를 추가했다.
- 로그인 화면은 점검 문구·예상 종료 시각을 표시하고, 점검 중 회원가입·비밀번호 재설정 UI를 숨긴다.
- 세션 폴링 스크립트는 점검 503을 `login?error=maintenance`로 전환한다.

## 1단계 — 거버넌스 준수성

- Staging에만 구현했고 운영 파일을 수정하지 않았다.
- 신규 함수와 라우트에 역할·의존성 관계·변경 영향 메타 주석을 추가했다.
- 결과: 통과.

## 2단계 — 사용자 의도 달성도

- 로그인 화면 점검 안내, 관리자 외 로그인 차단, 기존 비관리자 세션 만료, 관리자 제어 화면을 구현했다.
- 제안-013의 DB 복원 동결·온라인 복원 기능은 이 단계에 포함하지 않고 다음 작업으로 분리했다.
- 결과: 통과.

## 3단계 — 논리적 구동 가능성

- 상태 파일은 `os.replace`로 교체하고 DB와 분리해 복원 후에도 점검 상태가 유지된다.
- 일반 사용자 요청은 중앙 게이트에서 차단되며, 로그인 페이지는 만료된 세션을 비워 리다이렉트 루프를 방지한다.
- 제한: 다중 프로세스 배포 여부는 서버에서 확인해야 한다. 파일 상태는 공유되지만 현재 구현의 프로세스 내 잠금은 다음 제안-013 복원 조정기에 맞춰 확장해야 한다.
- 결과: 조건부 통과.

## 4단계 — 운영 병합 영향

- `before_request`, 로그인, 메뉴 초기화, 세션 폴링에 영향을 준다.
- 메뉴 추가는 `INSERT OR IGNORE`와 기본 권한 등록으로 기존 DB를 파괴하지 않는다.
- 결과: 조건부 통과. 운영 병합 전 전체 라우트 허용 목록을 재검토한다.

## 5단계 — 보안과 엣지 케이스

- 상태 변경 API는 로그인, 관리자 역할, CSRF, 현재 비밀번호, 확인 문구를 모두 요구한다.
- 상태 파일은 웹 정적 경로 밖의 Flask instance 경로를 기본값으로 사용하며 환경변수로 별도 보호 경로를 지정할 수 있다.
- 제한: 서버 운영 계정의 상태 파일 권한, HTTPS 구성, 심볼릭 링크 방어는 서버 검증 단계에서 확인해야 한다.
- 결과: 조건부 통과.

## 6단계 — 롤백

- 점검 해제 API는 명시적 관리자 재인증을 요구한다.
- 상태 파일이 손상되면 일반 운영을 열지 않고 `RECOVERY`로 처리한다.
- Staging 변경은 운영과 분리되어 있으며, 운영 병합 전까지 운영 롤백 대상이 없다.
- 결과: 통과.

## 7단계 — 휴먼 에러와 UX

- 활성화·해제는 서로 다른 확인 문구와 비밀번호 입력을 요구한다.
- 점검 안내에 사유와 예상 종료 시각을 표시하며, 자동 해제는 구현하지 않았다.
- 기존 일반 사용자 세션이 로그인 페이지에서 반복 리다이렉트되지 않도록 세션을 비운다.
- 결과: 통과.

## 8단계 — AI 메타 거버넌스

- Staging 생성은 운영 복사본에 한정했고 운영 파일을 변경하지 않았다.
- 로컬 Python 인터프리터가 실행 불가한 사실을 검증 통과로 표현하지 않고 제한으로 기록했다.
- 결과: 통과.
