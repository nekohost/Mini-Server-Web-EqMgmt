# [정적 검토 보고서] 제안-013 DB 백업·복원

작성일: 2026-09-08
작업 모드: 검토 및 비구동 정적 검사
대상: `Staging/app.py`, `Staging/templates/backup_restore.html`, `Staging/tests/test_proposal013_backup_restore.py`, `Staging/docs/proposal013-operation.md`, 제안-013 Plan·Task, 운영 원본과 systemd 서비스 파일
최종 판정: **부적합 — 현재 구현물의 운영 병합 차단**

## 1. 판정 요약

제안-013의 기본 흐름은 구현되어 있다. 점검 모드에서 관리자만 백업·후보 업로드·복원을 수행하고, SQLite 온라인 백업, 세션 만료, 복원 상태 폴링, 실패 시 자동 원복을 연결한 방향도 계획과 맞는다. Python 구문, 신규 라우트 중복, 템플릿 블록과 DOM 참조, 운영 원본 비변경 상태는 정적 검사를 통과했다.

다만 현재 상태로 운영 DB를 교체하기에는 차단 결함이 남아 있다. 가장 큰 문제는 외부 작업 저널 쓰기 실패가 자동 원복 자체를 건너뛰게 할 수 있다는 점, 기존 DB 연결의 예외 경로가 연결 계수를 누수하여 복원을 계속 막을 수 있다는 점, 후보 DB 호환성 검사가 실제 스키마 제약과 인덱스를 검증하지 않는다는 점이다. 민감한 상태 토큰의 URL 노출, 후보·백업 파일의 불완전한 수명 관리, 내부 오류 노출과 필수 감사 기록 누락도 운영 반영 전에 수정해야 한다.

이 보고서는 2026-09-07의 `Proposal013_Staging_Implementation_Validation_Report`보다 나중에 수행한 전수 정적 검토 결과이며, 운영 적합성 판단에서는 본 보고서를 우선한다.

## 2. 차단 결함

### B-01. 저널 쓰기 실패가 자동 원복을 건너뛸 수 있음 — 치명

- 근거: `Staging/app.py:1855`에서 `rolling_back` 상태 저널을 먼저 쓴 뒤 `Staging/app.py:1856`부터 원복을 시작한다.
- `update_database_job()`은 `Staging/app.py:1759-1763`에서 파일 쓰기·`fsync`·`os.replace` 예외를 그대로 전파한다.
- 작업 디스크가 가득 찼거나 권한·I/O 오류가 나면 원복 준비 상태 기록이 실패하고, 같은 `try` 안의 실제 원복 코드가 실행되지 않는다. 이후 코드는 자동 원복 실패로만 표시한다.
- 조치 조건: 실제 DB 원복을 상태 저널과 분리하고, 저널 실패 여부와 관계없이 원복을 최우선 실행해야 한다. 저널 실패도 별도 제한 정보로 기록해야 한다.

### B-02. 추적 DB 연결 계수가 예외 경로에서 누수될 수 있음 — 치명

- 근거: 모든 기존 `get_db_connection()`을 전역 추적 연결로 바꿨지만, 기존 코드는 중앙 `finally` 종료 규약을 사용하지 않는다.
- 예시: `get_server_session_role()`은 `Staging/app.py:1110`에서 연결한 뒤 SQLite 예외가 발생하면 `Staging/app.py:1116-1117`로 이동하여 연결 계수를 명시적으로 내리지 않는다. `validate_maintenance_admin_request()`도 `Staging/app.py:1583-1589`에서 같은 구조다.
- `TrackedDatabaseConnection.close()`이 호출돼야 `ACTIVE_DATABASE_CONNECTIONS`가 감소한다. 누수된 계수가 남으면 `Staging/app.py:1809-1812`의 복원 배출이 제한 시간 뒤 실패한다.
- 조치 조건: 연결 획득과 반환을 중앙 context manager 또는 요청 범위 관리자로 강제하고, 모든 정상·예외·조기 반환에서 계수 해제를 보장해야 한다. 전체 75개 연결 획득 지점을 재검사해야 한다.

### B-03. 후보 DB 스키마 호환성 검사가 계획보다 약함 — 높음

- 근거: `Staging/app.py:1678-1697`은 테이블 이름, 컬럼 이름, 적용 마이그레이션의 포함 관계만 비교한다.
- 컬럼 타입·NULL·기본값·PK, 외래키 정의, 인덱스·UNIQUE, 트리거·뷰를 비교하지 않는다. 이름만 같은 비호환 DB가 검사를 통과해 복원 후 쿼리 오류나 중복 데이터 허용 등 의미적 손상을 일으킬 수 있다.
- Plan 5절의 필수 컬럼·인덱스 검사와 수용 기준을 충족하지 못한다.
- 조치 조건: 운영에 필요한 스키마 계약을 명시하고 `sqlite_master`, `PRAGMA table_info`, `foreign_key_list`, `index_list/index_info` 결과를 정규화해 비교해야 한다.

### B-04. 모니터 토큰이 URL 쿼리에 노출됨 — 높음

- 근거: 화면은 `Staging/templates/backup_restore.html:146`에서 `?token=...`을 사용하고 서버는 `Staging/app.py:2052`에서 쿼리 값을 읽는다.
- 앱 내부 접근 로그는 `request.path`만 저장하지만 운영 Gunicorn `--access-logfile -`는 HTTP 요청선을 journal에 기록하므로 쿼리 토큰이 운영 로그에 남을 수 있다.
- 조치 조건: 토큰을 URL에서 제거하고 전용 요청 헤더로 전달해야 한다. 상태 응답의 캐시 금지는 유지한다.

### B-05. 민감 DB 파일 수명과 디스크 용량 통제가 불완전함 — 높음

- 다운로드 백업은 `Staging/app.py:1920-1926`에서 생성한 뒤 삭제·보존 기한·개수 제한이 없다. 반복 GET으로 백업 사본과 디스크 사용량이 계속 증가한다.
- 후보 DB의 30분 만료 삭제는 `Staging/app.py:1939`의 다음 업로드 요청 때만 실행된다. 추가 업로드가 없거나 프로세스가 재시작되면 만료 파일이 계속 남는다.
- 업로드, 다운로드 백업, 복원 직전 백업을 만들기 전 가용 디스크 검사도 없다. 저장 공간 부족은 자동 원복과 저널 기록까지 동시에 훼손할 수 있다.
- 조치 조건: 다운로드 완료 후 임시 사본 삭제, 후보 파일의 기동 시·주기적 청소, 자동 백업의 명시적 보존 정책, 작업 전 필요 공간 계산을 구현해야 한다. 백업 생성 GET에는 CSRF 방어가 없어 반복 유도에 취약하므로 CSRF가 적용된 생성 요청으로 바꿔야 한다.

### B-06. 내부 오류가 공개 상태와 응답에 그대로 포함될 수 있음 — 높음

- 근거: 복원 예외는 `Staging/app.py:1852`의 `str(error)`를 작업에 저장하고, `Staging/app.py:2057-2060`에서 `error`를 공개 상태로 반환한다. 업로드·재검증 오류도 `Staging/app.py:1982`, `2020`에서 원문을 반환한다.
- 파일시스템·SQLite 오류 문자열에는 내부 경로와 구조가 포함될 수 있다. 이는 Plan 4절의 내부 파일 경로와 SQL 오류 비노출 조건을 위반한다.
- 조치 조건: 사용자 응답은 정해진 오류 코드와 한국어 안전 문구만 사용하고, 기술 상세는 접근 제한된 서버 로그에 분리해야 한다.

### B-07. 계획된 비교 정보와 감사 추적이 누락됨 — 중간

- `inspect_database_file()`의 반환은 `Staging/app.py:1661`처럼 크기·필수 테이블 건수·무결성뿐이다. Plan에 명시된 파일 해시, 생성·업로드 시각, 스키마 버전 차이가 화면에 표시되지 않는다.
- DB 감사 기록은 `RESTORE_DATABASE`와 `RESTORE_DATABASE_FAILED`만 존재한다. Plan이 요구한 백업 다운로드와 후보 검증 기록이 DB 감사 로그와 외부 저널에 남지 않는다.
- 조치 조건: 비교 메타데이터와 각 민감 작업의 성공·실패 감사를 추가하되 비밀번호·토큰·내부 경로는 기록하지 않아야 한다.

### B-08. 검증 시나리오가 수용 기준보다 부족함 — 높음

- 작성된 테스트는 정상 복원, 복원 후 인증 실패 원복, 필수 테이블 누락의 3개다.
- Plan 8절의 손상 후보, 잠금·배출 시간 초과, 적용 중 실패, 자동 원복 실패가 없고, 업로드 상한, 인증·권한·CSRF, 병렬·중복 복원, 상태 토큰, 민감정보 비노출, 백업 다운로드도 검증하지 않는다.
- 조치 조건: 차단 결함 수정 후 실패 주입을 포함한 테스트를 보강하고 Linux 격리 DB에서 실행해야 한다.

### B-09. 신규 코드가 프로젝트 주석 규약을 충족하지 않음 — 거버넌스 차단

- 함수 메타 주석은 대부분 존재하지만 신규 코드의 모든 행에 설명 주석이 있지는 않다.
- `engineering.code-comments`는 함수·API 메타 주석과 모든 코드 행의 상세 주석을 함께 요구한다.
- 조치 조건: 운영 병합 전 신규 제안-013 변경분의 주석을 활성 규약에 맞춰 보완해야 한다.

## 4. Validation 1~8

### 1단계 — 거버넌스 준수성: 실패

Staging 격리, 운영 원본 보존, 외부 의존성 미추가는 통과했다. 신규 코드의 행 단위 상세 주석이 부족하여 활성 주석 규약은 실패했다. 운영 DB와 사용자 소유 `equipment.db`는 열거나 수정하지 않았다.

### 2단계 — 사용자 의도 달성도: 부분 통과

점검 중 관리자 웹 화면에서 백업·업로드·복원을 수행하고 한국어 확인 문구를 쓰는 핵심 동선은 존재한다. 파일 해시·시각·스키마 버전 비교와 백업·후보 검증 감사 기록은 누락됐다.

### 3단계 — 논리적 구동 가능성: 실패

SQLite 온라인 백업과 자동 원복의 기본 순서는 타당하다. 저널 쓰기 실패가 원복을 막는 예외 결합, 연결 계수 누수 가능성, 저장 공간 고갈 경로가 남아 있다. 실행 테스트가 아닌 구문·구조 검사만 수행했다.

### 4단계 — 운영 병합 영향: 실패

신규 라우트 충돌은 없다. 그러나 `get_db_connection()` 전체를 추적 연결로 바꾸므로 제안-013 이외의 모든 기존 DB 기능이 영향을 받는다. 단일 워커 전제는 현재 systemd와 일치하지만, 누락 파일이나 환경변수의 부분 병합은 복원 안전성을 깨뜨린다.

### 5단계 — 보안과 예외: 실패

관리자·CSRF·파일 크기·후보 계정 검증은 긍정적이다. 쿼리 문자열의 모니터 토큰, 원문 오류 반환, 민감 사본의 불완전한 정리, 백업 생성 GET의 CSRF 부재는 운영 보안 조건을 충족하지 못한다.

### 6단계 — 롤백과 역방향 파급: 실패

복원 직전 백업과 원복 검증 코드는 있다. 그러나 저널 I/O 실패가 실제 원복보다 앞서 예외를 내면 자동 원복이 실행되지 않는다. 프로세스 강제 종료 시 수동 복구 절차만 존재하며 Linux 장애 주입 검증도 아직 없다.

### 7단계 — 휴먼 에러와 UX: 부분 통과

점검 모드 선행 안내, 후보 검증 후 복원 영역 표시, 현재·후보 비밀번호와 한국어 확인 문구는 구현됐다. 비교 정보가 계획보다 부족하고 상태 폴링 실패 후 재시도 수단이 없으며, 백업 반복 클릭과 복원 후 비밀번호 값의 브라우저 메모리 정리가 없다.

### 8단계 — AI 메타 거버넌스: 통과

검토 범위를 구현·병합으로 확대하지 않았고 운영 파일·DB·Git 원격을 변경하지 않았다. 임시 정적 검사 파일은 검사 직후 삭제했다. 이전의 긍정적 보고서와 충돌하는 발견을 숨기지 않고 본 보고서가 최신 판정임을 명시했다.

## 5. 정적 테스트의 한계와 다음 검증 조건

프로젝트 규칙에 따라 Windows에서 Staging Flask 앱을 구동하지 않았다. 따라서 이 보고서는 실제 HTTP 응답, SQLite 백업 실행, 스레드 경합, Gunicorn journal 로그 형식을 실행으로 확인한 결과가 아니다.

운영 병합 검토를 다시 시작하려면 B-01부터 B-09까지 수정하고 영향받은 Validation 단계부터 재검증해야 한다. 그 뒤 Linux 격리 DB에서 단위·실패 주입 테스트와 브라우저 동선을 통과해야 한다. 현재 단계에서는 운영 병합, commit, push를 수행하면 안 된다.
