# [계획 검증 보고서] Rule 5-1-2 개발·검증·배포 순서 명확화

검증 대상: `Plans/2026/09/08/001_Rule_5-1-2_Deployment_Test_Order_Reinforcement_Plan.md`
결론: **적합 — 5-1-2와 대응 실행 노드의 동시 보강 권고**

## 1단계 — 거버넌스 준수성: 통과

현재 manifest 검증은 40개 노드, 오류 0건, 경고 0건으로 통과했다. `sync-status`는 기준 Rule과 현재 Rule의 SHA-256이 `0366391F84CF1F9C6AA30DB4E8E60927A05903A159E13AB815A2C586445AD7EB`로 같고 변경 섹션이 없으며 `inSync: true`임을 확인했다. `sync-plan`은 5-1-2의 대상 노드를 `operations.server-execution` 하나로 확정했다.

계획은 Rule 자체를 수정하지 않았으며 구현 승인 전 Staging 후보 작성, Rule·노드·map·baseline·manifest 동시 갱신, 정규 파서 검증 절차를 포함한다.

## 2단계 — 사용자 의도 달성도: 통과

사용자가 확정한 흐름인 “로컬 Staging 구현과 소스 정적 판단 → 운영 소스 병합 → Git push → Linux pull → 실제 구동·검증”을 번호 순서로 고정했다. 운영 소스 반영과 실행 중 Linux 서비스 적용을 별도 용어로 정의해 핵심 혼동 원인을 제거한다.

## 3단계 — 정적 논리: 통과

현행 5-1-1의 Windows 구동 금지, 5-1-3의 Staging 정적 검토, 7-3-3의 승인 후 병합·정리와 모순이 없다. 실제 테스트 환경을 Linux로 제한하면서도 후보를 Linux에 전달하려면 먼저 운영 소스 병합과 Git push가 필요하다는 의존 관계를 명시한다.

실패 경로도 정적 실패는 Staging으로, Linux 실행 실패는 Windows 개발 흐름으로 복귀하도록 종료점이 있다. 서버에서 직접 수정하는 우회 경로는 허용하지 않는다.

## 4단계 — 운영 영향: 통과

애플리케이션 코드, DB 스키마, systemd 설정과 서비스 상태에는 변화가 없다. 영향은 AI가 이후 배포 순서를 판단하는 방식에 한정된다. 보강 후에는 Linux 실행 검증 미완료를 이유로 승인된 운영 소스 병합과 Git 전달을 잘못 차단하는 행동이 줄어든다.

단, “운영 반영”이라는 표현을 문맥 없이 계속 사용하면 혼동이 남을 수 있으므로 최종 문안과 이후 보고서에서는 `운영 소스 반영`과 `Linux 서비스 적용`을 구분해야 한다.

## 5단계 — 보안과 예외: 통과

실제 테스트는 Git으로 전달된 정확한 commit을 Linux에서 확인한 뒤 수행하도록 한다. 운영 DB를 자동으로 시험 대상으로 지정하지 않으며 격리된 모의 데이터나 사용자 승인 조건을 우선한다. 서버 주소, 자격증명, 비밀값을 새 문안에 추가할 필요가 없다.

백업 Linux 서버를 사용할 때도 사용자가 검증 대상으로 지정한 경우로 제한해 임의 외부 배포를 방지한다.

## 6단계 — 롤백: 통과

Rule 보강은 Rule·노드·추적성·manifest를 하나의 commit으로 묶어 되돌릴 수 있다. 변경 전 Rule hash와 현재 노드 digest가 계획에 기록되어 있다. 일부 파일만 반영되거나 검증 오류가 발생하면 새 거버넌스 버전을 활성화하지 않고 변경 묶음 전체를 이전 commit으로 복귀한다.

## 7단계 — 휴먼 에러 방지: 통과

번호가 있는 10단계 순서, 네 가지 용어 정의, 단계별 실패 복귀 지점을 함께 제시했다. “Linux에서 테스트”라는 단일 문장에 의존하지 않으므로 단계 생략과 선후관계 역전을 줄일 수 있다.

구현 시 기존 Staging 작업과 섞이지 않도록 소유 작업 확인을 선행 조건으로 두었다.

## 8단계 — AI 메타 거버넌스: 통과

분석 결과를 과장해 새 실행 환경이나 새 라우터를 만들지 않는다. 5-1-2와 이미 매핑된 실행 노드만 의미 변경 대상으로 제한한다. 사용자 승인 전에는 Rule과 실행 거버넌스를 수정하지 않는다.

계획 작성 중 발견된 기존의 미추적 Task·보고서·Staging 산출물은 본 계획의 소유물이 아니므로 읽거나 변경하거나 정리하지 않았다.

## 종합 판정

보강계획은 현행 규칙의 실행 장소 제한을 유지하면서 전체 전달 순서를 명확하게 만든다. 구현 범위는 5-1-2, `operations.server-execution`, human map, 섹션 기준선, manifest로 제한하는 것이 적절하다. 새 노드와 router 변경은 필요하지 않다.
