# 대화 자동 기록 장기 누락 원인 분석 보고서

- 작성일: 2026-09-08
- 대상: Codex, Antigravity/Gemini, Claude 공통 대화 기록 구조
- 판정: 구조적 결함 확인
- 변경 범위: 분석 보고서와 Task만 작성했으며 Rule·노드·라우터·애플리케이션은 변경하지 않음

## 1. 결론

장기 누락의 직접 원인은 플랫폼 원본 대화가 저장되지 않은 것이 아니다. Codex JSONL과 Antigravity 전사에는 원본이 남아 있었지만, 이를 프로젝트의 `Chat/YYYY/MM/DD.md`로 자동 복제하는 실행 파이프라인이 구현되어 있지 않았다.

현행 Rule은 이 절차를 “자동 기록 파이프라인”이라고 부르지만 실제 구성은 다음과 같다.

1. 일반 작업에서는 대화 저장 노드가 로드되지 않는다.
2. 각 AI 진입점에는 매 턴 `record-conversation`을 강제로 추가하는 지시가 없다.
3. 응답 완료 후 최종 답변과 실제 시각을 수집하는 후처리 훅이 없다.
4. 직전 턴이 Chat에 저장됐는지 다음 턴 시작 시 대조하는 체크포인트가 없다.
5. 따라서 AI가 작업 중 대화 저장을 별도 작업으로 기억하고 직접 실행한 경우에만 Chat 파일이 갱신된다.

즉 현재 구조는 자동화가 아니라 규칙 준수를 AI의 작업 기억에 의존하는 수동 미러링이다. Codex와 Antigravity에서 같은 유형의 누락이 반복된 이유도 두 플랫폼이 같은 구조적 공백을 공유하기 때문이다.

## 2. 확인된 직접 증거

### 2-1. 대화 노드는 일반 작업에서 비활성화된다

`records.conversation-integrity`, `records.conversation-storage`, `records.timestamps`, `records.encoding`은 모두 `always_load: false`이고 `source_entrypoints: []`이다.

라우터의 `conversation-record` 규칙은 다음 조건에서만 해당 노드를 로드한다.

- intent: `record-conversation` 또는 `append-chat`
- path: `Chat/**`

실제 라우터 재현 결과는 다음과 같다.

| 요청 유형 | 로드 결과 |
| --- | --- |
| `implement` + `Staging/app.py` | staging·파일 편집 노드만 로드, 대화 저장 노드 없음 |
| `question` | 기본 4개 노드만 로드, 대화 저장 노드 없음 |
| `record-conversation` + `Chat/**` | 대화 저장 노드 로드 |

사용자의 일반 지시는 구현·검토·질문 intent로 분류되므로, 에이전트가 대화 저장 intent를 임의로 함께 추가하지 않으면 기록 규칙 자체를 읽지 않는다.

### 2-2. 세 AI 진입점에 매 턴 기록 지시가 없다

루트 `AGENTS.md`, `GEMINI.md`, `CLAUDE.md`는 모든 관련 intent와 path를 context 도구에 전달하라고 지시한다. 그러나 모든 대화에 `record-conversation` intent와 `Chat/**` path를 자동으로 추가하라는 항목은 없다.

세 진입점 모두 일반 작업에서는 사용자용 `Rule.md`를 읽지 않도록 명시한다. 따라서 Rule 제6조에만 적힌 자동 기록 요구는 일반 작업 시 에이전트의 활성 컨텍스트에 들어오지 않는다.

### 2-3. 실행 가능한 자동 기록기가 없다

프로젝트의 JavaScript, Python, PowerShell, JSON/JSONC 파일과 활성 Git hook을 검색한 결과 다음 기능을 수행하는 실행 코드가 없다.

- 사용자 메시지 수신 이벤트 감지
- AI 중간 안내 또는 최종 응답 이벤트 감지
- 플랫폼 원본에서 시각·원문 추출
- 날짜별 Chat 파일 append 또는 시간순 삽입
- 직전 기록 cursor와 원본 ordinal 비교
- 누락 시 자동 재시도·복구

현재 존재하는 것은 규칙 문서, 라우팅 정의와 플랫폼 capability 설명뿐이다.

### 2-4. 최종 응답을 턴 내부에서 완전하게 저장할 수 없다

Rule은 최종 응답의 원문과 실제 발생 시각을 저장하도록 요구한다. 그러나 AI가 최종 응답을 보내기 전에 파일을 쓰면 아직 최종 송신 시각이 존재하지 않고, 최종 응답을 보낸 뒤에는 해당 AI 턴이 종료되어 추가 파일 작업을 실행할 수 없다.

이 문제는 2026-09-03의 기존 순서 역전 진단에서도 확인됐다. 당시 Chat에 기록한 최종 응답 시각과 플랫폼이 사후 부여한 실제 송신 시각이 달랐다.

따라서 정확한 최종 답변 자동 기록에는 다음 둘 중 하나가 반드시 필요하다.

- 플랫폼 또는 IDE의 응답 완료 후 후처리 훅
- 다음 턴 시작 시 직전 턴 원본을 대조·보완하는 내구성 있는 재조정 절차

현행 구조에는 둘 다 없다.

### 2-5. 완료 검사가 Chat 완전성을 검사하지 않는다

거버넌스 validate는 manifest, 노드, YAML과 추적성 원장의 정합성을 검사한다. 특정 대화 원본의 마지막 event ID와 Chat의 마지막 기록을 비교하지 않는다.

Validation 1~8도 계획·검토 시에만 라우팅되며, 대화 완전성을 판정하는 전용 단계나 실패 조건이 없다. 일반 질문에는 Validation 노드조차 로드되지 않는다.

### 2-6. 플랫폼 capability가 보장을 선언하지 않는다

Codex capability는 정확한 타임스탬프와 전체 transcript export를 `false`로, Antigravity는 `runtime-dependent`로 선언한다. 이는 플랫폼 원본을 이용한 자동 기록이 환경별로 달라질 수 있음을 뜻하지만, 이 차이를 흡수하는 어댑터나 fallback 실행기는 구현되어 있지 않다.

## 3. Rule 문구에서 발생한 오해

Rule 제6-2의 제목은 “자동 기록 파이프라인”이고, 6-2-1은 별도 승인 없이 기록한다고 규정한다. 그러나 “승인이 필요 없다”는 것은 자동 실행을 의미하지 않는다.

또한 6-2-2는 사용자에게 전달한 중간 안내를 “최종 저장 시” 함께 기록한다고 하면서 긴 작업 중 매 과정마다 Chat을 즉시 갱신하도록 강제하지 않는다. 다음 항목이 정의되어 있지 않다.

- 최종 저장을 반드시 실행해야 하는 정확한 시점
- 저장 지연의 최대 허용 범위
- 응답 완료 후 실행 주체
- 실패 시 재시도와 다음 턴 복구
- 성공 여부를 확인하는 receipt 또는 cursor

이 때문에 “마지막에 저장한다”는 의무가 턴 종료와 함께 실행되지 않은 채 사라질 수 있다. 긴 작업일수록 중간 안내가 누적되어 누락 규모가 커진다.

## 4. 9월 누락 양상이 보여주는 결과

2026-09-08 재복원에서 기존 516건을 보존하면서 누락 406건을 추가했다.

| 날짜 | 추가 복원 |
| --- | ---: |
| 9월 1일 | 7 |
| 9월 2일 | 4 |
| 9월 3일 | 51 |
| 9월 4일 | 58 |
| 9월 7일 | 197 |
| 9월 8일 | 89 |

누락은 한 번의 쓰기 실패가 아니라 여러 날짜와 두 플랫폼에서 반복됐다. 특히 긴 작업이 이어진 9월 7일에는 197건이 누락됐다. 이는 자동 writer가 실패한 흔적이 아니라, 애초에 매 턴 실행되는 writer와 checkpoint가 없다는 분석과 일치한다.

9월 8일 Codex 기록을 처음 찾지 못했던 별도 오류도 있었다. 9월 8일 대화가 9월 7일에 시작한 연속 세션 JSONL 끝에 저장됐는데, 최초 복구가 폴더 날짜와 오래된 SQLite 투영본만 조회했다. 이는 복구 도구에도 thread cursor와 이벤트 시각 기반 탐색이 필요하다는 추가 증거다.

## 5. 원인 우선순위

| 우선순위 | 원인 | 영향 |
| --- | --- | --- |
| Critical | 대화 저장 노드가 일반 요청에서 자동 로드되지 않음 | 대부분의 일반 턴이 기록 절차를 인식하지 못함 |
| Critical | 응답 완료 후 writer·hook 부재 | 최종 답변 원문과 실제 시각을 같은 턴에서 확정 저장할 수 없음 |
| Critical | 원본 event와 Chat을 대조하는 cursor·완료 gate 부재 | 누락이 발생해도 장기간 탐지되지 않음 |
| Major | Rule의 “자동” 명칭과 실제 수동 절차의 불일치 | 에이전트와 사용자가 자동 보장을 오해함 |
| Major | 긴 작업의 저장 checkpoint·최대 지연 미정의 | 중간 안내와 여러 턴이 대량으로 누적 누락됨 |
| Major | 플랫폼별 원본 위치·형식 차이를 흡수하는 어댑터 부재 | Codex 연속 세션 및 Antigravity 상위/하위 전사 판별 오류 가능 |
| Minor | `Chat/`이 Git 추적 제외 | 로컬 보관 정책에는 맞지만 CI·커밋 기반 누락 감지가 불가능함 |

## 6. 필요한 개선 방향

완전 자동 기록을 보장하려면 규칙 문구만 강화해서는 부족하다. 다음 실행 구조가 필요하다.

1. 세 AI 진입점이 모든 사용자 턴에 `record-conversation`을 필수 intent로 자동 결합한다.
2. 대화 무결성·저장·시각 노드를 항상 로드하거나 기본 로드 집합에 넣는다.
3. 사용자 메시지와 사용자에게 전달한 중간 안내는 발생 즉시 event ID와 함께 저장한다.
4. 플랫폼 응답 완료 후 훅이 최종 답변 원문과 실제 시각을 기록한다.
5. 후처리 훅을 제공하지 않는 플랫폼은 다음 턴 시작 시 직전 원본 event 이후의 모든 항목을 먼저 재조정한다.
6. 플랫폼별 adapter가 폴더 날짜가 아니라 event timestamp와 thread ID·ordinal로 원본을 탐색한다.
7. `last_source_event_id`, `last_chat_hash`, `recorded_at`을 가진 로컬 cursor를 유지한다.
8. 다음 작업을 시작하기 전에 `원본 마지막 event == Chat 마지막 반영 event`를 검증하고, 불일치하면 작업보다 복구를 먼저 수행한다.
9. 저장 성공 receipt가 없으면 “기록 완료”로 판단하지 않는다.

최소한 진입점과 라우터만 보강하면 누락 빈도는 줄일 수 있지만, 최종 응답의 정확한 사후 시각과 프로세스 중단 복구까지 보장하지는 못한다. 사용자가 요구한 “자동적으로 기록”을 충족하려면 post-response hook 또는 다음 턴 reconcile 중 하나는 필수다.

## 7. Validation 1~8

1. 거버넌스: Rule 제6조, 실행 노드, 라우터, 세 AI 진입점과 추적성 원장을 함께 대조했다. 거버넌스 validate는 40개 노드, 오류 0, 경고 0이다.
2. 사용자 의도: 복구 방법이 아니라 장기 누락이 반복된 원인과 자동 기록 보장 실패를 분석했다.
3. 정적 논리: 일반 구현·질문 context를 실제 재현하여 대화 저장 노드가 로드되지 않음을 확인했다.
4. 운영 영향: 분석 문서만 추가했으며 애플리케이션, DB, Rule과 라우터는 변경하지 않았다.
5. 보안: 플랫폼 원본의 내용은 누락 수와 구조 확인에만 사용하고 비밀값을 보고서에 복사하지 않았다.
6. 롤백: 신규 Task와 보고서만 생성했으므로 이 분석 자체는 애플리케이션 동작에 영향을 주지 않는다.
7. 휴먼 에러: “승인 없는 기록”을 “자동 실행”으로 오인하기 쉬운 문구와 저장 시점 미정의를 확인했다.
8. AI 메타: 특정 AI 한 번의 실수로 축소하지 않고 세 플랫폼이 공유하는 라우팅·실행·검증 공백을 원인으로 판정했다.

## 8. 최종 판정

대화 누락은 사용자의 기대가 잘못된 것이 아니다. 현재 Rule의 명시적 목표는 사용자의 기대와 같다. 문제는 그 목표가 실행 가능한 자동화, 라우팅 강제, 사후 기록 훅과 완료 검증으로 연결되지 않았다는 점이다.

따라서 현재 시스템은 “대화 자동 기록 기능이 구현된 상태”로 볼 수 없다. 대화 보존 규칙과 수동 복구 절차만 존재하는 상태다.
