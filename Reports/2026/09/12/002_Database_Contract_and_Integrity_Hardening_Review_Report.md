# 데이터베이스 계약 및 무결성 강화 계획 검토 보고서

## 1. 결론

읽기 전용 운영 DB 감사에서 발견된 잔여 문제는 신규 통합 계획으로 관리하는 것이 적절하다. 기존 계획 002와 003은 각각 장비·옵션 수명주기와 독립 감사 로그·백업 장애라는 완료된 범위를 갖는다. 이번 문제를 그 문서에 병합하면 완료 상태와 새 구조 변경의 승인·rollback 경계가 흐려진다.

접근 로그는 관리자가 필요에 따라 구성한 운영 정책이라는 사용자 판단을 반영해 개선 대상에서 제외했다. 보고서의 나머지 발견인 FK 강제, 마스터 삭제, 스키마 계약, 레거시 테이블, 조회 성능만 계획에 포함했다.

## 2. 근거 요약

- 운영 DB는 현재 `integrity_check=ok`, `foreign_key_check=0건`으로 즉시 손상된 상태가 아니다.
- 일반 연결은 FK 강제를 보장하지 않아 이후 쓰기의 참조 무결성 위험이 남는다.
- 카테고리·제조사 삭제 코드는 실제 NOT NULL 스키마와 충돌한다.
- 신규 생성과 역사 migration의 물리적 컬럼 순서 차이는 의미상 동등한 DB를 호환성 검사에서 오판할 수 있다.
- 레거시 `equipment`는 비어 있지만 현재 rollback 및 필수 테이블 검사와 연결되어 즉시 삭제할 수 없다.
- 일부 조회는 인덱스 후보가 있으나 rowid 최신순 조회처럼 SCAN 표기만으로 추가 인덱스를 정당화할 수 없는 사례도 있다.

## 3. Validation 1~8 검토

### 1단계 — 거버넌스·입력 검증

Recorder preflight와 governance validate가 통과했고, plan·architecture·migration intent 및 대상 코드·문서 경로로 생성된 두 context pack을 순서대로 검토했다. 기준 증거는 운영 서버 코드 `main@1f19fd30b626`와 읽기 전용 DB 감사 결과다.

### 2단계 — 사용자 의도 검증

요청은 접근 로그를 허용된 현행 정책으로 유지하고 나머지 문제의 계획을 세우는 것이다. 구현·운영 반영으로 확대하지 않고 계획, Task, 검토 보고서만 작성했다.

### 3단계 — 정적 설계 검증

선후 관계는 연결 FK 강제와 삭제 계약 정리, 스키마 버전·호환성, 레거시 전환, 인덱스 측정 순이다. 레거시 DROP은 `down_migration.py` 대체 전 금지해 순환 의존과 복구 경로 상실을 막았다.

### 4단계 — 운영 영향 검증

FK 활성화는 기존에 숨어 있던 고아 데이터를 드러낼 수 있고 인덱스·migration은 잠금과 쓰기 비용을 발생시킬 수 있다. 운영 복제 staging, 점검 모드, 적용 전 백업, 적용 후 무결성 검사와 중단 조건을 계획에 포함했다.

### 5단계 — 보안·권한 검증

접근 로그 정책은 사용자 승인 범위대로 유지한다. 실제 DB 수정은 애플리케이션 migration과 제한된 운영 절차로만 수행하며 수동 직접 변경을 허용하지 않는다. 외래 키 강제 실패 시 이를 우회해 서비스를 계속하지 않도록 했다.

### 6단계 — rollback 검증

코드, 인덱스·버전, 데이터 이동, 테이블 DROP의 rollback 성격을 분리했다. 특히 레거시 DROP은 이번 1차 범위에서 제외해 검증 전 비가역 변경을 차단했다.

### 7단계 — 사람의 조작 오류 검증

삭제 대상과 병합 대상을 명시적으로 분리하고 참조 건수, 동일 대상, 승인 상태, 이름 충돌을 사전 검사한다. 운영 적용은 해시와 스키마 지문이 기준선과 다르면 중단한다.

### 8단계 — AI·기준선 오류 검증

로컬 작업공간이 원격보다 뒤처진 상태였으므로 로컬 코드만을 운영 기준으로 오인하지 않고 서버 HEAD와 실제 DB를 기준으로 삼았다. 인덱스 후보는 추론만으로 확정하지 않고 staging 측정으로 채택 여부를 결정한다.

## 4. 최종 판정

계획은 구현 가능한 순서, staging 게이트, 운영 중단 조건, rollback 경계를 갖췄다. 현 단계 판정은 **계획 적합 / 구현 미착수**다. 다음 작업에서는 Task 체크리스트를 순서대로 수행하고 staging 검증 보고서가 통과한 뒤에만 운영 반영을 제안해야 한다.

## 5. 사용자 운영 반영 승인 후 재검토 (2026-09-12)

현재 사용자가 중단 작업과 계획 작업의 구현·운영 적용을 끝까지 승인했다. 별도 승인 대기 상태는 해제했다.

1. 거버넌스: recorder ensure와 validate 통과, 전 대상 context 노드 읽기, 기존 미완료 Task 004와 릴리스 Task 005 확인. 현재 HEAD 1f19fd3으로 fast-forward하고 수정은 Staging에서 수행했다.
2. 의도: DB 개선의 1차 범위를 구현한다. 기존 5개 릴리스는 미완료 Linux 검증·배포 기록을 완결한다. 별도 미구현 로드맵 작업은 원래 Task의 계획 작성 범위를 완결한다. 주석 전면 재구축 제외와 접근 로그 정책을 유지한다.
3. 논리: FK 초기화와 연결 실패 cleanup을 분리해 계수 중복 감소를 방지한다. 마스터 삭제·병합은 동일 writer transaction과 감사 callback을 사용한다. 물리 cid 외의 SQL 문자열·CHECK·COLLATE·generated·FK·index 계약을 보존한다.
4. 운영: 필요한 변경은 4개 인덱스·user_version·명명 migration 1개이며 업무 행을 수정하거나 테이블을 DROP하지 않는다. 사본 기동 전후 모든 기존 테이블의 행 지문을 비교한다.
5. 경계: ID 범위·중복·bool·JSON 타입·CSRF·관리자 권한을 검사한다. 대기 승인 참조는 삭제/병합을 차단하며 승인 JSON을 임의 치환하지 않는다.
6. 복구: migration/down 모두 사전 온라인 백업과 원자 transaction을 사용한다. legacy equipment를 보존하고 기존 변환 스크립트의 중복 적용을 버전으로 차단한다.
7. 사용자 오류: 관리자 목록에 노드·옵션·대기 승인 건수를 표시하고 직접 삭제가 막힌 경우 통폐합 동선을 안내한다. 기존 확인 대화상자는 정확한 동작에 맞게 수정한다.
8. AI 메타: 미니서버 192.168.0.166은 현재 제공된 키로 인증되지 않는다. 사용자 지정 백업 서버 192.168.0.24에서는 기존 Linux 회귀 39/39가 통과했다. 두 서버의 적용 상태를 구분하여 보고한다.

기술 근거: [SQLite 연결별 FK 활성화](https://www.sqlite.org/foreignkeys.html), [PRAGMA의 구조 정보](https://www.sqlite.org/pragma.html), [부분 인덱스의 WHERE 조건](https://www.sqlite.org/partialindex.html). 외래 키는 transaction 시작 전에 연결마다 활성화하며, 부분 인덱스는 실제 쿼리와 조건을 일치시킨다.
