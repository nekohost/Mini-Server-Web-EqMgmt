## 구현 결과

사용자의8개 요구와 기존 긴 닉네임3줄 조건을 함께 적용했다. 새 제안 번호를 만들지 않고 공통 UI019·020, 계정025·034, 관리자035, 전자결재027, 노드047의 후속 개선으로 기록한다.

| 요구 | 구현 |
|---|---|
| 메뉴명 괄호 제거 | 내 정보·웹 접근 로그 등의 부연을 제거하고 동적 메뉴 카드/권한 목록은 표시 시 정리. 가입/재설정의 Staging 제목도 정리 |

| 상단바/내 정보 아이콘 | 제거. 테마는 현재 선택값 라이트/다크/시스템, 기존 전환/저장 유지 |
| 비밀번호·탈퇴 | 프로필 하단 버튼 → 각각 native dialog. 취소/Escape·포커스 복귀·닫을 때 입력 초기화·처리 중 중복/닫기 차단 |

개인 결재함을 장비 임시저장함 안에 넣지 않은 이유는 카테고리·제조사·노드·옵션 요청을 특정 장비의 등록 상태와 무관하게 찾을 수 있어야 하기 때문이다. 관리자 처리함과 구분되도록 이름을 나의 결재함으로 정했다.

선택 여부·역할·정책 경고 등의 괄호까지 일괄 삭제하지 않았다. 메뉴 표시만 정리하고 DB 메뉴명 원문은 보존한다. 기존 오른쪽 카드형 버튼·빨간 로그아웃·파란 역할과 긴 닉네임 말줄임/전체 접근성 이름을 유지한다.

## 데이터 및 권한 계약

- `/my_approvals`, `/api/my_approvals`는 로그인과 해당 메뉴 권한을 확인한다. 조회 조건은 세션의UserId로 고정하며 관리자 호출도 본인 요청만 반환한다. 외부RequesterId/scope 입력으로 다른 사용자 조회를 확대하지 않는다.
- 전체/PENDING/APPROVED/REJECTED와 페이지 크기1~100(기본25), 최신 RequestId순을 지원한다. 잘못된 인자400, 미인증401, 권한 없음403. 사용자 화면에는 승인/반려 API 호출 기능이 없다.
- 비관리자의 기존 `/approvals` 주소는 개인 화면으로 이동한다. 기존 `/api/approvals`에도 개인 메뉴 권한을 확인해 메뉴 거부 우회를 막는다. 관리자용 전체 조회·처리 API의 기존 관리자 제한은 유지한다.
- `personal_approvals_portal_20260914`를 같은 transaction 안에서 기록하는 일회성 메뉴 마이그레이션을 추가했다. 새 최상위my_approvals 메뉴와 현재admin/user의 개인 조회 허용2행만 추가했다.
- 기존user는approvals 허용1이었으나 부모admin_center는 허용되지 않아 화면 접근이 막혀 있었다. 이 잔여 허용을0으로 옮겼다. 관리자 센터 접근을 부여하지 않았고 관리자 및 다른 권한은 그대로다. 이후 명시적으로 개인 메뉴를 거부하면 재시작 시 다시 허용하지 않는다.
- 업무 스키마 v3 및 장비·노드·옵션·결재 행은 변경하지 않았다. 새 역할이 생길 때의 권한은 관리자가 역할별 화면에서 부여한다.
- 기존 비밀번호 확인·탈퇴 확인·30일 유예 정책, 노드/옵션 참조 보호·미사용 옵션 삭제·공식 모델명은 보존한다.
