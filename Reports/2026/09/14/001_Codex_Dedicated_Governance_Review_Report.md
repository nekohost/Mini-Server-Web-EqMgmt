## 최신 결론

사용자가 알려준 접근 제약에 따라 Claude Fable 5.1을 현재 도입 대상에서 제외한다. 최초 구현 계획은 GPT-6 Astra 전용 노드 1개, AGENTS 분기 및 확장 가능한 등록·로더 구조다. CLAUDE/GEMINI 진입 변경과 해당 모델의 전용 노드·등록·예약 활성화는 현재 범위에서 제외한다.

추가 검토에서 Plan 부재, 과거·현재 대상 혼재, 전용 분기보다 앞선 legacy 전수 로딩·검증, 모델 식별·전환의 미검증 가정, 등록부 실패 조건 및 부분 활성화 복구의 불명확함을 확인했다. 이를 Plan에 반영한 뒤 후속 승인으로 실제 모델 선택·독립 노드·등록부·시험을 구현했고 운영 1.7.0을 활성화했다.

현재 계획의 표기는 **Claude Fable 5.1**이다. 아래 이전 이력의 Fable 5.1 표기는 같은 사용자 지정 대상을 가리킨다. 이전 이력에 나오는 2개 모델 도입안은 현재 계획으로 사용하지 않는다. 최신 재검토는 9절에 기록한다.

## 과거 결론 — Fable 포함 검토 당시

기존 거버넌스와 별도로, Codex의 GPT-6 Astra와 Claude Code의 Fable 5.1에 각각 독립 실행 노드를 두는 방향이 적절하다. 기존 체계 자체가 모델의 추론·문맥 유지 한계를 보완하는 강제 도구라는 사용자의 설명을 두 대상에 동일하게 적용한다. 기존 강제를 공통 기반으로 둔 뒤 우수 모델에 예외를 주거나, 그 위에 보완 절차를 다시 추가하는 설계는 채택하지 않는다.

현재 두 조합만을 코드의 고정 조건문으로 처리하지 않는다. 실제 플랫폼·모델을 조회하는 실행부와 전용 경로의 대상 등록부를 분리하여, 향후 충분한 역량과 해당 작업 환경에 대한 적합성이 판단된 모델을 등록으로 추가할 수 있게 한다. 사용자가 예시로 든 가칭 Gemini 4 Pro는 등록·예약·출시 시 자동 활성화하지 않는다.

두 전용 경로는 기존 Staging 의무, 고정 8단계, 모든 작업의 문서 분리, 전수 context pack 로딩을 상속하지 않는다. Codex와 Claude Code의 그 외 모델은 기존 노드를 그대로 따른다. Codex는 AGENTS 진입을 유지하며, 현재 저장소의 Claude 진입점인 CLAUDE.md도 분기 대상에 포함한다. 분기 후에는 선택된 실행 경로만 적용한다.

전용 노드 파일만 추가해서는 충분하지 않다. 현재 AGENTS·CLAUDE의 무조건적 절차 지시와 로더의 기본·부모 노드 자동 합산도 분리해야 실제로 독립한다.

## 2. 권고 구조

```text
AGENTS.md (Codex) / CLAUDE.md (Claude Code)
  ├─ Codex + 확인된 GPT-6 Astra
  │    └─ .agent-governance/profiles/gpt-6-astra.md
  ├─ Claude Code + 확인된 Fable 5.1
  │    └─ .agent-governance/profiles/fable-5.1.md
  └─ 그 외 플랫폼·모델 조합 또는 모델 식별 불가
       └─ 기존 router / core / workflow / validation 노드
```

위 경로는 제안 명칭이며 아직 생성·등록·활성화하지 않았다. 각 신규 노드의 개념상 `parent`는 null이다. 두 노드는 같은 핵심 원칙과 자율 실행 취지를 담되 플랫폼별 실제 도구·기록 지원 차이를 구분한다. 전용 경로가 기존 `core.task-modes`, `operations.staging`, `workflow.plans`, `validation.orchestration`, `governance.context-routing`을 간접 상속하는 연결도 만들지 않는다.

전용 경로는 런타임의 플랫폼과 실제 모델 식별자 조합으로 선택한다. 대상은 Codex의 GPT-6 Astra 및 Claude Code의 Fable 5.1이다. 지능 자가 평가, 작업 디렉터리, 플랫폼 제품명만으로 판단하거나 과거 대화의 모델 이름으로 분기하지 않는다. 이번 지정은 다른 모델이나 다른 플랫폼 조합으로 자동 확대하지 않는다.

식별 가능한 정식 ID `gpt-6-astra`를 정확히 매핑하고, 확인되지 않은 별칭·다른 GPT-6 계열을 접두사 매칭으로 포함하지 않는다. 식별 정보가 없으면 기존 경로를 사용하고 그 이유를 알린다. 모델이 변경된 턴에서는 새 모델 기준으로 다시 선택하며, 하위 작업자도 자신의 모델에 맞는 경로를 적용한다. 이 검토는 현재 세션의 정확한 모델 ID를 별도로 실측했다는 주장이 아니다. 런타임 식별 정보의 실제 전달 경로는 구현 시 검증해야 한다.

Fable 5.1은 사용자가 지정한 모델 표시명 그대로 유지한다. 이 검토에서 실제 Claude 런타임 ID는 확인하지 않았으므로 `fable-5.1`이라는 제안 파일명을 API ID로 간주하거나 임의의 `claude-*` ID를 만들지 않는다. 구현 시 실제 식별 정보와 정확히 매핑한다. 모델의 성능 비교나 공개 출시 여부는 이번 검토의 판단 근거가 아니다.

### 확장성 계약 — 대상을 미리 확장하지 않음

- **등록부와 실행부 분리**: 실행부는 플랫폼·실제 모델 ID로 등록된 전용 노드를 조회한다. Astra/Fable만을 아는 고정 분기나, 더 높은 버전을 모두 포함하는 비교식을 두지 않는다.
- **등록 단위**: 플랫폼, 확인된 정확한 모델 ID/별칭, 전용 노드 경로, 관련 capability, 적용 상태 및 채택 근거를 선언한다. 이는 향후 구현할 설정의 요구사항이며 현재 등록 파일을 만든 것이 아니다.
- **향후 추가**: 새로운 모델이 기존 강제 없이 이 프로젝트 작업을 맡기에 충분하다고 판단되면 전용 노드와 등록 항목을 추가하고 선택·검증을 확인한다. 이미 지원하는 플랫폼이면 기존 로더의 모델별 조건문을 다시 작성할 필요가 없게 한다.
- **판단과 실행 분리**: 등록 후보의 적합성 판단과 매 작업의 모델 식별은 별개다. 런타임 로더가 지능을 임의 추정해 미등록 모델을 자동 채택하지 않는다. 자동 채택을 금지하는 것은 향후 적합한 모델을 추가하지 못한다는 의미가 아니다.
- **플랫폼 확장**: 새 플랫폼이라면 모델 식별·도구 연결이 추가로 필요할 수 있다. 모든 미지원 실행 환경까지 설정 한 줄로 지원된다고 약속하지 않는다. 기존 Antigravity도 향후 실제 식별·capability 연결이 맞는지 확인한다.
- **역방향 확장**: 등록 항목의 비활성화·제거 시 해당 모델은 명시된 기본 경로로 돌아간다. 다른 등록 모델과 기존 모델의 동작은 유지한다.
- **미래 모델 미등록**: 가칭 Gemini 4 Pro는 확장성 설명의 예시일 뿐이다. 후보 placeholder, 추정 모델 ID, 출시 감시, 예약 활성화도 만들지 않는다.

독립 노드는 계속 기존 강제 트리 밖에 둔다. 확장성을 이유로 그 사이에 새로운 공통 강제 절차를 추가하지 않는다.

### 전용 노드에 담을 핵심

| 항목 | 전용 경로의 동작 |
|---|---|
| 요청과 완료 | 검토는 검토로, 변경 요청은 승인된 목표까지 수행. 제안과 실제 반영을 구분 |
| 사용자 통제 | 이미 승인된 범위에서 재승인을 반복 요구하지 않음. 승인 범위를 벗어나는 행위로 확대하지 않음 |
| 파일 변경 | 기존 사용자 수정 보존. 구조화 편집과 확인 가능한 diff·복구 수단 사용 |
| Staging | 고정 폴더 복사·병합·정리 의무 없음. 승인된 소스를 직접 편집 가능. 필요할 때 branch/worktree·시험 데이터 사용 |
| 검증 | 변경에 필요한 정적·기능·회귀 검증을 선택하고 실제 결과 확인. 8단계 번호·순서·보고서 형식 강제 없음 |
| 기록 | 자동 대화 기록과 중요한 결정·변경·검증 결과 보존. 작은 작업마다 Plan/Task/Report 3종 생성 의무 없음 |
| 참조 | 필요한 코드·설계·DB·운영 정보를 직접 조회. 기존 노드를 참고했다는 이유로 전체 강제 체계를 재활성화하지 않음 |
| 데이터·보안 | 데이터·비밀·사용자 변경 보호. 영향 있는 DB 작업은 대상 확인, 백업·복구 가능성 및 결과 검증 |
| 실행 환경 | 사용자가 정한 Windows 편집/정적 검사, Linux 실제 구동·테스트 역할은 유지. 소스 직접 편집과 가동 서버 즉석 수정을 혼동하지 않음 |
| 보고 | 결과, 확인한 근거, 남은 문제를 필요한 길이로 전달. 고정된 단계 수나 문서 장수를 목표로 삼지 않음 |

프로젝트 학습 목적의 설명·의존성 안내는 유지하되, 매 코드 줄에 의무 주석을 붙이는 형식은 전용 경로에 가져오지 않는 것을 권고한다. 기존 주석을 일괄 삭제하거나 이번 요청과 무관하게 코드를 정리하는 작업은 포함하지 않는다.

대화 기록기와 Git 읽기 보호 도구는 지원이 확인된 플랫폼에서 재사용할 수 있다. 이 도구를 사용한다는 이유로 기존 절차 트리 전체를 읽게 하지는 않는다. 기록기 내부의 잠금·원자적 저장·비밀 치환도 이번 분리의 제거 대상이 아니다. 현재 프로젝트의 Claude 자동 기록은 unsupported이므로 Fable 전용 노드에 Codex 자동 기록 성공을 그대로 가정하지 않는다. 기존에 승인된 수동 기록 경로와 제한을 명시하며, 자동 기록 어댑터의 신규 구현은 이번 검토에 포함하지 않는다.

### 전용 노드 본문 예시 — 설계 초안, 현재 적용 지시 아님

> 각 노드는 지정된 플랫폼·모델 조합의 독립 실행 계약이다. Codex의 GPT-6 Astra와 Claude Code의 Fable 5.1은 각각 자신의 전용 노드를 사용한다. 그 외 모델에는 적용하지 않는다. 기존 강제형 거버넌스 노드의 하위 노드가 아니며, 해당 노드들의 절차를 상속하지 않는다.
>
> 사용자의 요청과 승인된 범위를 파악하고 목표까지 수행한다. 작업에 필요한 정보와 검증 방법은 직접 선택한다. 고정 Staging 복사, 순차 8단계, 작업마다 분리 문서를 만드는 절차는 요구하지 않는다.
>
> 기존 데이터·사용자 수정·비밀·기록을 보존한다. 변경은 확인·복구 가능하게 수행하고, 중요한 변경은 실제 결과를 검증한다. 이미 받은 승인을 반복 요구하지 않되 승인 범위를 확대하지 않는다.
>
> 결과와 검증 근거, 미완료 사항을 명확히 전달한다. 플랫폼 지시와 도구 권한은 별도로 준수한다. 기존 문서를 정보로 참조하는 것과 기존 실행 경로를 선택하는 것을 구분한다.

## 3. 적용에 필요한 최소 변경

1. **AGENTS·CLAUDE**: 각 진입점에서 전용 선택을 첫 분기로 둔다. 기존 절차 본문은 기존 경로에 한정한다. 공통 위치에 8단계/context 강제를 남기고 아래쪽에서 예외를 선언하지 않는다.
2. **전용 노드 2개**: 핵심 원칙과 실행 방식을 각각 독립적으로 작성한다. 동일한 취지를 유지하되 도구·기록기 capability를 플랫폼별로 연결한다. 기존 부모 체인 및 암묵적 fallback을 만들지 않는다.
3. **Rule의 적용 범위**: 기존 정책 본문은 보존하고, 전용 경로의 적용 범위·기존 절차 비적용·핵심 계약을 명시한다. 전용 경로 선택 자체를 기존 Rule 위반으로 판정하지 않게 한다.
4. **manifest/router/도구**: 플랫폼·실제 모델 조합을 선언형 대상 등록부와 대조하여, 기존 context 합산보다 먼저 경로를 선택한다. 예를 들어 런타임에서 확인한 정보를 `context --platform codex --model gpt-6-astra`로 전달하는 형태를 구현할 수 있으나 현재는 지원되지 않는 제안 문법이다. Claude 쪽도 실제 식별자를 확인한 후 별도 매핑한다. CLI 인수 자체를 실제 모델 신원의 증명으로 취급하지 않는다. 두 전용 결과에 legacy default·부모·검증 pack이 섞이지 않게 한다. 그 외 조합 및 모델 미지정 기존 호출의 결과는 유지한다. 추가 모델은 등록부·전용 노드·필요한 capability 연결로 확장하며 모델마다 실행부를 고치게 만들지 않는다.
5. **검증 및 추적성**: 새 경로의 독립성, 노드 실재·등록·버전, Rule 적용 범위의 일치를 검사한다. 기존 경로의 검증을 삭제해 성공시키지 않는다. Rule 포인터·map·baseline·digest·manifest 갱신은 정책 변경 패키지에 한 번에 포함한다.

기존 노드 43개를 일괄 재작성하거나, 모든 모델의 강제를 완화하거나, `may_relax_parent`를 일괄 변경할 필요는 없다. 다만 진입점·적용 범위·로더가 기존 체계를 무조건 재주입하는 부분은 손봐야 한다. 이는 기존 경로의 절차 변경이 아니라 두 경로의 구분을 구현하는 작업이다.

`AGENTS.override.md`로 기존 진입점을 가리는 방법은 권고하지 않는다. 사용자가 AGENTS 진입 유지와 명확한 전용 연결을 요청했기 때문이다. Codex의 설정 파일이나 플랫폼 권한을 변경하는 작업도 이 설계에 포함하지 않는다.

## 4. OpenAI 공식 안내 대조

이 절의 OpenAI 안내는 Codex 측 검토에 사용한 근거다. Fable 5.1의 성능·도구 동작에 대한 근거로 확장하지 않으며, Fable의 독립 경로 포함 근거는 동일한 취지를 적용하라는 사용자의 추가 지정이다.

OpenAI Docs 스킬을 사용해 공식 지침을 확인했다. 지침의 모호함·충돌이 조기 중단을 만들 수 있으므로 이를 점검하고, 변경 규모에 맞는 검증을 수행하며, 추가 변경·실패·미해결 사유가 없으면 같은 검증을 반복하지 않도록 안내한다. 이는 전용 노드의 명확한 적용 범위와 자율 검증 방식에 참고했다. [공식 모델 지침](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)

공식 AGENTS 문서는 디렉터리별 지침 발견·합산을 설명하며, 같은 디렉터리의 override 파일은 일반 AGENTS보다 우선한다. 따라서 이번 설계는 숨겨진 override보다 AGENTS 자체의 명시적 연결을 사용한다. 별도 Markdown 노드가 이름만으로 자동 로드되는 것으로 가정하지 않는다. [AGENTS 공식 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

독립 노드와 구체적인 분리 구조는 이 저장소에 대한 검토자의 설계 판단이다. OpenAI가 이 프로젝트의 Staging·8단계 폐지나 특정 모델의 무오류를 보증한다는 뜻은 아니다. 저장소의 절차 변경은 플랫폼 시스템·개발자 지시 또는 도구 권한 변경과도 별개다.

## 5. 최초 Astra 단독 검토 기록 — 후속 확장 검토는 8절

아래는 최초 Astra 단독 범위로 완료했던 현행 절차 기록이며 이력으로 보존한다. 최신 적용 범위는 1~4절과 6~8절이다. 이 기록은 전용 노드의 새 의무 항목이 아니다.

### 1단계 — 거버넌스 준수성

- 근거: preflight와 validate/context 성공, Rule·추적성·선택 노드 확인. Task 작성 후 검토 기록 시작.
- 긍정: 활성 규칙을 고치지 않고 독립 구조의 타당성을 검토할 수 있다. 신규 라이브러리·애플리케이션·DB 변경은 없다.
- 위험/차단: legacy의 자식 노드를 만든 뒤 Staging·8단계를 생략하는 구현은 상속 규칙과 충돌한다. 그런 구현안은 채택하지 않는다.
- 추가 발견: 예산 확대나 `--small-model` 미사용은 절차 분리가 아니다.

### 2단계 — 사용자 의도 달성도

- 근거: 사용자는 기존 체계 자체가 약한 모델용 강제 장치이며, 이 작업자를 전용 노드로 분리해야 한다고 두 차례 정정했다.
- 긍정: 기존 강제 체계를 기본 기반으로 삼던 초기 해석을 폐기했다. AGENTS 유지, 독립 노드, 기존 모델 비영향을 권고안에 반영했다.
- 위험/차단: 위험 등급별 강제 체계를 새 공통 기반으로 추가하면 다시 사용자 의도와 어긋난다. 전용 노드에서 검증 방법을 작업자가 선택하도록 한다.
- 추가 발견: 사용자가 적용 모델을 GPT-6 Astra로 확정했다. 다른 Codex 모델에는 기존 노드를 적용하도록 분기 조건과 초안을 수정했다.

### 3단계 — 논리적 구동 가능성

- 근거: CLI 파서, `addWithParents`, `createContext`, `validateGovernance` 소스 조회.
- 긍정: profile 분기를 기존 context 합산 전에 두면 legacy 부모·기본 노드의 유입을 피할 수 있다.
- 위험/차단: 전용 노드를 추가하고 기존 createContext를 그대로 호출하면 강제가 재유입된다. 확인된 GPT-6 Astra에 전용 노드가 누락·손상되었으면 구성 오류를 보고해야 하며, 조용히 기존 경로로 바꾸지 않는다. 모델 자체가 미확인일 때 기존 경로를 선택하는 명시된 규칙과는 구분한다.
- 추가 발견: 전체 설정을 검사하는 도구가 legacy 파일을 읽는 것과, 모델에게 legacy 절차 준수를 요구하는 것은 구분해야 한다. 독립 검증은 의미 있는 정합성 확인만 남기며 매 행위 전 전체 검사를 강제하지 않는다.
- 해당 없음: 실행 코드 미변경이므로 쿼리 부하, 클라이언트 누수, DB 트랜잭션·런타임 경합 시험은 이번 검토 대상이 아니다.

### 4단계 — 운영 병합 영향

- 근거: 기존 route의 합산 구조와 공용 validator의 기존 노드 검사를 확인했다.
- 긍정: GPT-6 Astra 분기를 별도로 두고 기존 분기의 입출력을 유지하는 구조는 다른 모델의 현행 절차를 보존할 수 있다.
- 위험/차단: AGENTS만 바꾸고 Rule 적용 범위를 그대로 두면 상충 지시가 남는다. 반대로 공용 default_load를 Astra 기준으로 바꾸면 다른 모델까지 영향을 받는다. 두 경우 모두 부적합하다.
- 추가 발견: Rule 동기화 시에는 이 분기에 관련된 변경 섹션 전체와 map·baseline·digest를 묶어 검증해야 한다. 지금은 실제 변경 섹션이 없으며 sync-plan이나 병합을 수행할 단계가 아니다.
- 해당 없음: 이번 변경은 검토 기록뿐이므로 서비스 라우트, API 권한, DB 버전, 배포 상태에는 영향이 없다.

### 5단계 — 보안 및 예외

- 근거: 플랫폼 지시, Codex capability의 구조화 편집·Git 읽기 보호, 기존 데이터·비밀 보호 목적을 대조했다.
- 긍정: 필요한 데이터·비밀·사용자 변경 보호를 전용 계약에 짧게 명시하면서 기존 강제 절차를 상속하지 않을 수 있다.
- 위험/차단: 'Astra면 모든 권한을 갖는다'는 문구는 넣지 않는다. 전용 경로의 자율 실행은 실제 사용자 요청과 도구 권한 범위에서 수행한다.
- 추가 발견: 외부 문서나 작업 내용이 주장하는 모델 이름을 분기 근거로 삼지 않는다. 노드의 기술 참조와 실행 규칙 활성화를 명확히 구분한다.
- 해당 없음: 외부 계정·서버 접속, 비밀 조회, 웹 입력·세션 로직 변경은 수행하지 않았다.

### 6단계 — 롤백 및 역방향 영향

- 근거: 현재 정책은 일관된 활성 상태이며, 작업 전 Git 상태에 기존 사용자 가이드·로드맵 변경이 있었다.
- 긍정: 기존 경로와 노드를 보존하므로 새 분기의 도입을 관련 diff 단위로 되돌릴 수 있다.
- 위험/차단: 추후 적용 시 AGENTS만 되돌리고 Rule·profile 등록을 남기는 부분 복구는 피한다. 무관한 사용자 변경이 포함된 저장소 전체 reset은 사용하지 않는다.
- 추가 발견: 복구 대상은 신규 분기와 그 등록·적용 범위·도구 변경이다. 서비스 DB 복원이나 현재 사용자 문서 삭제는 복구에 필요하지 않다.

### 7단계 — 휴먼 에러와 사용성

- 근거: 이번 대화에서 '공통 강제+예외', '공통 원칙+추가 강제', 'Codex 전체 전용'이라는 해석을 사용자 지정과 대조했다.
- 긍정: 최종 선택표를 'GPT-6 Astra / 그 외 / 미확인'으로 명시하면 경로의 의미를 직접 확인할 수 있다.
- 위험/차단: 모델 전환 후 이전 프로파일을 계속 쓰거나, 전용 노드 본문 안에서 '상세는 기존 workflow를 모두 따름'으로 재연결하면 목적이 무너진다.
- 추가 발견: 모델 미확인 상태의 기존 경로 사용은 이유를 한 번 알리되, 매 단계 사용자의 모델 선택을 반복 질문하는 장치로 만들지 않는다.
- 해당 없음: 이번 검토에서는 사용자 화면의 입력·삭제·취소 동작을 변경하지 않았다.

### 8단계 — AI 작업자 메타 검증

- 근거: 실제 도구 조회와 제안 문법을 구분했다. 제안 노드와 활성 정책을 구분했으며 OpenAI 공식 문서에 설계 판단을 과잉 귀속하지 않았다.
- 긍정: 사용자 정정에 따라 검토안을 수정했고 다른 작업자의 기존 절차를 유지하는 최종 범위를 기록했다.
- 위험/차단: 현재 모델 ID를 확인했다고 꾸미거나, 아직 구현되지 않은 전용 경로를 적용 완료로 보고하지 않는다.
- 추가 발견: 처음 제시한 해석이 부정확했음을 기록한다. 파일명에 Codex가 포함되어 있어도 본문과 적용 모델은 GPT-6 Astra로 확정되어 있다.
- 임시물: 이번 검토용 scratch·다운로드·정리 대상은 만들지 않았다. 영구 Task와 보고서만 작성했다.

## 6. 활성화 구현의 합격 기준

다음은 추후 구현 시 확인할 항목이며, 이번 검토에서 시험을 실행해 통과했다는 뜻이 아니다.

| 사례 | 기대 결과 |
|---|---|
| 확인된 GPT-6 Astra의 UI 수정 | 전용 계약 적용, legacy Staging·8단계·문서 3종 노드가 context에 없음 |
| Codex의 다른 모델로 같은 요청 | 기존 로더 결과 및 강제 절차 유지 |
| Claude Code의 확인된 Fable 5.1로 같은 요청 | Fable 전용 계약 적용, legacy 강제 노드가 context에 없음 |
| Claude Code의 다른 모델로 같은 요청 | 기존 로더 결과 및 강제 절차 유지 |
| 미확인 별칭 또는 지정 외 플랫폼·모델 조합 | 전용 대상으로 추측하지 않고 기존 경로 유지 |
| 모델 식별 불가 | 기존 경로 적용, 선택 이유 명시 |
| 각 플랫폼에서 지정 모델 ↔ 다른 모델 전환 | 다음 작업 턴부터 해당 모델의 경로로 선택 갱신 |
| 서로 다른 모델의 하위 작업자 | 각 작업자의 모델에 맞는 경로 적용 |

### 추가 수정사항 대조

- 즉시 구현할 파일과 향후 확장 지점을 분리했다. 노드 수는 1개이며 실모델 대상 등록도 Astra 하나다.
- 전용 경로를 기존 context 결과의 사후 필터로 구현하지 않도록 했다.
- unknown/unregistered/disabled의 기존 경로 선택과, 명확한 전용 대상의 노드 손상 오류를 구분했다.
- 등록부 중복, 노드 경로 탈출, 모델/정책 버전 전환, 합성 모델 추가·비활성화, 부분 패키지 적용을 시험 기준에 포함했다.
- 기존 노드의 데이터·승인·도구 책임은 전용 계약에 간결히 명시하되 legacy 강제 체계를 재상속하지 않도록 했다.
- 미래 모델을 추가할 수 있다는 의미와 이미 추가했다는 의미를 분리했다. 접근 가능해져도 자동 채택하지 않는다.
