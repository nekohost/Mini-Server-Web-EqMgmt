# 관리자용 Strata 구현 및 검증 결과

사용자가 권장 방식의 구현을 승인했다. Staging에서 관리자용 메뉴·iframe·인증 연계와 Nginx 스트리밍 중계를 구현한다. 검증 결과 승인 전에는 운영 소스를 병합하지 않는다.

## 구현 전 순차 검토

1. 거버넌스: recorder와 profile 절차를 수행했고 legacy context와 governance validate가 통과했다. 신규 후보는 Staging에 격리한다.
2. 사용자 의도: 기존 장비관리 메뉴 안에 260의 Strata UI를 제공한다. 전체 UI는 관리자 전용이며 모델은 260에 둔다.
3. 논리: Flask는 짧은 권한 확인·화면 응답만 처리하고 AI 스트림은 Nginx가 전달한다. 원본 UI 경로와 API 기준 주소를 조정한다.
4. 운영 영향: 기존 메뉴 테이블에 추가만 하며 기본 기능 비활성, 장비 데이터 스키마 변경 없음, 기존 worker 수 변경 없음으로 설계한다.
5. 보안: API 키 서버 보관, 관리자 확인, 현재 로그인 토큰 검증, 요청 경로·메서드 허용 목록, POST Origin·CSRF, 사용자별 저장소 공간과 로그아웃 정리를 적용한다.
6. 롤백: 기능 비활성과 전용 Nginx 설정 제거로 화면·중계를 함께 닫는다. 장비 DB 전체 복원이나 모델 파일 삭제를 하지 않는다.
7. UX: 연결 상태, 모델 대기, 재시도, 로그인 만료, 모바일 높이와 취소를 처리하고 공통 장비관리 내비게이션을 유지한다.
8. AI 범위: 기존 수정은 보존한다. 비밀 값과 운영 서버 호스트 신뢰를 추측하지 않고, 정적 검사와 Linux 실제 실행 결과를 구분한다.

## 현재 제약

운영 백업 서버에 대한 비대화형 SSH 확인은 신뢰된 ED25519 호스트 키가 없어 실패했다. 호스트 검증을 해제하거나 새 키를 임의 신뢰하지 않았다. Windows에서 애플리케이션을 실행하지 않는 프로젝트 절차에 따라, 실제 동작 검증은 신뢰된 Linux 연결에서 수행해야 한다.

## Staging 구현 결과

`Staging/Strata_Integration_20261030/overlay/`에 신규 파일 20개를 준비했고, 기존 `app.py`에는 import, 포털 메뉴 필터, 기능 설치 호출의 세 변경을 별도 후보로 작성했다. 후보가 요구하는 원본 해시는 다음과 같다.

```text
91a81cbcf9b416da3c01e8f6c4d7102215695af9edc8f83d48e0e27ad0c941b8
```

신규 파일 경로의 기존 파일 유무도 검사하여 기존 작업을 덮어쓰지 않도록 했다. `candidate.json`이 정확한 변경을 정의하고 `app.patch`는 검토용 diff다.

구현에는 관리자용 `/ai` 화면, `/ai/console` iframe, 세션별 저장소, API 키 브라우저 저장·전송 차단, POST CSRF·Origin, Nginx 원래 메서드·URI의 허용 목록, 짧은 health 확인, MIT 라이선스를 보존한 고정 Strata UI, 스트리밍·취소 전달 설정과 비공개 키 include 생성 도구가 포함된다. MCP 도구는 임베디드 UI에서 기본 비활성으로 두고 관리자가 명시적으로 선택할 수 있게 했다.

## 정적 검증 후 1단계부터 8단계 재확인

1. 거버넌스: 활성 규칙 검사 통과. 신규 코드는 Staging에만 있으며 기존 운영 소스에는 병합하지 않았다.
2. 의도: 장비관리 프레임 안에 Strata 전체 UI를 넣는 관리자 메뉴를 구현했다. 일반 사용자 개방과 모델 이전은 범위 밖으로 유지했다.
3. 논리: 후보의 앱 통합 결과를 메모리에서 AST로 파싱하고, Python 3개, JavaScript·MJS 4개, Jinja 템플릿 2개를 검사했다. 실제 앱 import·서버 실행은 없었다.
4. 운영 영향: 원본 `app.py` 해시 보존, 신규 파일 충돌 없음, 장비 DB를 열지 않음, 기능 기본 비활성, 긴 스트림은 Nginx로 분리했다. 실제 Nginx syntax·스트리밍 검증은 미실행이다.
5. 보안: 관리자·현재 세션 검사, 비밀 없는 인증 응답, POST Origin·CSRF, 경로·메서드 허용 목록, upstream Cookie 제거, 고정 서버 주소와 API 키 비공개 include가 정적 검토 대상이다. 실제 요청 경계 테스트는 Linux 전용으로 준비했으나 아직 실행하지 않았다.
6. 롤백: 기능 비활성 시 화면·API 검사와 메뉴 필터가 닫힌다. 전용 Nginx 경로도 함께 차단하는 절차를 문서화했고 기존 DB 항목 전체를 되돌리는 동작은 없다.
7. UX: 상태·모델 대기·재시도·접근 거부 메시지와 프레임 크기를 구현했다. 세션별 저장과 계정 전환 정리, 연결 실패 시 iframe 종료를 넣었다. 모바일·실제 화면과 사용자 상호작용 검증은 미실행이다.
8. 작업 범위: 기존 기능·제안 원장의 선행 변경을 보존했다. 실제 키를 읽거나 생성·공개하지 않았고, 운영 프로세스·방화벽·Nginx 설정을 변경하지 않았다. 실제 동작 검증을 정적 통과로 대체해서 보고하지 않는다.

## 테스트 및 실행 상태

- 정적 검사: 통과. 상세 결과는 Staging의 `validation.json`에 기록했다.
- Python 격리 동작 테스트 23개: 준비 완료, 미실행. 실제 기존 로그인·권한 함수의 AST를 fixture에 넣어 사용하는 방식이며 운영 `app.py`를 import하지 않는다.
- 브리지 동작 테스트 6개: 준비 완료, 미실행. Request body·AbortSignal 보존, CSRF·키 제거, 저장소 분리, 외부 요청 차단, 접근 거부 처리를 다룬다.
- Linux Nginx `-t`, 실제 인증 서브요청·스트리밍, 브라우저: 미실행.
- C 운영 소스 병합, Git commit·push, Linux 서비스 적용: 미실행.
- 새 핵심 주석은 EN rev.1로 작성했으며 프로젝트 규격의 한국어 동기화 감사는 별도 인계 대상으로 남는다. 다른 작업자가 감사한 것으로 표기하지 않았다.

## 다음 단계

프로젝트 규칙의 Staging 결과 승인 후, 이 후보를 C 프로젝트의 운영 소스로 병합할 수 있다. 이는 실제 Linux 서비스 배포와 구분된다. Linux 적용·실행 검증에는 신뢰된 SSH 접속 환경, 실제 Nginx 설정·모듈 확인과 기존 Strata API 키의 보호된 서버 설정이 필요하다. API 키를 대화나 소스에 적지 않는다.

## SSH 해결 후 병합 재개

사용자가 SSH 설정 완료 후 기존 작업 재개와 운영 소스 병합 → Git 반영 → 서버 pull 순서를 명시했다. 현재 PC와 서버의 기준 commit은 `db89543a490f7caad4c1f8948fbe075afdf98c00`로 일치했고 서버 추적 소스에 변경이 없었다. 최초 Staging 정적 검사를 다시 통과한 뒤 운영 소스를 병합했다.

기존 app.py에는 세 통합 지점만 수정했고 신규 파일은 정적 검사 도구를 포함해 21개다. 운영 파일과 최종 후보의 원시 바이트는 21/21 일치한다. 운영 소스의 정적 검사 결과 Python 5개·JavaScript 4개·Jinja 2개 통과, 앱 실행·DB 열기·동작 테스트 없음이다. 최초 후보 manifest·patch·검사기·결과는 이 보고서 옆 `strata-integration-candidate/`에 보존한다. 기존 다른 작업의 dirty 변경은 이번 commit에서 제외한다.

백업서버의 실제 앱은 단독 Python app.py 프로세스이며 확인한 systemd 유닛은 비활성/미등록 상태다. Nginx auth_request 모듈은 존재하지만 운영 설정은 root만 읽을 수 있고 sudo 비밀번호가 필요하다. Git pull과 Linux 검증을 먼저 수행하고, Nginx·환경 설정·기존 프로세스의 안전한 재시작은 준비·복구 경로를 갖춘 적용 단계에서 처리한다.
