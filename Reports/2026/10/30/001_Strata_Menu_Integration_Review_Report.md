# 장비관리 메뉴의 Strata 웹 화면 통합 검토

장비관리 시스템에 새 메뉴를 만들고 그 화면 안에 R7-260에서 실행 중인 Strata 웹 화면을 표시할 수 있다. 초기 범위는 관리자에게 기존 Strata 화면을 제공하고, 장비관리 서버가 로그인과 권한을 확인한 뒤 260으로 통신을 중계하는 방식을 권고한다. 모델 추론은 260에서 계속 수행한다.

검토 기준 경로는 사용자 지시에 따라 `C:\Project\Mini-Server-Web-EqMgmt`로 전환했다. 이 경로는 개발·검토 사본이며, 현재 서비스 중인 Linux 장비관리 서버의 배포 경로를 옮겼다는 뜻은 아니다. 메뉴, DB, 서비스 코드, 프록시와 Strata 설정은 변경하지 않았다. 프로젝트 절차의 대화 기록과 이번 검토 문서만 작성했다.

위 HTTP 확인은 읽기 전용 GET으로 수행했다. 모델 생성, 설정 변경, 모델 로드·언로드, 서비스 재시작 요청은 보내지 않았다. Strata는 HEAD 요청에 501을 반환하므로 단순 HEAD 실패를 서비스 장애로 판단하지 않았다.

추가 프론트엔드 프레임워크 없이 현재 Vanilla JavaScript, 공통 템플릿, iframe으로 초기 화면을 구성할 수 있다. 중계는 이미 사용 중인 Nginx를 활용하는 안이며, `auth_request` 모듈의 설치 여부는 운영 서버에서 확인해야 한다. 모듈이 없으면 지원 가능한 인증·중계 구성부터 다시 선택한다.

## 권고하는 초기 구성

경로는 아직 만들지 않은 설계 예시다.

```text
장비관리 로그인
  → 새 Strata 메뉴
  → 장비관리 내부 화면 /ai
  → 화면 안의 iframe /strata/
  → 장비관리 로그인·메뉴 권한 확인
  → Nginx가 Strata 화면·API를 260으로 중계
  → 260이 모델을 실행하고 답변을 스트리밍
```

메뉴 화면 주소와 중계 주소를 구분하면 화면 라우트와 프록시 경로가 충돌하는 것을 피할 수 있다. 중계 대상은 설정으로 고정된 260 한 곳으로 제한하며, 브라우저가 보내는 임의 URL을 서버가 대신 요청하는 형태로 만들지 않는다.

장비관리 화면을 그린다는 이유만으로 iframe 내부까지 자동 로그인되는 것은 아니다. 메뉴 진입 화면, Strata HTML·정적 파일, 채팅 API, 설정·모니터 API를 각각 어느 권한으로 허용할지 정해야 한다. 최초에는 관리자만 전체 UI를 사용하고 일반 사용자는 기본 거부하는 구성이 적합하다.

Strata API 키는 중계 서버에서 보호하고 요청할 때만 260에 전달하는 구성을 권고한다. 공동 키를 HTML·JavaScript·브라우저 localStorage에 자동 배포하면 장비관리 로그아웃 이후에도 그 키로 직접 접근할 여지가 생긴다. 사용자의 메뉴 권한과 Strata 공동 키를 같은 권한으로 취급하지 않는다.

## 구현 전 해결할 조건

1. **운영 서버 연결과 중계 모듈.** 실제 장비관리 운영 서버가 260의 8080 포트에 도달할 수 있어야 한다. 이번에는 5650U에서 260으로의 접근을 확인했다. 운영 서버에서의 접근, Nginx 실제 설정과 모듈, 운영 소스 버전은 아직 확인하지 않았다. 내부 HTTP 통신을 사용할 경우 운영망의 신뢰 범위를 정하고, 필요하면 TLS나 사설 터널을 적용한다.
2. **로그인과 권한의 적용 범위.** 메뉴 카드의 표시뿐 아니라 모든 중계 요청을 검사한다. 미로그인은 401, 권한 부족은 403처럼 API가 처리할 수 있는 응답으로 구분해야 한다. 기존 페이지용 로그인 리다이렉트를 인증 서브요청에 그대로 재사용하지 않는다. 권한 변경·계정 비활성·로그아웃 후 다음 API 접근도 차단해야 한다.
3. **일반 사용자와 관리 기능의 분리.** Strata에는 `/config`, `/settings`, `/metrics`, `/api/requests`와 모델 `/load`, `/unload` 등의 경로가 있다. 일부는 조건부 기능이다. 일반 사용자에게 채팅을 허용할 때는 화면 탭 숨김이 아니라 서버에서 API·메서드별 허용 목록을 적용해야 한다. 설정된 MCP 도구를 사용할 수 있는 범위도 함께 확인한다.
4. **스트리밍과 기존 서비스 응답성.** 저장소의 systemd 예시는 Gunicorn `--workers 1`이며 별도 비동기 worker 지정이 없다. 운영도 동기 worker 한 개인 경우 Flask가 긴 AI 응답을 직접 중계하면 다른 장비관리 요청을 기다리게 할 수 있다. Nginx 중계에서 응답 버퍼링·캐시, 읽기 제한 시간, 취소·연결 종료를 설계하고, 불필요한 자동 재시도로 생성 요청이 중복되지 않도록 해야 한다. 실제 운영 worker 설정은 별도 확인한다.
5. **서브경로와 화면 크기.** 현재 Strata 정적 파일·폰트·대부분 API 호출은 상대 경로라 `/strata/` 아래 재사용에 유리하다. 다만 `app.js:401`은 `location.origin`으로 API 접속 예시를 만들어 `/v1`을 붙이므로 중계 경로를 반영하도록 조정해야 한다. 뒤의 `/` 유무, 이미지 응답 URL과 다운로드 등도 검증 대상이다. 공통 헤더 아래 가용 높이, 모바일 입력창, 이중 스크롤, 복사·파일 첨부·대화 내보내기를 확인한다.
6. **CSRF와 사용자 데이터.** 서버가 API 키를 대신 붙이는 경우에도 POST의 Origin·CSRF 검증을 생략하면 안 된다. 현재 Strata 웹은 고정된 `strata.chat`, `strata.apikey`, `strata.sampling` localStorage 항목을 사용한다. 같은 브라우저에서 다른 장비관리 계정으로 로그인했을 때 이전 대화가 보이지 않도록 저장소를 계정별로 나누거나 로그아웃 시 처리해야 한다. 서버 요청 기록도 계정별 비공개 대화함으로 간주할 수 없다.
7. **iframe 신뢰와 브라우저 정책.** 동일 origin iframe은 CSS·문서 구조 분리에는 유용하지만 장비관리와 독립된 보안 경계를 제공하지 않는다. Strata UI와 업데이트를 신뢰할 수 있는 범위를 정한다. 강화된 격리가 필요하면 별도 origin과 인증 연계를 선택한다. 최종 HTTPS 응답의 CSP `frame-src`·`frame-ancestors`, X-Frame-Options, 쿠키·클립보드 정책도 확인한다. 보안 헤더를 전역으로 해제하지 않는다.
8. **260 장애와 세션 만료.** 260이 꺼졌거나 모델이 준비되지 않았을 때 해당 메뉴 안에서 상태를 안내하고 다른 장비관리 기능을 사용할 수 있어야 한다. iframe의 load 이벤트만으로 서버 정상 여부를 확정하지 않는다. 긴 답변 도중 장비관리 세션 만료·상위 화면 새로고침이 발생할 수 있으므로 입력 보존과 진행 중 연결의 처리도 정한다.

## 순차 검증 결과

### 1단계 거버넌스

`C:\Project\Mini-Server-Web-EqMgmt`의 프로젝트 절차를 읽고 대화 기록 preflight, profile 선택, governance validate와 전체 context pack 확인을 수행했다. profile은 `runtime-session-mismatch`로 legacy 경로를 선택했고, validate는 오류·경고 없이 통과했다. 검토 Task를 먼저 작성했다. 구현·운영 반영 승인은 없으며, 서비스 코드·DB·프록시 수정으로 진행하지 않았다. 외부 Strata 프로젝트는 읽기 전용 참고 범위다.

### 2단계 사용자 의도

기존 장비관리 메뉴 안에서 260의 실제 Strata 화면을 사용하는 목적에 iframe 재사용이 맞는다. C 폴더는 검토 사본으로 사용하고, 추론은 260에 둔다. 관리자용 전체 UI와 일반 사용자용 채팅은 권한·데이터 분리 범위가 달라 구현 전에 구분해야 한다. 사용자가 화면 전체 이식을 요청했다는 이유로 일반 사용자에게 모든 운영 API 권한을 주지 않는다.

### 3단계 논리와 연결

메뉴 DB, 공통 프레임, 상대 경로 정적 자원, API 키 인증과 SSE 응답이 연결 가능한 구조임을 확인했다. 읽기 전용 GET 확인은 공개 서비스 302, Strata 화면 200, health 정상, 키 없는 보호 API 401이었다. 서비스 코드·프록시를 만들거나 모델 생성·부하 시험을 수행한 결과는 아니다. 운영 서버의 중계 모듈과 260 접근이 실제 구현 전 확인 조건이다.

### 4단계 운영 영향

신규 내부 화면과 전용 프록시 경로를 사용하고 기존 `/api/`·정적 파일 경로를 가로채지 않는 방향이다. 기존 메뉴·권한 테이블의 추가 항목으로 설계할 수 있으며 장비 데이터 스키마 변경은 현재 목적에 필요하지 않다. 장시간 중계를 기존 단일 동기 worker에 맡기는 설계는 응답성을 해칠 수 있다. 260 장애를 장비관리 로그인·일반 메뉴의 장애로 전파하지 않도록 분리한다. 이번 검토에서 운영 변경은 하지 않았다.

### 5단계 보안과 예외

공동 API 키의 서버 보관, 모든 중계 경로의 세션·메뉴 권한, 쓰기 요청의 CSRF·Origin 검증, 고정 upstream, 요청 크기·동시 사용 제한, 설정·모니터 API 분리가 필요하다. 같은 origin iframe과 공유 localStorage는 사용자별 격리를 자동 제공하지 않는다. 일반 사용자에게 전체 UI를 그대로 제공하는 안은 이 조건이 해결되기 전에는 권고하지 않는다. 실제 비밀 값은 문서와 출력에 포함하지 않았다.

### 6단계 롤백

구현 시 별도 기능 스위치로 메뉴 화면과 중계 접근을 함께 차단할 수 있어야 한다. 메뉴만 감추고 API 중계를 남기는 롤백은 불완전하다. 기존 메뉴·권한 항목을 보존하며 새 항목과 설정만 되돌리는 절차를 계획한다. Strata 모델·가중치·기존 대화 파일을 삭제하거나 장비 DB 전체를 과거 백업으로 덮어쓸 이유는 없다. 이번에는 구현을 하지 않아 운영 롤백 실행 대상은 없다.

### 7단계 사용성과 오조작

공통 헤더·뒤로 가기, 260 미연결 안내, 장시간 대기·취소, 세션 만료 시 입력 보존, 모바일 화면과 다운로드가 검증 대상이다. Strata의 원래 “this PC” 안내는 메뉴 사용자의 브라우저 기기에서 추론한다는 오해를 줄 수 있으므로 실제 260 처리 구조에 맞춘 문구를 검토한다. 로드·언로드와 공유 설정 변경은 관리자 기능으로 구분한다. 실제 iframe 화면·모바일 상호작용 시험은 구현 후 검증으로 남는다.

### 8단계 AI 작업 범위

코드에서 읽은 사실, GET으로 관찰한 응답, 제안 설계와 미확인 운영 조건을 구분했다. 모델 요청·설정 변경·프로세스 재시작·배포·외부 메시지는 수행하지 않았다. 기존 사용자 수정 사항은 보존했으며, 기능 소스·DB 대신 검토 기록만 추가했다. 복제 작업의 과거 D 경로를 현재 작업 기준으로 사용하지 않는다.

## 결론과 구현 범위

통합은 가능하다. 초기에는 관리자용 메뉴에서 기존 Strata 웹 UI를 표시하고, Nginx가 장비관리의 인증·권한 확인과 연계하여 260의 서비스로 중계하는 구성이 적합하다. 필요한 변경 범위는 메뉴·권한 항목, 내부 화면과 iframe, 인증 확인 경로, 프록시·스트리밍 설정, Strata의 경로 기준과 사용자 저장소 처리다.

구현 전에는 전체 관리 화면을 관리자에게 제공할지, 일반 사용자에게 채팅을 제공할지 정해야 한다. 또한 운영 서버의 실제 설정과 260 통신을 확인하고, 같은 origin의 신뢰 범위 또는 별도 origin 격리를 선택해야 한다. 이번 검토는 이 선택을 위한 근거이며 구현은 시작하지 않았다.

## 공식 기술 근거

- [MDN Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content): HTTPS 문서에서 HTTP iframe과 fetch는 차단 대상이다.
- [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe): 문서 삽입, same-origin 접근·sandbox 한계, load 이벤트의 제한을 설명한다.
- [MDN CSP frame ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors): 어떤 상위 문서가 화면을 삽입할 수 있는지 응답 정책으로 제한한다.
- [Nginx proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering): 버퍼링을 끈 응답을 수신 즉시 클라이언트에 전달하는 동작을 설명한다.
- [Nginx auth request module](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html): 인증 서브요청의 2xx·401·403 처리와 모듈 빌드 조건을 설명한다.

이 문서의 서비스 주소와 프로젝트 경로는 사용자의 운영 검토를 위한 정보다. 공개 배포 문서로 전환할 때에는 공개 범위를 다시 확인한다.
