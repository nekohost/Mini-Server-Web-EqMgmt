# [Staging 검증 보고서] 제안-013 DB 백업·복원 운영 반영 적합성

> **대체됨:** 이 보고서는 구현 전 복사본을 진단한 기록이다. 제안-013 구현 후 결과는 `2026-09-07_Proposal013_Staging_Implementation_Validation_Report.md`를 따른다.

작성일: 2026-09-07
대상: `Staging/app.py`, `Staging/templates/`, `Plans/2026-09-07_Proposal013_DB_Backup_Restore_Plan.md`
결론: **부적합 — 운영 병합 차단**

## 핵심 판정

현재 Staging 산출물은 제안-046 운영 파일의 격리 복사본이며 제안-013 기능 구현물이 아니다. 운영 원본과 Staging의 `app.py`, `login.html`, `maintenance.html`, `maintenance_admin.html`, `miniserver_frame.html`은 각각 차이가 없다. 계획에 명시된 신규 `backup_restore.html`은 존재하지 않고, 백업·업로드·후보 검증·온라인 복원 API와 요청 계수기, 접근 로그 워커 동결, 자동 원복 조정기도 검색되지 않았다.

따라서 현재 산출물을 운영에 병합해도 DB 백업·복원 메뉴나 기능은 생기지 않는다. 기존 제안-046 동작을 바꾸지는 않지만, 제안-013이 구현됐다고 판단하고 운영에 반영하면 관리자가 기대한 DB 안전 작업을 수행할 수 없다는 기능적 결함이 발생한다.

복원 이중 확인 문구는 영문 `RESTORE` 대신 한국어 `데이터베이스 복원`으로 계획서에 확정했다. 기존 점검 기능의 확인 문구 `점검시작`, `점검종료`도 이미 한국어임을 확인했다.

## Validation 1~8

### 1단계 — 거버넌스 준수성

- 거버넌스 매니페스트 검증은 오류 0건, 경고 0건으로 통과했다.
- 운영 파일 대신 Staging 격리 사본을 검토했다.
- 신규 외부 라이브러리나 운영 DB 변경은 없다.
- 차단 조건: 계획 산출물 자체가 없으므로 운영 병합 불가.

### 2단계 — 사용자 의도 달성도

- 긍정: 제안-046의 점검 상태와 관리자 접속 통제는 사본에 포함되어 있다.
- 실패: 화면에서 DB를 내려받고 업로드해 교체한다는 핵심 동선이 전혀 없다.
- 실패: `데이터베이스 복원` 한국어 확인 입력 UI와 서버 검증이 아직 구현되지 않았다.

### 3단계 — 논리적 구동 가능성

- 현재 파일은 운영 원본과 동일하므로 제안-046 수준의 정적 일관성은 유지된다.
- 제안-013의 정상·실패·재시도 흐름은 코드가 없어 검증할 수 없다.
- 요청 배출, 병렬 복원 거부, 로그 워커 정지와 재개, 자동 원복 종료 조건 모두 미검증이다.

### 4단계 — 운영 병합 영향

- 기존 파일과 동일한 사본을 병합하면 실질 변경이 없으므로 기존 기능을 깨뜨릴 직접 차이는 없다.
- 신규 메뉴·권한·라우트·템플릿이 없으므로 제안-013 기능도 제공되지 않는다.
- 부분 병합 위험: 계획 문서만 구현 완료로 오인하거나 빈 Staging 사본을 운영 코드로 덮어쓸 수 있다.

### 5단계 — 보안과 예외

- 기존 제안-046 API의 관리자·CSRF 검사는 유지된다.
- 업로드 크기 제한, SQLite 헤더와 무결성 검사, 파일명 무시, 경로 격리, 후보 관리자 인증, 일회성 복원 토큰이 구현되지 않았다.
- 민감한 DB 다운로드의 `Cache-Control: no-store`와 첨부 응답도 구현되지 않았다.

### 6단계 — 롤백

- Staging 사본 삭제만으로 이번 격리 준비 작업은 되돌릴 수 있다.
- 실제 DB 복원 전 자동 백업과 복원 실패 시 원복 코드가 없어 데이터 롤백 능력은 검증되지 않았다.
- 자동 원복까지 구현·모의 검증되기 전 운영 병합을 금지한다.

### 7단계 — 휴먼 에러와 UX

- 기존 점검 시작·종료는 한국어 확인 문구를 사용한다.
- 복원 화면이 없어 파일 오선택, 중복 클릭, 비밀번호 오류, 후보 DB 불일치에 대한 안내와 버튼 잠금이 없다.
- 복원 확인 문구는 `데이터베이스 복원`으로 통일해야 한다.

### 8단계 — AI 메타 검증

- 실제 존재하는 파일과 검색 결과만 근거로 판정했다.
- 복사본을 구현물로 과장하지 않았다.
- 사용자 소유의 미추적 파일과 `equipment.db`는 열거나 수정하지 않았다.

## 운영 반영 전 필수 조치

1. `Staging/templates/backup_restore.html`과 관리자 메뉴·권한을 구현한다.
2. 백업 다운로드, 후보 업로드·검증, 복원 승인, 작업 상태 조회 API를 구현한다.
3. `RESTORING` 전 요청 배출과 접근 로그 워커 동결·재개를 구현한다.
4. 복원 직전 자동 백업, 온라인 복원, 후속 무결성 검사, 실패 시 자동 원복을 구현한다.
5. 모든 파괴적 복원 확인 문구와 오류 안내를 한국어로 제공한다.
6. 모의 DB에서 정상 복원과 손상·잠금·중복·원복 실패 시나리오를 검증한다.

위 조치와 재검증이 완료되기 전까지 제안-013의 운영 반영 판정은 `차단`이다.
