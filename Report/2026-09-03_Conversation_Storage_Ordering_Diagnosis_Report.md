# 대화 저장 순서 역전 진단 보고서

## 결론

현재 문제의 주원인은 **동시 다중 작업자 환경의 구조적 문제**다. 다만 현행 규칙이 append 전용과 정확한 발생 시각을 요구하면서도 동시성·표시 순서·중간 checkpoint를 정의하지 않아, 그 구조적 문제를 막지 못하는 **정책 공백**도 함께 존재한다.

따라서 “규칙이 잘못되었다” 또는 “구조만의 문제다” 중 하나만으로 분류하면 불완전하다. 원인은 `단일 일자 Markdown 파일에 여러 AI가 직접 쓰는 구조`이고, 규칙의 미정의 영역이 그 결과를 허용하고 있다.

## 확인한 최근 증거

`Chat/2026/09/03.md`의 물리적 순서는 다음과 같다.

1. Gemini 사용자·응답 블록: `2026-09-03 14:39:10.000` 및 `14:39:15.000`
2. Codex 작업의 사용자 시작 블록: `2026-09-03 14:21:57.790`
3. Codex 중간 안내와 완료 블록: `14:22:17.323`~`14:45:34.484`

헤더 48개를 실제 파일 순서로 검사한 결과, 인접한 시간 역전은 1건이다. 즉 `14:39:15.000` Gemini 응답 뒤에 더 이른 `14:21:57.790` 사용자 발언이 붙어 있다.

Codex 플랫폼 원문은 이 사용자 발언의 실제 발생 시각을 UTC `05:21:57.790Z`(KST `14:21:57.790`)으로 보관한다. 반면 Codex는 긴 운영 승격 작업의 원문을 마무리 시점에 일괄 append했고, 그 사이 Gemini가 같은 일자 파일의 끝에 기록했다. 파일의 append 순서는 보존됐지만 사건 발생 순서는 보존되지 않았다.

추가로, Codex 최종 응답의 플랫폼 원문 송신 시각은 KST `14:46:33.313`인데 Chat 헤더는 `14:45:34.484`다. 최종 답변을 보내기 전에 파일을 쓰면 실제 최종 송신 시각을 알 수 없으므로 이 차이는 우연한 실수가 아니라 현 방식의 예측 가능한 한계다.

## 현행 규칙과의 관계

규칙은 다음을 명확히 요구한다.

- 기존 일자 파일의 끝에만 이어 쓰고, 기존 기록의 수정·제거·덮어쓰기를 금지한다.
- 사용자 발언, AI 중간 안내, 최종 응답을 원문과 KST 밀리초 시각으로 보존한다.

이 규칙은 유실·덮어쓰기 방지에는 강하다. 그러나 다음은 정의하지 않는다.

- 파일의 물리적 append 순서와 대화 발생 시각 순서 중 무엇이 정본인지
- 긴 작업 중 어떤 간격으로 중간 안내를 영구 기록할지
- 여러 AI가 같은 파일에 동시에 기록할 때의 lock, 단일 writer, 충돌 재시도 규칙
- 최종 응답의 실제 송신 시각을 사전에 알 수 없을 때의 timestamp source·보정 방식
- 뒤늦게 수집한 원문을 append만으로 보존하면서 사용자용 시간순 보기까지 제공하는 방식

따라서 현행 규칙은 모순적이라기보다 **동시성 모델이 빠진 단일 작성자 전제의 규칙**이다. 여러 AI가 병렬로 활동하면 append는 데이터 유실을 줄여도 시간순 서술을 보장하지 않는다.

## 구조적 원인

1. 하나의 `Chat/YYYY/MM/DD.md`가 원문 보관소와 사람이 읽는 시간순 타임라인을 동시에 맡는다.
2. 각 AI의 저장 시점은 사건 발생 시점이 아니라 해당 AI의 작업 완료 또는 배치 저장 시점이다.
3. 직접 파일 append에는 전역 순번·작업 ID·원자적 단일 writer가 없다.
4. AI가 최종 답변을 전송하기 전에는 플랫폼이 부여하는 실제 완료 시각을 확정할 수 없다.

이 때문에 저장 순서, 발생 순서, 표시 순서라는 세 순서가 분리되며, 현재 파일 형식에는 이를 구분할 필드가 없다.

## 선택 가능한 보완 설계

### 권고안: 불변 이벤트 저널과 시간순 보기의 분리

`Chat`의 원본을 append 전용 이벤트 저널로 정하고, 사람이 읽는 Markdown은 그 저널에서 생성한 시간순 보기로 분리한다.

- 저널 이벤트 필드: `event_id`, `thread_id`, `agent`, `kind`, `occurred_at`, `recorded_at`, `timestamp_source`, `sequence`, `content_hash`, `content`
- `occurred_at`: 플랫폼 원문에서 확인된 실제 발생 시각. 확인할 수 없으면 추정하지 않는다.
- `recorded_at`: 파일에 실제로 기록한 시각. append 순서와 지연을 감사할 수 있다.
- `sequence`: 동일 시각의 결정적 정렬과 재현을 위한 전역 또는 writer별 순번이다.
- Markdown 타임라인: `occurred_at`, 이어서 `sequence`로 정렬한 읽기 전용 투영본이다.

원본 저널은 절대 재정렬하거나 덮어쓰지 않으므로 append 보존 목적을 지킨다. 시간순 Markdown은 재생성 가능한 표시물로 취급하므로, 나중에 다른 AI의 원문이 도착해도 원본 훼손 없이 올바른 위치에 보일 수 있다.

### 함께 필요한 운영 규칙

1. 중간 안내·사용자 발언은 가능한 즉시 이벤트로 기록한다. 긴 작업 종료까지 메모리에 모아 두지 않는다.
2. 실제 송신 시각을 플랫폼이 사후에만 제공하면, 먼저 `recorded_at`과 `timestamp_source: local-recorded`를 기록하고 다음 확인 기회에 플랫폼 원문으로 검증한 별도 보정 이벤트를 append한다. 기존 원문은 수정하지 않는다.
3. 저널에 직접 쓰는 주체는 단일 writer 서비스 또는 잠금·재시도·중복 제거를 갖춘 조정자로 제한한다. 다수 AI가 하나의 Markdown 끝을 직접 편집하지 않는다.
4. 사용자용 타임라인에는 물리적 기록 시각이 아닌 발생 시각을 기본 표시하고, 지연·보정 여부를 투명하게 표시한다.

### 최소 보완안

새 구조를 바로 도입하지 않는다면, 각 AI가 중간 안내 때마다 즉시 append하고 각 블록에 `발생 시각`과 `기록 시각`을 함께 기록할 수 있다. 다만 이 방식은 중간 저장 간격을 줄일 뿐, 동시 append 경쟁과 최종 시각 문제를 해결하지 못한다.

## Validation 1~8 검토

1. 거버넌스: 현행 append 보존 규칙을 임의로 변경하지 않았다. 보고서만 추가했다.
2. 사용자 의도: 최근 실제 역전 사례와 규칙·구조의 원인 분리를 수행했다.
3. 정적 논리: 48개 헤더의 물리 순서를 파싱해 시간 역전 1건을 재현했다.
4. 운영 영향: 본 보고서는 앱 코드·DB·배포에 영향을 주지 않는다.
5. 보안: 플랫폼 원문은 시각·원문 확인 근거로만 읽었고, 비밀값을 보고서에 복사하지 않았다.
6. 롤백: 파일 변경은 이 보고서 1건뿐이므로 삭제가 필요하면 사용자 재확인 후 가능하다.
7. 휴먼 에러: 현 구조는 사람이 파일을 시간순 대화로 오해하기 쉬우며, 권고안은 원본과 표시를 분리한다.
8. AI 메타: 규칙 변경이나 Chat 재정렬은 사용자 승인 없이 수행하지 않았다. 확인한 한계와 증거를 구분해 기록했다.

## 이번 판단의 범위

이 보고서는 진단과 설계 제안만 포함한다. `Rule.md`, 실행 노드, Chat 원문, 저장 도구는 수정하지 않았다. 보완안을 실제 규칙과 도구에 반영하려면, 저장 정본과 표시물의 분리 방식 및 동시 writer 조정 주체를 사용자께서 선택한 뒤 별도 계획과 승인이 필요하다.
