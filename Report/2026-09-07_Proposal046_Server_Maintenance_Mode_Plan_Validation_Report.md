# [수정 검증 보고서] 제안-046 서버 점검 모드 계획

작성일: 2026-09-07
범위: 서비스가 계속 실행되는 점검·DB 복원 연동 계획

## 1단계 — 거버넌스 준수성

- 근거: Staging 우선 구현, 데이터 보존, 관리자 명시 확인과 복구 절차를 포함한다.
- 긍정: 운영 서비스 중지나 배포 설정 변경 없이 설계할 수 있다.
- 위험: 실제 점검 활성화와 세션 만료는 운영 상태 변경이므로 구현 승인과 실행 승인을 구분한다.
- 결과: 조건부 통과.

## 2단계 — 사용자 의도 달성도

- 근거: 점검 설정값의 로그인 안내, 일반 사용자 차단·로그아웃, 관리자 로그인 유지, 화면 기반 DB 다운로드·교체를 모두 포함한다.
- 긍정: 관리자 화면은 복원 작업 상태를 끝까지 표시한다.
- 위험: DB 복사 순간에는 새 관리자 로그인도 DB 접근이므로 잠시 차단된다. 기존 화면은 살아 있으며 복원 직후 `RECOVERY`에서 다시 로그인할 수 있다.
- 결과: 통과.

## 3단계 — 논리적 구동 가능성

- 근거: 기존 `SessionToken` 갱신과 5초 세션 폴링을 재사용한다.
- 긍정: 중앙 게이트를 먼저 활성화하므로 세션 갱신 중에도 일반 사용자 요청이 DB로 진입하지 않는다.
- 위험: 점검 상태 파일과 세션 갱신은 단일 DB 트랜잭션이 아니다. 실패 시 안전한 방향인 점검 유지로 종료한다.
- 결과: 보완 후 통과.

## 4단계 — 운영 병합 영향

- 근거: 로그인, 모든 요청의 전처리, 전역 fetch와 세션 폴링에 영향을 준다.
- 긍정: 중앙화된 정책으로 개별 API의 점검 검사 누락을 줄인다.
- 위험: 허용 목록 오류가 로그인이나 정적 자원을 막거나 우회 경로를 만들 수 있다. 전체 라우트 목록과 대조해야 한다.
- 결과: 조건부 통과.

## 5단계 — 보안과 엣지 케이스

- 근거: Role은 DB에서 확인하고 상태 변경에는 관리자 재인증·CSRF·확인 문구를 요구한다.
- 긍정: 일반 사용자 세션의 Role 위조나 직접 API 호출을 중앙 게이트에서 차단한다.
- 위험: 점검 코멘트 XSS, 상태 파일 권한·심볼릭 링크, 일회성 토큰 재사용, 작업 상태 노출을 방어해야 한다.
- 결과: 조건부 통과.

## 6단계 — 롤백과 역방향 파급

- 근거: 점검 상태는 DB 밖에 있어 DB 교체 후에도 유지된다.
- 긍정: 복원 실패·원복 중에도 일반 사용자 접근이 자동 재개되지 않는다.
- 위험: `RESTORING` 중 앱이 비정상 종료되면 미완료 작업 저널을 확인해 `RECOVERY`로 안전하게 시작해야 한다.
- 결과: 조건부 통과.

## 7단계 — 휴먼 에러와 UX 방어

- 근거: 점검 코멘트·시간 미리보기, 활성화·해제 재확인, 복원 진행 단계를 제공한다.
- 긍정: 예상 종료 시각이 지나도 자동 해제하지 않아 복원 중 일반 접근이 재개되지 않는다.
- 위험: 성공 후 세션 만료와 재로그인 이유를 명확히 표시해야 한다.
- 결과: 통과.

## 8단계 — AI 메타 거버넌스

- 근거: 기존 계획의 `OFFLINE`·외부 정적 페이지 전제를 제거하고 사용자 요구에 맞춰 관련 문서를 동기화했다.
- 긍정: 관리자 화면 유지와 DB 동결의 차이를 명시했다.
- 위험: 없음.
- 결과: 통과.

## 종합 판단

제안-046은 Flask를 계속 실행하는 앱 점검 모드로 구현할 수 있다. [제안-013] 복원 순간에는 서비스 전체를 종료하지 않고 DB를 사용하는 요청과 접근 로그 쓰기만 잠시 동결해야 한다.
