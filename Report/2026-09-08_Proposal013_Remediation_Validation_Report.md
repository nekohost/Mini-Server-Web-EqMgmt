## 정적 검증

- Python 3.11 `compile()`로 운영 `app.py`와 제안-013 테스트 파일의 구문을 확인했다.
- `git diff --check`를 통과했다.
- 거버넌스 manifest 검증은 오류 0건, 경고 0건으로 통과했다.
- 템플릿에 URL 쿼리 토큰이 없고, 헤더 토큰·CSRF POST 백업·모든 DOM ID 참조가 존재함을 검사했다.
- 운영 `app.py`, 템플릿, 운영 가이드와 테스트에 승인된 산출물을 반영했다. 운영 DB와 Git 원격은 이 검증 단계에서 변경하지 않았다.

## Validation 1~8

### 1단계 — 거버넌스: 조건부 통과

검증된 Staging 산출물을 운영 위치로 병합했고 새 외부 라이브러리나 DB 스키마 파괴 작업은 없다. 운영 반영 뒤 중복 Staging 파일을 제거했다.

### 2단계 — 사용자 의도: 통과

관리자는 점검 중 웹 화면에서 백업을 내려받고 후보 DB를 업로드·비교·복원할 수 있다. 서비스는 살아 있고, 비교 정보와 안내는 한국어로 제공된다.

### 3단계 — 정적 논리: 통과

저널·감사 I/O 실패는 원복·복원 본체와 분리했다. 요청 종료 연결 정리, 파일 정리, 용량 사전 검사, 단일 워커 전제를 코드와 문서에 반영했다. 실제 SQLite 백업·스레드 경합 실행은 Windows 정책상 수행하지 않았다.

### 4단계 — 운영 병합 영향: 조건부 통과

라우트는 기존 경로와 충돌하지 않고 `--workers 1` systemd 전제와 일치한다. 운영 소스 병합은 완료했다. `get_db_connection()`의 전역 추적 변경은 기존 모든 DB 요청에 영향을 주므로 Linux 서버에서 전체 테스트를 실행해야 실제 서비스 반영 검증이 끝난다.

### 5단계 — 보안과 예외: 통과

관리자·CSRF 검사는 유지됐고, 백업 생성도 CSRF POST로 바뀌었다. 토큰은 URL에서 제거했으며, 사용자 응답·공개 상태·외부 저널에서 비밀번호·토큰·내부 경로·오류 원문을 제외했다. 후보 파일명은 계속 신뢰하지 않고 크기·무결성·스키마·관리자 인증을 검사한다.

### 6단계 — 롤백: 통과

자동 백업을 만들고 사후 검증 실패 시 원복·재검증한다. 상태 저널 실패를 주입한 원복 시나리오 테스트도 추가했다. 프로세스가 강제 종료되는 경우에는 7일 보관 자동 백업과 외부 저널을 이용한 수동 복구가 여전히 필요하다.

### 7단계 — 휴먼 에러와 UX: 통과

점검 모드 선행, 후보 검증 후 복원 표시, 한국어 확인 문구, 중복 클릭 방지, 비교 정보, 안전한 오류 안내를 유지했다. 백업 파일은 화면에서 직접 내려받고 서버 임시 사본은 응답 종료 후 제거한다.

### 8단계 — AI 메타: 통과

검토에서 승인받은 코드·문서·테스트만 운영 위치에 반영하고 Staging 중복물을 정리했다. 실제 DB 작업과 Linux 서비스 실행은 수행하지 않았다.
