# [수정 검증 보고서] 제안-013 웹 기반 DB 백업·복원 계획

작성일: 2026-09-07
검증 범위: Flask를 중지하지 않는 관리자 화면 기반 백업·온라인 복원 계획

## 1단계 — 거버넌스 준수성

- 근거: 운영 파일보다 Staging 구현과 모의 DB 검증을 먼저 수행한다.
- 긍정: 실제 운영 DB 접근·복원은 계획 승인과 분리되고, 복원 전 자동 백업과 원복 경로가 있다.
- 위험: 실제 복원은 파괴적 데이터 작업이므로 구현 완료 후 별도 운영 실행 승인과 정확한 대상 확인이 필요하다.
- 결과: 조건부 통과.

## 2단계 — 사용자 의도 달성도

- 근거: 백업 다운로드, 보유 DB 업로드·대체, 점검 중 관리자 화면 유지 요구를 모두 반영했다.
- 긍정: 일반 사용자만 차단하고 관리자는 백업·후보 검증까지 계속 수행할 수 있다.
- 위험: `RESTORING`의 짧은 구간에는 DB 일관성을 위해 새 관리자 로그인과 다른 관리자 DB 요청도 잠시 대기 또는 503 처리된다. 이미 열린 복원 화면은 계속 상태를 표시한다.
- 결과: 통과.

## 3단계 — 논리적 구동 가능성

- 근거: SQLite 공식 문서는 Online Backup API가 소스 DB 내용을 대상 DB로 복사·교체하고, 작업 동안 대상 DB에 쓰기 트랜잭션을 유지한다고 설명한다. Python은 이를 `Connection.backup(target)`으로 제공한다. 현재 별도 접근 로그 워커가 있으므로 대상 DB 쓰기 정지가 필요하다.
- 긍정: 서버 프로세스 중지 없이 대상 DB 연결에 복원하고 완료 직후 검증할 수 있다.
- 위험: 인플라이트 요청, 접근 로그 워커, 병렬 복원, 제한 시간 초과가 경합을 일으킬 수 있다. 요청 계수기, 중앙 게이트, 워커 정지 확인, 단일 restore lock으로 통제한다.
- 결과: 보완 후 통과.

## 4단계 — 운영 병합 영향

- 근거: `before_request`, DB 연결, 접근 로그 워커와 세션 폴링을 함께 변경해야 한다.
- 긍정: 프로세스 관리자나 프록시 변경 없이 앱 내부에서 기능을 완결할 수 있다.
- 위험: 조정기 일부만 병합하면 복원 중 쓰기가 발생할 수 있다. 점검 게이트·워커 제어·복원 API·UI를 하나의 배포 단위로 취급해야 한다.
- 결과: 조건부 통과.

## 5단계 — 보안과 엣지 케이스

- 근거: 관리자 역할, CSRF, 현재 관리자 재인증, 후보 DB 관리자 계정 검증, 일회성 승인·모니터 토큰을 요구한다.
- 긍정: 손상 파일과 관리자가 없는 백업으로 인한 잠금 위험을 적용 전에 차단한다.
- 위험: 악성 SQLite 파일, 과대 업로드, 경로 조작, 상태 API 정보 노출을 제한해야 한다. 후보는 읽기 전용으로 열고 정확한 스키마 호환성 검사를 수행한다.
- 결과: 조건부 통과.

## 6단계 — 롤백과 역방향 파급

- 근거: 적용 직전 온라인 백업, 적용 후 재검증, 실패 시 역방향 온라인 복원을 설계했다.
- 긍정: 서버를 중지하지 않고 같은 조정기 안에서 자동 원복할 수 있다.
- 위험: 자동 원복까지 실패할 수 있다. 이 경우 점검 모드를 유지하고 다운로드 백업과 외부 자동 백업을 이용한 수동 복구로 전환한다.
- 결과: 조건부 통과.

## 7단계 — 휴먼 에러와 UX 방어

- 근거: 후보 비교, 현재·후보 관리자 자격 검증, 확인 문구, 단계별 진행 상태를 제공한다.
- 긍정: 파일 선택만으로 복원이 시작되지 않으며 중복 클릭과 페이지 이탈을 방어한다.
- 위험: 복원 성공 후 현재 세션이 만료된다. 적용 전 후보 DB 관리자 계정 로그인을 검증하고 성공 화면에서 재로그인을 안내한다.
- 결과: 통과.

## 8단계 — AI 메타 거버넌스

- 근거: 사용자 요구에 따라 기존 서버 중지 계획을 폐기하고 관련 문서를 함께 수정했다.
- 긍정: 서버를 살려 두면서 필요한 DB 쓰기만 동결한다는 경계를 명시했다.
- 위험: 없음.
- 결과: 통과.

## 종합 판단

서버 프로세스를 중지하지 않는 화면 기반 백업·복원은 구현 가능하다. 완료 조건은 모든 DB 사용 경로와 접근 로그 워커가 `RESTORING` 동결을 준수하고, 적용 실패 시 자동 원복이 모의 DB와 서버 환경에서 검증되는 것이다.
