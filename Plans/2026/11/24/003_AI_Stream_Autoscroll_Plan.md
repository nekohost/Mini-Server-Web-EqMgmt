# AI 도우미 출력 자동 스크롤 사용자 우선 계획

## 1. 요청과 승인 범위

- 요청: AI 답변이 출력되는 동안 기본적으로 최신 출력까지 자동 스크롤한다. 사용자가 스크롤을 조작하면 자동 스크롤을 멈추고, 사용자가 다시 최신 출력 끝으로 돌아오면 자동 스크롤을 다시 켠다. 추론(사고) 과정 표기에도 같은 규칙을 적용한다.
- 승인: 논리 개선을 Staging까지 진행한다. 검증은 가상 답변 모델(합성 전송)과 스크린샷으로 수행한다.
- 범위 밖: 운영 소스 병합, commit·push, 서버 배포, 실제 모델 질의. strata 연결이 자체 개선 중이므로 실제 모델 호출로는 검증하지 않는다.
- 반영 대상 서버: 운영 반영을 별도로 승인받으면 `eqmgmt-backup`에만 반영한다. 사용자가 미니서버 반영은 필요 없다고 확인했다.

## 2. 원인

1. 대화 영역: `static/js/equipment_ai.js`의 `follow()`는 매 출력 프레임마다 "바닥에서 100px 이내"인지 다시 계산하고, 그 안이면 바닥으로 이동시킨다. 사용자가 100px보다 적게 올리거나, 터치·스크롤바 조작이 프레임 사이에 진행 중이면 다음 프레임이 화면을 다시 바닥으로 끌어내린다. 사용자 조작 여부를 기억하는 상태가 없다.
2. 추론 과정: `.ai-thought-text`는 최대 높이 350px의 독립 스크롤 영역인데, 추론 텍스트를 갱신할 때 내부 스크롤을 전혀 따라가지 않는다. 긴 추론에서는 최신 추론이 상자 아래에 가려진다.

## 3. 변경 설계

1. 공용 함수 `scrollFollower(element)`를 추가한다. 스크롤 영역마다 "따라가기(pinned)" 상태를 보관한다.
   - 이탈: 휠 위로, 터치로 내용을 위로 끌기, 위쪽 이동 키(ArrowUp·PageUp·Home·Shift+Space), 실제 스크롤 위치가 위로 이동한 경우.
   - 재부착: 스크롤 위치가 최신 끝에서 24px 이내에 들어온 경우.
   - 조작 중 보류: 휠·터치·스크롤바·키 조작 직후 450ms 동안은 따라가기 상태여도 강제로 이동하지 않는다. 보류가 끝나면 1회 따라잡는다.
   - 내부 스크롤 영역(추론 상자·표·코드)이 그 방향으로 더 스크롤할 수 있으면 바깥 대화 영역의 상태는 바꾸지 않는다.
   - 코드에 의한 위치 고정이나 내용 감소로 바닥에 다시 맞춰진 경우는 이탈로 보지 않는다.
2. `follow()`는 대화 영역 follower를 사용한다. 따라가기 상태이면 바닥으로, 아니면 기존처럼 사용자의 위치를 보존한다.
3. 어시스턴트 메시지마다 추론 상자 follower를 만든다. 추론 텍스트 갱신 시 같은 규칙으로 따라가거나 위치를 보존한다. 답변 시작 뒤 사용자가 접힌 추론을 다시 펼치면 다시 보기로 보고 자동 이동하지 않는다.
4. 새 질문 전송과 대화 열기는 기존처럼 바닥에서 시작하고 따라가기 상태로 둔다. 상태 동기화로 대화를 다시 그리는 경우(`preserveReader`)는 이전 위치와 따라가기 상태를 함께 복원한다.
5. 전역 리스너·새 의존성·서버 API·DB 변경은 없다.

## 5. 검증 절차

1. `Staging/20261124-ai-stream-autoscroll/`에 변경 패치를 작성하고 깨끗한 `HEAD` 임시 사본에 적용한다.
2. 임시 사본 기준으로 `eqmgmt-backup`의 Linux tmpfs와 Chromium에서 다음을 수행한다. 실제 모델 호출과 운영 DB 접근은 없다.
   - 신규 가상 답변 모델 시나리오: PC 마우스 휠과 모바일 터치 제스처로 이탈·유지·재부착을 대화 영역과 추론 상자 각각 확인하고 단계별 스크린샷을 남긴다.
   - 기존 회귀: 출력 표시(`polish-stream`), 입력 설정, 전송 hitbox, Fold7, viewport, 모델 패널, 백엔드 전체, 정적 보안 검사.
3. 수정 전 코드에서 신규 검사가 실패하는지 확인해 회귀 검출력을 확인한다.
4. 운영 소스 병합·commit·배포는 수행하지 않는다. Staging 폴더는 운영 반영 승인 전까지 보존한다.

## 6. 롤백

Staging 단계이므로 운영 소스는 변경하지 않는다. 운영 반영 후 문제가 생기면 해당 commit을 `git revert`하고 같은 배포 절차를 수행한다. 데이터·설정 변경이 없어 클라이언트 캐시나 저장소 잔여물에 의한 롤백 장애가 없다.
