## 1. 실제 표 렌더링

- 기존 렌더러의 DOM 생성 방식을 확장한다. 모델의 HTML을 그대로 삽입하지 않고 셀 내용은 text node와 현재 허용한 인라인 표현으로 처리한다. 새로운 외부 패키지는 추가하지 않는 안을 우선한다.
- 헤더와 구분 행의 열 수, 좌/중앙/우 정렬, 셀의 이스케이프된 파이프, 빈 셀과 누락 셀을 처리한다. 코드 펜스 안의 표 예시는 코드로 유지한다. [GFM 표 문법](https://github.github.io/gfm/#tables-extension-)의 지원 범위를 명시하고 전체 GFM 지원으로 과장하지 않는다.
- table을 가로 스크롤 영역으로 감싸 모바일 문서 전체가 넘치지 않게 한다. 헤더 대비·셀 경계·줄바꿈·숫자 정렬을 현재 테마 변수로 제공하고 배경 테마 규격은 유지한다.
- 스트리밍 중 아직 닫히지 않은 구분 행/셀 때문에 답변을 잃거나 줄을 합치지 않는다. 완성된 구조를 기준으로 갱신하며 재렌더링 시 사용자의 세로/가로 스크롤·선택·추론 펼침을 보존한다.
- 긴 표는 렌더 비용을 제한하되 생략을 명시하고 원문을 보존한다. 장비 조회의 기존 20개 페이지/전체 개수 정보도 안내해 일부 조회 결과를 전체 목록으로 오인하지 않게 한다.
- 저장된 메시지를 새 렌더러로 다시 표시하므로 기존 정상 Markdown 표도 개선된다. 과거 메시지 본문·실패 기록·추론을 DB에서 재작성하지 않는다.

## 2. 빈 조회 필터와 진단 기록 분리

실제 실패 인자는 다음과 같다.

```json
{"scope":"my","query":"","page":1,"status":"","due":""}
```

현재 검색 도구의 `status`는 선택 필드이지만 값이 들어오면 ACTIVE/LOANED/REPAIR/DISPOSED만 허용한다. 도메인의 검색 코드는 상태가 비어 있으면 원래 필터를 넣지 않는다. 모델 schema와 실제 조회 의미가 일치하도록 다음을 조정한다.

1. `search_equipment.status`의 빈 문자열을 '상태 필터 없음'으로 명시한다. 생략과 같은 뜻으로 canonical 조회 인자에서 제거한다. 필터를 쓰지 않을 때 생략할 수 있다는 설명도 모델 도구 schema에 넣는다.
2. HTTP finish의 선행 검사와 `Domain.read_or_prepare()`의 재검사가 같은 공통 검증/정규화 함수를 사용하게 한다. 한쪽에서 허용하고 다른 쪽에서 거부하는 상태를 만들지 않는다.
3. 이 규칙은 지정한 조회 선택 필터에만 적용한다. 알 수 없는 값, 추가 필드, 타입 혼동, 타 owner/scope, `prepare_equipment_status`의 빈 상태값은 계속 거부한다. 오류 시 후속 작업 중단 정책도 유지한다.
4. 원래 전달된 인자는 감사에서 보존하고 실행에는 정규화한 인자를 사용한다. 과거 실패 job을 성공으로 바꾸거나 같은 요청을 몰래 다시 실행하지 않는다.

부수적으로 `build_context()`의 완료 이력은 현재 job purpose를 구분하지 않아 probe의 제목/nonce가 일반 문맥에 들어간다. 새 기능시험 기록은 관리자 진단 조회로 분리하고, 일반 목록/문맥에서는 **순수 probe 기록**을 제외한다. 기존 지정 대화처럼 일반 chat이 이미 섞인 대화는 계속 열 수 있게 유지한다. 그 안의 일반 사용자 메시지와 답변을 보존하고 모델 문맥에서 probe 행만 제외한다. 진단 기록의 열람은 관리자 권한과 기존 owner/account 검사를 유지하며, 순수 진단 기록에서 대화하려는 경우 새 대화를 안내한다. 단순 제목 문자열로 대화를 숨기거나 삭제하지 않는다.

## 3. 짧은 모델 선택 이름

- 기본 형식: `연결 이름 / 모델 표시 이름`.
- 양자화까지 표시하는 예: `260Strata / Qwen3.8 Flash Next · IQ3_XXS`.
- 현재 관리자 화면의 연결 이름/모델 표시 이름 필드를 그대로 사용한다. 양자화 자동 표시는 서버가 확인할 수 있는 정보가 있을 때만 제한적으로 사용하고, 관리자가 표시 이름에 이미 썼다면 중복하지 않는다. 이름을 얻기 위해 전체 호출 ID·파일 경로·주소를 사용자 브라우저에 공개하지 않는다.
- 장비 업무 가능/대화 전용/사용 불가 사유는 이미 있는 별도 상태 영역에 둔다. 드롭다운 옵션 문자열에서 기능 설명을 제거해도 비활성화와 접근성 설명은 유지한다.
- 표시 문자열 변경은 opaque 선택 ID·모델 호출 ID·물리 그룹·진행 요청의 snapshot에 영향을 주지 않는다. 과거 답변에 저장된 당시의 출처를 현재 이름으로 덮어쓰지 않는다.

## 4. 관리자 센터로 메뉴 이동

`equipment_ai_settings`의 URL은 `/admin/ai/providers`로 유지한다. 신규 설치 seed의 ParentMenuCode를 `admin_center`로 바꾸고 기존 행에는 정확한 메뉴 코드/URL/예상 부모를 검증한 뒤 같은 부모로 옮기는 metadata 이전을 한다. INSERT OR IGNORE 수정만으로 기존 운영 행이 고쳐질 것으로 기대하지 않는다.

이전은 짧은 transaction으로 처리하고 동일 명령 반복 시 변경이 없는지 확인한다. 기존 메뉴명/순서/다른 메뉴/권한 설정과 업무 데이터는 보존한다. 관리자 센터 API·메인 목록·상위 메뉴/뒤로 가기 동선을 함께 검증한다. 사용자 AI 도우미 메뉴는 메인에 유지한다. 서버의 현재 관리자/메뉴 권한 검사는 그대로 유지한다.

## 5. 연결 관리의 처리 UX

공통 로딩은 `showGlobalLoading()`/`hideGlobalLoading()`을 재사용할 수 있다. 공통 성공/실패 dialog는 현재 확인되지 않아, 이 화면에서 쓸 재사용 가능한 native dialog 기반 컴포넌트를 새로 만든다. 다른 기능의 기존 alert/confirm을 이번 작업에서 일괄 교체하지 않는다.

| 조작 | 시작/처리 | 결과 |
| --- | --- | --- |
| 연결 추가·수정 저장 | 입력 검사 → 저장 중 overlay → 중복·편집 전환 잠금 | overlay를 닫고 저장 완료 modal. 현재 revision의 모델 시험 필요 여부도 안내 |
| 연결 폐기 | 연결 이름·신규 요청 중지/기록 보존·재활성 불가를 확인하는 modal → 폐기 중 overlay | 폐기 완료 modal. 공유 모델 프로세스는 중단하지 않음 |
| 모델 설정 저장·수동 추가 | 해당 조작의 입력/지원 단계 검사 → 처리 중 overlay | 무엇을 저장했는지와 재시험 필요 여부를 modal로 안내 |
| 자동 모델 조회·명시적 새로고침 | 조회 중 overlay·중복 요청 차단 | 완료/실패 modal. 실패해도 기존 목록을 보존 |
| 기능 시험 | 짧은 접수 구간 overlay → 접수 ACK 후 overlay 해제 | 접수와 완료를 구분. 큐/진행/단계를 화면에 유지하고 최종 성공/실패/취소/종료 확인 필요를 각각 modal로 알림 |

- 완료 modal은 스크롤 위치와 관계없이 보이고 키보드/스크린리더로 인식할 수 있어야 한다. 처리 중 입력·연결 전환을 막고 `aria-busy`/focus 복구를 제공한다. 다시 렌더된 버튼에도 올바르게 복귀한다.
- API 저장 성공과 후속 목록 재조회 실패를 분리한다. 저장 ACK를 받은 뒤 GET이 실패했다면 '저장 완료, 목록 갱신 실패'로 표시하고 POST를 자동 재전송하지 않는다.
- 네트워크 단절/timeout으로 저장 결과를 모르면 실패 확정이나 성공으로 단정하지 않는다. '결과 확인 필요'를 표시하고 기존 ID/revision/폐기 상태를 GET으로 확인한다. 신규 생성의 결과를 확인하지 못하면 자동 재생성하지 않는다. 추가 서버 멱등 키가 필요한 범위는 Staging 설계에서 명시한다.
- 409 경합과 입력 오류는 입력을 보존하고 재확인 경로를 준다. API 키를 modal/로그에 노출하지 않고 성공/페이지 이탈 시 입력을 비운다.
- 상태 조회 실패는 시험 자체의 실패로 단정하지 않는다. 저장한 job ID로 조회를 재개하며 새 시험을 자동 접수하지 않는다. `done`만 시험 성공으로 표시한다.
- 오래 걸리는 정상 모델 생성에는 총시간 기준의 취소를 넣지 않는다. modal을 닫거나 페이지를 떠나는 행위도 공유 Strata의 취소/초기화로 연결하지 않는다.

## 6. 기존 Strata 시험 화면 폐기

폐기 대상과 보존 대상을 경로/역할로 구분한다.

| 폐기·회수 대상 | 보존 대상 |
| --- | --- |
| 장비관리 `/ai`, `/ai/console`, 기존 Strata 메뉴/iframe | `/assistant`, 관리자 연결 화면, 기존 사용자 AI 대화/초안/실행 영수증/감사 |
| `templates/strata*.html`, `strata_page.js`, `strata_bridge.js`, 전용 CSS/vendor 화면 자산 | `utils/ai_assistant`의 Strata adapter, Chat Completions 연결, 모델 목록 조회, 내부 worker/그룹 큐 |
| `/strata/*` browser proxy·옛 health/auth API와 Nginx 내부 auth location | LAN의 Strata 서비스와 다른 서비스의 요청 |
| `STRATA_ENABLED` 등 옛 UI 전용 설정·설치 코드/검사 | `USER_AI_STRATA_URL/KEY`·독립 암호화 키·worker token·allowlist·epoch |

순서:

1. 새 AI의 표/조회/관리 UX 검증과 실제 연결 상태를 먼저 확인한다. 옛 화면에서 진행 중인 요청이 있는지 확인하고 정상 종료 후 전환한다. 실행이 길다는 이유로 공유 모델을 취소하지 않는다.
2. 기존 UI 설정을 비활성화하고 메뉴를 회수한다. 정확한 `strata` 메뉴/권한 행은 사본으로 보존하며, 필요 시 명시적인 숨김 필터를 유지한다. 관리자 메인 조회가 grant를 우회하므로 grant 변경만으로 숨김이 끝났다고 판단하지 않는다.
3. `/ai`·`/ai/console`은 인증 후 폐기 안내와 `/assistant` 링크를 제공하는 경로로 바꾼다. 옛 API/proxy는 명시적으로 404/410을 반환해 upstream에 도달하지 않게 한다. 이전 POST를 새 대화 POST로 자동 변환하지 않는다.
4. Nginx `/strata/`·내부 auth 연결을 회수하고 설정 검사 후 reload한다. 앱/다른 사이트의 공통 proxy 설정은 건드리지 않는다. 옛 static vendor 자산도 공개 경로에서 회수하며 Git/검토 아카이브와 라이선스 근거는 보존한다.
5. 옛 화면 설치/양성 테스트를 폐기 계약/차단 테스트로 갱신한다. 메뉴 seed·필터·root import 등 잔여 참조를 확인한 뒤 명확한 whitelist 경로만 제거한다. 현재 메뉴/권한 행의 최종 삭제는 참조/FK·복구 확인 후 해당 행만 대상으로 하며 AI·업무·감사 기록은 지우지 않는다.
6. 보호 키 의존성을 정리한 뒤 옛 설정/배포 보조 도구를 정리한다. **현재 `deploy_user_ai.py.prepare-key`가 옛 Nginx key 파일을 읽으므로 그 의존성을 먼저 끊어야 한다.** 새 AI의 기존 private 환경 또는 운영자가 제공한 권한 제한 키 입력을 사용하는 경로로 바꾸어 검증한다. 옛 root 키 파일을 UI 자산처럼 함께 지우거나 실제 API 키를 임의 회전하지 않는다.

옛 브라우저 대화는 `eqmgmt.strata.*` localStorage에 있었고 새 AI SQLite와 별개다. 필요 시 기존 내보내기 경로를 확인하되 자동 삭제/자동 병합은 하지 않는다. 이미 유실된 브라우저 기록을 복구했다고 주장하지 않는다.

## 7. 대화 휴지통과 영구삭제

현재 대화는 업무 DB와 분리된 `instance/ai/assistant.sqlite3`에 저장된다. 확인한 읽기 전용 백업의 `ai_meta.version`은 3이며, `conversations`에는 삭제 상태나 삭제 시각이 없다. 기존 구조를 확장하고 기존 대화는 모두 정상 목록에 남기는 추가 migration을 계획한다. 사용자가 예시로 제시한 DeleteYN의 역할은 기존 snake_case 규칙에 맞춘 `is_deleted`로 구현한다.

### 사용자 동작과 시간 기준

| 동작 | 화면/서버 처리 | 복구·보관 기준 |
| --- | --- | --- |
| 정상 목록에서 삭제 | 대상 제목·30일 보관을 확인한 뒤 휴지통으로 이동하고 정상 목록에서 숨김 | 서버가 이동한 시각부터 정확히 30×24시간 보관 |
| 휴지통 열기 | 본인 대화만 페이지 단위로 표시. 제목·이동일·자동 삭제 예정일·남은 기간과 읽기 전용 내용 확인 제공 | 새 질문·모델 변경·업무 실행 확인은 비활성화 |
| 복구 | 같은 대화 ID·제목·메시지/추론·모델 선택 이력을 정상 목록으로 복귀 | 이전 삭제 예정일 해제. 취소된 요청/미확정 업무는 다시 실행하지 않음 |
| 복구 후 다시 삭제 | 새 이동 시각과 삭제 예정 시각으로 갱신 | **다시 넣은 시각부터 새로 30일** |
| 30일 경과 | 서버 정리 작업이 대화 및 종속 대화 데이터를 영구삭제 | 만료 시점부터 복구/일반 열람 불가. 서버 중단 중 만료되면 다음 기동 시 정리 |
| 휴지통에서 영구삭제 | 대상 제목과 복구 불가를 명시한 별도 확인 modal 후 서버 삭제 | 30일을 기다리지 않으며 완료 ACK 후 앱 휴지통에서도 복구 불가 |

예를 들어 11월 5일 10:00 KST에 이동하면 12월 5일 10:00 KST가 만료다. 11월 8일 복구하고 11월 12일 15:00 KST에 다시 이동했다면 새 만료는 12월 12일 15:00 KST다. 단순 목록 조회·동일 삭제 요청의 재전송·이미 휴지통인 항목의 재조작으로 기산일을 연장하지 않는다.

### 데이터·API 계약

- `conversations`에 `is_deleted INTEGER NOT NULL DEFAULT 0`, `deleted_at REAL NULL`, `purge_after REAL NULL`, `lifecycle_revision INTEGER NOT NULL DEFAULT 0`을 추가하는 **v3→v4** migration을 계획한다. UTC epoch를 서버에서 생성하고 KST 등 사용자 표시 시간대로 렌더링한다. 정상 상태는 0/NULL/NULL, 휴지통은 1/이동시각/이동시각+2,592,000초로 일치시킨다.
- 정상 목록/대화 접근용 owner·account·상태 인덱스와 휴지통 목록/만료 정리용 시각 인덱스를 둔다. 목록 필터·페이지 cursor에 상태를 반영하고 정상 목록 cursor를 휴지통에 재사용하지 않는다. 현재 사용자별 200개 대화와 문자 보관 예산은 정상+휴지통 합계로 유지한다. 휴지통 이동만으로 공간이 반환된다고 안내하지 않는다.
- 서버 인증에서 얻은 **owner와 account_key**로 소유권을 검사한다. 관리자 로그인이나 숫자 UserId 재사용만으로 다른 계정의 대화에 접근할 수 없게 한다. 브라우저가 보낸 owner·삭제 시각·만료일·삭제 flag를 권한 또는 시계로 신뢰하지 않는다.
- 정상/휴지통 목록, 휴지통 이동, 복구, 휴지통 안의 영구삭제를 구분한 API를 `/assistant`의 기존 인증/CSRF·Origin 경계 안에 둔다. 영구삭제는 정상 항목에 바로 적용하지 않는다. 이 기능을 모델의 업무 tool 목록에 추가하지 않으며 기존 장비 삭제 금지는 유지한다.
- 변경 요청에는 현재 `lifecycle_revision`과 조작 식별자를 사용한다. 짧은 `BEGIN IMMEDIATE` 안에서 상태/소유자/revision/현재 서버 시각을 재검사한다. 같은 조작은 멱등 처리하고, 복구 후 도착한 이전 삭제 요청이나 이전에 스캔한 GC 후보는 409 또는 조건 불일치로 종료한다. 영구삭제 재시도는 삭제 감사 식별자로 확인하며 내용·제목을 별도 재보관하지 않는다.
- 복구는 `now < purge_after`인 항목만 허용한다. 만료일을 넘겼으나 정리 작업이 아직 실행되지 않은 항목을 복구해 보관 기간을 우회하지 못하게 한다. 복구와 정리가 경합하면 먼저 확정된 transaction의 상태를 기준으로 한쪽만 성공한다.

### 실행 중 요청·업무 확정과의 관계

휴지통 이동 시 그 대화의 queued 요청과 미확정 proposal은 취소하고, 실행 중인 **자기 요청**은 후속 도구/쓰기/출력 저장을 중단하는 draining으로 전환한다. 이미 확정된 장비 등록·수정이나 그 영수증은 되돌리지 않는다. 업무 확정과 휴지통 이동은 서버의 동일한 작업 진입 게이트를 사용해 이동 후 새 확정을 막고, 이미 진입한 확정의 결과는 기존 업무 감사에서 확인한다. 복구는 대화 열람/후속 새 질문만 가능하게 하며 취소 상태를 초기화하거나 이전 업무를 자동 재실행하지 않는다.

현재 그룹 점유는 `jobs`의 running/draining/recovery_required 부분 unique index에 묶여 있다. 따라서 실행 job을 단순 DELETE하면 아직 upstream에서 실행 중인데도 다음 요청이 시작될 수 있다. **영구삭제를 제공하기 전에 실행 점유와 대화 본문을 분리한다.** 모든 그룹 점유를 대화 FK에 의존하지 않는 단일 실행 제어 원장(예: `ai_execution_guards`)으로 이전하고 job ID·그룹 ID·worker lease/epoch·취소/종료 상태·시각 등 최소 제어값만 남긴다. 대화/프롬프트/응답/추론/도구 인자/인증 키는 이 원장에 넣지 않는다.

이 방식으로 직접 영구삭제와 30일 만료 시 대화 본문을 제거하면서도 미종료 요청의 그룹 점유는 보존한다. 늦은 chunk/finish는 원장에 따라 버리거나 종료 상태만 갱신하고 삭제한 대화를 재생성하지 않는다. 종료 불명확은 recovery_required로 남겨 확인 절차를 유지하며 오래됐다는 이유로 점유를 풀지 않는다. 점유 원장의 이전·단일 점유 검증이 완료되기 전에는 영구삭제 API/정리 timer를 활성화하지 않는다. 다른 서비스의 Strata 요청 취소·모델 unload·전역 큐 제어로 해결하지 않는다.

### 영구삭제 범위와 정리 작업

| 데이터 | 휴지통 이동/복구 | 영구삭제 |
| --- | --- | --- |
| 대화 제목·메시지·추론·message_steps·jobs의 문맥/snapshot·proposals·ai_task_drafts·ai_selection_events | 보관하되 새 실행 차단. 복구 시 과거 기록으로 열람 | 해당 대화의 종속 행을 FK 순서대로 같은 transaction에서 삭제. FK가 없는 선택 이력/messages.job도 명시적으로 점검 |
| storage_accounts 및 요청 예약량 | 휴지통도 사용량에 포함, 취소 후 출력 예약은 기존 종료 규칙과 정합 유지 | 본문+handoff+draft의 실제 차감량을 계산해 정확히 한 번 반영. 계정 전체 원장은 지우지 않음 |
| 미종료 실행의 최소 점유 원장 | 자기 요청의 새 업무/기록 생성을 차단하며 종료 확인 유지 | 대화 내용 없이 점유만 유지하고 실제 종료가 확인되면 해제 |
| 장비·카테고리/제조사 요청 등 이미 확정된 업무와 업무 파일 | 기존 상태/업무 정책 유지 | 대화 삭제로 업무를 삭제하거나 취소하지 않음 |
| 기존 access/audit 로그·AI_EXECUTE 영수증·보호 CSV 감사 원본/ai_audit_artifacts | 기존 감사 정책 유지 | 앞선 사용자 감사 보존 지시에 따라 별도 보존. 대화와 함께 연쇄삭제하지 않음 |
| 프로바이더·모델·키·resource group·세션 폐기 목록(revocations) | 기존 설정/보안 정책 유지 | 공유 설정/보안 기록을 삭제하지 않음 |
| 운영 백업 | 기존 백업 정책 유지 | 백업 전체/감사까지 즉시 소거된다고 표현하지 않음. 복구 시 삭제 이력을 대조해 만료/영구삭제한 대화를 서비스에 되살리지 않음 |

현재 참조는 ON DELETE CASCADE가 아니므로 의존 행 목록을 migration과 함께 명시한다. 문자 원장 차감·종속 삭제·내용 없는 삭제 감사 기록은 같은 AI transaction에서 처리하고, 도중 실패는 전체 rollback한다. 감사 원본/업무 DB를 삭제하는 작업은 포함하지 않는다. '영구삭제'는 **앱의 대화 저장소에서 복구 불가능하게 제거**하는 뜻으로 UI에 설명한다. 기존 별도 감사/백업은 계속 남을 수 있으며 디스크의 모든 물리 복제본을 즉시 secure erase했다고 주장하지 않는다.

정리는 모델 호출이나 사용자의 로그인에 의존하지 않는 별도 서버 user systemd service/timer로 구성한다. **5분 주기와 서버 기동 시 따라잡기**, 만료 인덱스·작은 배치·짧은 transaction·단일 정리 실행을 사용한다. 30일 만료와 실제 정리 사이에는 소량의 정상 배치에서 한 주기 정도의 지연이 생긴다. 대량 만료 backlog·오류·서버 중단은 제한된 배치로 차례대로 따라잡아 더 늦어질 수 있으나 열람·복구는 만료 정각부터 차단한다. 오류/디스크 부족/잠금 경합은 건수·원인·재시도 상태를 남기고 다음 실행에서 재검사하며 완료로 오표시하지 않는다. 주기 정리를 위해 정상 모델 요청에 전역 시간제한을 추가하지 않는다.

### 화면·이전·수용 기준

정상 목록의 각 대화 메뉴에 '휴지통으로 이동', 별도 '휴지통' 진입점에 '복구'와 '영구삭제'를 둔다. 처리 중 중복 클릭 차단·짧은 로딩·완료/오류 modal은 5번 공통 UX를 따른다. 대상 대화 제목과 실제 삭제 예정일을 현재 스크롤 위치에서도 확인할 수 있게 한다. 내용은 기존 안전한 renderer로 읽기 전용 표시하고, 저장 실패/결과 불명확을 성공으로 꾸미지 않는다. 여러 탭·재접속에서는 서버 상태를 다시 읽어 정상 목록/휴지통/선택 대화를 일치시킨다.

이전 전 일관 백업과 schema/종속 행/원장 합계를 확인한다. 기존 행은 모두 정상 상태로 추가 migration하고, **Store 기동 검사·providers.migrate의 version=3 갱신·worker·점유 index·API·UI·timer를 함께 갱신**해 부분 배포를 막는다. migration은 반복 실행 가능하게 하며 새 DB와 기존 v3 사본을 모두 검증한다. 복귀는 timer 중지 후 v4/휴지통 상태를 이해하는 호환 코드로 수행한다. 옛 v3 코드를 그대로 띄워 휴지통을 노출하거나 컬럼 삭제/과거 DB 덮어쓰기로 복구하지 않는다. 영구삭제는 기능 rollback으로 복구할 수 있는 작업이라고 안내하지 않는다.
