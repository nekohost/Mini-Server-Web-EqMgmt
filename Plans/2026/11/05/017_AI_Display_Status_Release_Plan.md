# AI 내부 식별자 표시·입력칸 위 상태 안내 및 운영 반영

사용자가 기존016 Staging에 아래2건을 가산 병합하고 정적/스크린샷 검사에서 발견한 문제를 수정한 후 **운영 서버 반영까지 별도 승인 없이 진행**하도록 명시 승인했다. 이 승인은 기존1~10과 추가11~12의 검증된 누적 후보를 포함한다.016 검증 원문 ZIP/결과는 수정하지 않는다.

| 추가 번호 | 요구 | 구현 기준 |
|---|---|---|
| 11 | 일반 장비 목록/답변에 내부 ID 불필요 노출 방지 | SYSTEM·읽기 도구 설명/결과의 표시 정책에서 사용자 표시 필드와 내부 참조를 구분한다. 장비/옵션/사용자/파일/요청/메시지 ID와 revision은 후속 도구 연계에만 사용한다. 기본 답변·표에는 명칭/모델/상태·사용자가 등록한 시리얼/자산번호 같은 업무 값을 사용한다. |
| 12 | 입력칸 바로 위 노랑/빨강 상태 안내 | 상단 별과 동일한 상태 수신/TTL/현재 요청 우선순위를 사용한다. yellow는 `다른 세션/사용자의 요청 처리 중`, red는 응답 불가 안내와 확인된 사유를 동일한 색 아이콘과 함께 표시한다. |

## ID 표시와 업무 호환

현재 search_equipment/get_equipment 등의 원본에는 도구 연계에 필요한 EquipmentId/id·option_id·Revision 등이 있다. 내부 ID를 무작정 제거하면 수정·상세 조회가 깨지므로 원본 업무 계약은 유지하고 **표시 allowlist/내부 참조 field 메타와 명시적인 답변 규칙**을 추가한다. 같은 값을 raw/display 두 벌로 복제해16,000자 도구 결과 예산을 낭비하지 않는다.

일반 숫자 정규식 마스킹은 사용하지 않는다. 시리얼·모델명·수량·날짜는 정상 표시하고, 장비를 구분해야 하면 이름/모델/사용자 식별값으로 확인한다. 사용자 데이터 안의 지시문은 표시 정책을 바꾸지 못한다. 이전 답변이나 모델 전환 handoff에 내부 참조가 있어도 일반 출력에서는 재노출하지 않는 규칙을 유지한다. 기존 링크의 내부 참조·감사 원문·서버 권한 검사·정답 평가·저장된 과거 대화는 변경하지 않는다. 이는 AI의 출력 지침 강화이며 모든 모델의 임의 자연어를100% 강제 차단했다고 주장하지 않는다.

## 상태 안내

ai-bottom에서 form/textarea 바로 위에 compact한 role=status/aria-live 영역을 둔다. 상단 별과 같은 render 경로에서 색/문구/scope를 갱신하여 상태가 어긋나지 않게 한다. 새로운 poll/probe를 추가하지 않는다. 정상·확인 중·오래된 정보·context 전환·HTTP 오류·TTL 만료에서는 과거 노랑/빨강을 지우고 기존 오류 notice는 독립 유지한다. 반복된 동일 상태를2.5초마다 다시 발표하지 않는다.

`서버 다운`은 실제 원인이 확인된 경우에만 사용하고 일반 연결 실패는 `AI 서버의 응답을 받지 못하고 있습니다.`로 안내한다. 타 사용자 신원/프롬프트나 endpoint/key를 노출하지 않는다. 라이트/다크·작은 폭/낮은 높이·확대 글자·모델 panel 펼침에서 겹침/잘림과 viewport 조건을 검증한다.

## 검증·운영 순서

1.016 후보/baseline/ZIP 무결성을 확인하고017 새 결과와 분리한다. 두 변경은 독립 담당으로 병렬 구현하며 부모가 배포를 단독 수행한다.
2. Python AST/JS 구문·도구 결과/업무 참조/프롬프트·상태 전이/TTL/XSS·기존 회귀와 새 화면을 Linux 합성 fixture에서 검증한다. 결함은 Windows Staging에서 수정하고 영향 검사를 반복한다.
3. 검증된 후보·목록/해시/보고를 보존한 뒤 Windows root에 정확히 병합하고 다시 정적 확인한다. 후보 임시 파일만 정리하고 기존 사용자 dirty 변경은 보존한다. 승인 범위의 commit/push를 작성한다.
4. 서버의 owned web/worker와 큐/점검 상태를 읽는다. 진행 중 정상 모델 요청은 끊지 않고 완료를 기다린다. 실제 DB·환경/소스/서비스 원문은 private backup에 보존하고 사본 기동/기존 행 보존을 검증한다.
5. 같은 Git commit을 pull/검증하고 idle 상태에서 해당 웹·worker만 전환한다. proxy/키/다른 서비스는 변경하지 않는다. 실패하면 검증된 백업과 이전 commit으로 복귀하며 서버에서 즉석 소스 수정을 하지 않는다.
6. 운영 API·실제 브라우저/스크린샷·선택/대화/메뉴·데이터 보존을 확인한다. 제안/로드맵은 완료 이력으로 남기고 미구현 목록에서 완료 항목을 제거한다. 실제 기능 명세는 FEATURES에 반영한다.

### 사전 배포 감사에서 확인한 안전 보강

기존 helper의 유휴 판정은 jobs가 삭제된 뒤에도 남는 running/draining/recovery_required 실행 guard를 함께 확인하도록 보강한다. 기존 두 확인 지점(점검 진입 전·접수 차단 후)이 같은 읽기 snapshot에서 작업과 orphan guard를 검사하며, 진행 요청이 있으면 정상 완료까지 기다린다. 이 수정과 합성 회귀도 Staging 후보에 포함한다.

retention timer의 원래 enabled/active 상태를 private 기록에 보존하고 전환 동안 timer만 일시 정지한다. 이미 실행 중인 cleanup은 종료시키지 않고 정상 완료를 기다린 뒤 DB snapshot과 전환을 진행한다. 최종 commit pull 이후 새 프로세스에서 실제 DB 사본 검사를 실행하고 그 HEAD/결과를 대조한다. 기동 오류가 나면 접수를 다시 차단하고 기존 코드/환경을 복원하되 최신 DB·삭제 원장은 덮지 않는다.

실행 중 장애나 인증상 필요한 정보가 생기면 사실과 필요한 조치만 알리며, 이미 받은 운영 반영 승인을 다시 묻지 않는다.
