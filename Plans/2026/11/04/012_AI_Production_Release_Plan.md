# AI 도우미 운영 반영 계획

대상은 011 원장의 최종 Staging 후보와 현재 장비관리 운영 primary인 백업 Linux 서버다. Windows 앱은 실행하지 않고 승인된 파일을 루트에 구조화 병합한다. 기존 tracked dirty 9개와 무관한 untracked 자료를 섞어 commit하지 않는다. Git 경유 push/pull·정확한 commit 확인 후 서버에 적용한다.

서버/로컬에 기존 업무 DB의 일관된 SQLite 온라인 백업을 먼저 보존하고 비밀 설정·AI DB/감사 자료가 있으면 권한 제한 백업에 포함한다. 운영 DB의 본문·스키마 확인은 로컬 백업 수신 후 수행한다. 실제 데이터 사본에서 app import/AI v3 초기화와 기존 업무 행 지문 보존을 검증한다. 신형 AI DB는 별도 경로이며 업무 DB에는 AI 메뉴/권한의 멱등 등록만 추가하는 것이 기본이다. 기록 삭제나 기존 owner/역할 변경은 하지 않는다.

환경 설정은 현재 Flask SECRET_KEY를 유지하고 독립 worker token·Fernet key·DB epoch를 권한 제한 파일에 준비한다. 기존 Strata 주소/키를 같은 운영 서비스 연결에만 사용하고 키를 명령 인수·Git·보고서에 노출하지 않는다. 현재 key include는 root 전용이고 sudo 인증이 없으므로 배포 도구/백업/Git/사본 검증까지 준비한 뒤 현재 PC의 인증 창에서 사용자 직접 입력이 필요한 최소 단계만 요청한다. 기존 Nginx 키 보호 권한을 풀지 않는다.

현재 앱은 systemd unit이 아니라 사용자 소유 Python 프로세스로 가동 중이다. PID/cwd/HEAD를 재확인하고 정상 종료·복귀 가능한 기존 구동 방식을 유지한다. 자체 AI worker만 별도 사용자 unit 또는 검증된 독립 프로세스로 관리한다. 공유 Strata 모델/다른 서비스의 프로세스·큐·load/unload·설정은 건드리지 않는다. 독립 키와 암호화 의존성을 준비한 뒤 신규 AI 기능을 활성화한다.

검증은 익명/일반 사용자/관리자 HTTP 경계, 모델 목록·표준 추론 비활성 상태·프로바이더 설정, 실제 짧은 모델 응답과 읽기 도구, 대화 재접속/모델 출처/중단 사유를 포함한다. 업무 변경은 사용자가 검토할 제안까지로 제한하며 실제 장비 등록·수정·삭제·승인을 테스트로 확정하지 않는다. 관리자 로그인은 사용자가 기존 계정으로 직접 완료했다. 별도 일반 사용자 검증이 필요하면 기존 권한과 개인정보를 보존하는 제한된 테스트 경로를 선택한다.

운영 브라우저 desktop/mobile·light/dark 캡처와 실제 API/모델 결과를 012 증거 원장에 남긴다. 합성 112/93 통과와 실제 운영 검증을 구분한다. 서비스 실패 시 신규 AI 접수를 닫고 이전 코드/보호 설정 및 필요 시 일관된 DB 백업 쌍으로 복귀한다. 업무·감사 기록을 되감아 테스트 흔적을 숨기지 않는다. 이번 후보의 임시 Staging 정리는 검증 재현 원본을 아카이브로 보존한 뒤 대상만 식별하여 수행하고 무관한 Staging 폴더는 건드리지 않는다.
