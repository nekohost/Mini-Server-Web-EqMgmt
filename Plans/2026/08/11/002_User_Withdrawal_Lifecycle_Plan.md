# [계획서] [제안-025] 회원탈퇴 고도화 및 [제안-021] 관리자 계정 제어 연동 개정 계획

## 개요
본 계획서는 **[제안-025] 회원탈퇴 및 철회(Soft Delete / 30일 유예 / 1년후 영구파기 / 재가입시 복구)** 상세 요구사항을 정의하고, 이에 맞춰 이미 구현된 **[제안-021] 관리자 전용 사용자 계정 제어(완전삭제 + 비활성화/활성화 토글 + 다중 선택)**를 연동 개정하는 아키텍처 및 구현 방안입니다.

## 1. [제안-025] 회원탈퇴 4단계 라이프사이클 설계
### Phase 1 (탈퇴 신청 ~ 30일 유예 기간)
- 사용자가 탈퇴 신청 시 `users` 테이블의 `IsDeactivated='Y'`, `DeactivatedAt=현재시각` 설정.
- 탈퇴 즉시 다른 기기에서의 접근을 막기 위해 `[제안-018]`의 로직을 재사용하여 `SessionToken`을 강제 갱신(전체 로그아웃) 처리.
- 로그인 시 인증은 성공하나, 잔여 D-Day(30일 기준) 표기 및 비활성화 철회(계정 복구) 버튼만 표출되는 전용 안내 페이지(`/deactivated_notice`)로 강제 랜딩.

### Phase 2 (30일 경과 ~ 1년 미만)
- 탈퇴 신청 후 30일이 지나면 `IsDeleted='Y'`, `DeletedAt=탈퇴완료시각` 갱신.
- 이 상태부터는 로그인 시도시 "아이디 또는 비밀번호가 잘못되었습니다" 처리 (일반 실패).
- **상태 전이 트리거 (Lazy Evaluation)**: 백그라운드 데몬 없이 사용자가 로그인을 시도할 때나 관리자가 사용자 목록을 조회할 때 `DeactivatedAt` 시간을 계산하여 30일이 지났으면 즉시 Phase 2 상태로 자동 전환(DB 갱신).

### Phase 3 (비활성화일로부터 1년[365일]+1일 경과 시점)
- 1년 1일 경과 시 계정 데이터 DB 영구 삭제 (Hard Delete).
- 삭제 시 `[제안-021]` 완전 파기 로직 호출 (장비 `UserId = NULL, IsPublic = 1` 이관, `user_settings` 삭제, 감사 로그 적재).
- Phase 2와 동일하게 Lazy Evaluation 방식을 통해 로그인/조회 시 트리거됨.

### Phase 4 (재가입 복구 프로세스 및 보안 강화)
- 탈퇴 완료 계정(`IsDeleted='Y'`)의 LoginId로 신규 회원가입 시도시 복구 프로세스로 분기.
- **보안 검증**: 타인에 의한 계정 탈취를 막기 위해 가입 시 등록했던 '이름(Name)'을 정확히 입력하여 본인 소유권을 증명하도록 요구. 검증 성공 시 새 비밀번호로 계정 부활.

## 2. [제안-021] 관리자 기능 확장 (비활성화 연동)
- 관리자 화면에 "계정 비활성화 / 활성화" 토글 기능 및 다중 체크박스 제어 추가.
- **자진 탈퇴와의 충돌 회피**: 관리자가 '비활성화'를 누를 때는 `IsDeactivated='Y'`만 설정하고 `DeactivatedAt=NULL`로 처리. 카운트다운 로직이 작동하지 않아 관리자가 원할 때까지 무기한 정지 상태로 유지.

## 3. 구현 단계
1. **DB 스키마 마이그레이션**: `users` 테이블에 4개 상태 관리 컬럼 추가 (`migrate_users_soft_delete` 구현).
2. **상태 지연 평가 로직 구현**: `evaluate_user_lifecycle()` 유틸리티 함수 작성.
3. **API 엔드포인트 신설**: 
   - `/api/users/withdraw` (탈퇴 신청)
   - `/api/users/withdraw/cancel` (철회)
   - `/api/users/<id>/toggle_deactivation` (관리자 토글)
   - `/api/users/deactivate_selected` (관리자 일괄 처리)
4. **프론트엔드 연동**: `mypage.html`, `deactivated_notice.html`, `users_management.html` 개정.
5. **재가입 연동**: `register.html` 및 `/register` API 로직 분기.
