## 1. 목적과 현재 대상

기존 Rule·거버넌스는 모델의 한계를 보완하기 위한 강제 도구다. GPT-6 Astra에는 기존 강제 체계를 상속하지 않는 별도 실행 노드를 제공한다. 다른 모델의 기존 체계를 전체적으로 완화하거나, 기존 강제 위에 예외를 덧붙이는 방식은 사용하지 않는다.

| 구분 | 이번 구현 계획 | 현재 정책 상태 |
|---|---|---|
| Codex / GPT-6 Astra | 독립 전용 노드 1개와 선택 경로 구현 | 운영 활성 · 현재 턴의 실제 선택 확인 |
| Claude Code / Claude Fable 5.1 | 향후 적합성·접근성 검토 예시. 이번 등록·구현 제외 | 기존 경로 유지 |
| Antigravity / 가칭 Gemini 4 Pro | 향후 적합성·접근성 검토 예시. 이번 등록·구현 제외 | 기존 경로 유지 |
| 나머지 모델 또는 식별 불가 | 기존 경로 유지 | 기존 노드와 강제 절차 유지 |

Claude Fable 5.1은 사용자가 알려준 구독 접근 제약 때문에 현재 도입에서 제외한다. 이 제약은 사용자 제공 운영 조건으로 기록하며, 공급자의 전체 요금제·접근 정책을 독립 검증했다는 주장은 하지 않는다. 표시명은 사용자 정정에 맞춘 것이며 실제 API·런타임 ID로 간주하지 않는다.

보류 모델에는 전용 노드, 활성·비활성 등록 항목, 추정 ID, 예약 활성화, 출시 감시를 만들지 않는다. 모델 출시·접근 가능·성능 적합·프로젝트 채택은 서로 다른 조건이다. 구독 변경이나 접근성 확보 자체도 이번 작업에 포함하지 않는다.

## 2. 이번에 보완한 설계

| 기존 설계의 문제 | 수정 방향 |
|---|---|
| Fable 포함 후 노드 2개와 CLAUDE 진입 수정이 구현 범위에 남음 | Astra 노드 1개만 계획. CLAUDE/GEMINI 진입 변경 및 해당 플랫폼 연결 구현은 현재 제외 |
| 설계가 보고서에만 있고 독립 Plan이 없으며 과거·현재 결론이 혼재 | 이 Plan을 현재 범위의 단일 기준으로 신설. Report는 최신 요약과 명확히 구분된 검토 이력으로 유지 |
| createContext 이전 분기만으로 독립성을 설명 | 실제 main은 loadGovernance와 전역 validate를 먼저 실행한다. 전용 선택을 legacy 전수 로딩·검증보다 앞에 배치 |
| 전용 경로도 매 작업 전체 legacy 검증을 받으면 절차가 재유입 | 전용 실행 검증과 전체 정책 패키지 검증을 분리. 전체 검증은 변경·활성화 때 수행하고 실행 경로는 필요한 계약만 확인 |
| 실제 모델 ID 전달 방식과 턴 전환 동작이 미확인 | 구현의 첫 확인 항목으로 지정. 입력 문자열·기본 모델 설정·과거 대화만으로 현재 모델을 확정하지 않음 |
| 등록부의 중복·잘못된 경로·선택 실패 정책이 불명확 | 정확한 매핑, 중복 차단, 경로 검증, fallback과 구성 오류 구분을 계약으로 명시 |
| 메모리 안에 이전 노드가 남는 모델 전환 문제 | 선택 이유와 정책 버전을 노출하고 턴·모델 변경 시 갱신. 실제 실행 환경의 지침 재적용 여부를 별도로 시험 |
| 전용 경로 도입 자체의 검증·복구 순서와 도입 후 일상 절차가 혼동됨 | 최초 전환 패키지의 검증과 도입 후 Staging·8단계 비적용을 구분 |

실제 근거: `.agent-governance/tooling/governance-tool.mjs`의 `main()`은 `loadGovernance()`를 먼저 호출하고, 기존 context 처리에서 `validateGovernance()`를 통과한 뒤 `createContext()`를 호출한다. `addWithParents()`와 default_load도 legacy 노드를 합산한다. 따라서 출력 결과에서만 노드를 빼는 방식은 채택하지 않는다.

## 3. 독립 실행 구조

```text
AGENTS.md
  → 현재 플랫폼·모델 식별 / 대상 등록부 조회
       ├─ 확인된 Codex + 등록된 GPT-6 Astra
       │    → Astra 전용 계약 확인 → 독립 노드
       └─ 그 외 / 모델 식별 불가 / 명시적 비활성
            → 기존 bootstrap·router·검증·노드

CLAUDE.md / GEMINI.md → 현재 기존 경로 유지
```

전용 노드 제안 경로는 `.agent-governance/profiles/gpt-6-astra.md`다. 기존 강제형 노드의 자식이 아니며 개념상 parent는 null이다. 루트 AGENTS는 유지하고 숨겨진 override 파일이나 외부 Codex 설정으로 우회하지 않는다.

전용 노드는 다음만 간결하게 담는다.

- 요청과 승인 범위를 파악하고 그 목표까지 수행한다. 검토·계획 요청을 구현으로 확대하지 않는다.
- 기존 데이터·사용자 수정·기록·비밀을 보존하고 변경을 확인·복구 가능하게 수행한다.
- 고정 Staging 복사·병합·정리, 고정 8단계, 작은 작업마다 Plan/Task/Report를 분리 생성하는 절차를 요구하지 않는다.
- 실제 변경에 필요한 정보를 조회하고 검증 방법·범위를 선택한다. 확인한 결과와 미해결 사항을 사실대로 보고한다.
- 이미 승인된 범위에서 반복 승인을 요구하지 않는다. 플랫폼 지시와 실제 도구 권한은 별도로 따른다.
- 프로젝트의 Windows 편집/정적 검사와 Linux 서비스 실행 역할은 유지한다. 소스 직접 편집 가능과 가동 서버의 무검증 즉석 수정을 혼동하지 않는다.

학습 목적의 설명과 필요한 의존성 안내는 유지하되 매 행의 형식적 주석 의무는 가져오지 않는다. 기존 주석을 일괄 삭제하는 작업은 포함하지 않는다.

기존 노드를 기술 정보로 참고해도 legacy 절차 전체를 다시 적용하지 않는다. 반대로 현재 사용자가 특정 작업에 별도 조건을 명시하면 그 조건은 존중한다. 독립성을 확보하려고 새로운 거대한 공통 강제 계층을 만들지 않는다.

## 4. 최소 선택 계약과 확장성

등록부는 실행 로직과 분리한 선언형 설정으로 둔다. 아래는 구현 시 필요한 필드의 설계이며 아직 파일·CLI 기능을 생성한 것이 아니다.

| 정보 | 용도 |
|---|---|
| schema/version | 해석할 설정 규격과 정책 버전 식별 |
| platform + exact model IDs | 정확한 대상 조합 매핑. ID가 확인된 별칭만 명시적으로 추가 |
| profile ID + node path | 선택할 독립 계약과 실제 파일 위치 |
| capability reference | 현재 플랫폼에서 사용할 도구 연결과 지원 상태 |
| enabled + adoption basis | 명시적 적용/비활성 및 채택 근거 |

최초 등록 대상은 Codex + `gpt-6-astra` 하나뿐이다. API의 정식 모델 ID와 현재 Codex 세션에서 관측되는 식별 문자열이 실제로 어떻게 대응하는지는 구현 전에 확인한다. reasoning effort나 구독 등급 자체로 다른 모델을 이 대상으로 바꾸지 않는다.

### 식별·선택·오류

1. 현재 작업에 연결된 런타임 메타데이터를 확인하고 출처와 대상 턴/작업을 연결한다. 도구가 이 정보를 제공하지 않으면 이용 가능하다고 가정하지 않는다. 현재 모델을 확인하기 위해 다른 세션의 대화 본문이나 계정 비밀을 수집하지 않는다.
2. CLI의 `--model` 같은 인수는 전달 수단일 뿐 모델 신원의 증명이 아니다. 임의의 자가 선언, 과거 세션 정보, 이름 유사성 또는 버전 비교로 전용 대상을 선택하지 않는다.
3. 모델 미확인·미등록·명시적 비활성은 기존 경로를 선택하고 이유를 알린다. 명확한 전용 대상이지만 노드가 누락·손상되면 구성 오류로 보고한다. 두 경우를 혼동하지 않는다.
4. 등록부 손상이나 중복 매핑은 임의 항목을 고르지 않고 선택을 중지한다. 노드 경로는 선언된 정책 디렉터리 내부의 확인된 파일이어야 하며 경로 탈출·순환 상속을 허용하지 않는다.
5. 결과에는 관측된 플랫폼/모델, 선택 profile·버전, 선택 이유와 확인한 노드 정보를 담는다. 세션 비밀이나 대화 본문은 넣지 않는다.
6. 모델·턴·작업 또는 정책 버전이 달라지면 해당 선택을 다시 확인한다. 다른 모델의 하위 작업자도 자신의 경로를 따른다. 프로필 캐시를 만든다면 이 조건을 키와 무효화 조건에 포함하며, 최초 구현에 캐시 도입을 강제하지 않는다.

이 구조는 프로젝트의 절차 선택기다. 모델 식별을 구현한다고 플랫폼 권한을 얻거나 도구 제한이 바뀌는 것은 아니다. 식별을 위한 별도의 과도한 인증 인프라도 만들지 않는다.

### 확장 방법

향후 다른 모델이 강제 절차 없이 이 작업을 맡기에 충분하다고 판단되고 실제 이용·도구 연결도 가능하면, 정확한 식별자를 확인한 뒤 전용 노드와 등록 항목을 추가할 수 있다. 이미 지원하는 플랫폼이면 모델별 로더 조건문을 새로 작성하지 않아도 되게 한다.

새 플랫폼은 식별·도구 연결 어댑터나 해당 진입점의 연결이 필요할 수 있다. 이는 확장 지점으로 남기되 아직 사용하지 않는 Claude·Antigravity용 전용 연결을 이번에 선행 구현하지 않는다. 충분한 지능의 판단과 자동 실행 시 모델 식별은 구분하며 런타임이 미등록 모델을 스스로 승격하지 않는다.

확장성은 격리된 fixture에 합성 플랫폼/모델과 노드를 넣어 검증한다. 실제 Claude Fable 5.1이나 가칭 Gemini 4 Pro를 시험 핑계로 운영 등록부에 넣지 않는다.

## 5. 검증 구조와 기존 모델 보존

전용 선택은 legacy 전수 load/validate보다 먼저 처리한다. 필요한 최소 등록 정보와 전용 계약을 읽고, legacy 경로가 선택됐을 때에만 기존 로딩·검증 체인을 실행한다. 기존 호출에 모델 정보가 없는 경우의 기본 동작도 유지한다.

정책 유지보수용 전체 validate는 별도로 보존하고 새 등록부와 전용 계약의 연결까지 검사하도록 확장한다. Rule·노드·등록부·map·baseline·manifest의 정합성과 의미 대조를 활성화 때 확인한다. 해시가 맞는다는 이유만으로 의미도 같다고 주장하지 않는다.

따라서 전용 일상 작업에 전체 legacy 정책 읽기를 강제하지 않으면서도, 정책 패키지의 불일치를 검증에서 감출 필요는 없다. 전용 노드가 사용하는 핵심 원칙은 직접 담고 legacy의 always_load·부모 규칙을 가져오지 않는다.

기존 Codex·Claude·Antigravity 노드의 의미와 선택 결과는 유지한다. 경로 분류 성공은 사용자 승인으로 취급하지 않으며, 실제 대상과 참고 경로도 혼동하지 않는다.

## 6. 후속 구현 범위와 순서

| 순서 | 후속 작업 | 완료 근거 |
|---|---|---|
| 1 | Codex의 실제 모델 식별 정보·턴 전환·도구 지원을 읽기 전용으로 확인 | 사용 가능한 증거 경로와 미확인 제한이 명확함. 무관한 세션·비밀 조회 없음 |
| 2 | 독립 노드 1개, 최소 등록부, AGENTS 선택 분기 및 Rule 적용 범위 후보 작성 | Astra만 등록. legacy 상속·전용 Fable/Gemini 파일 없음 |
| 3 | 로더의 선행 전역 로딩을 경로별로 분리하고 전체 유지보수 검증 확장 | Astra 경로에 legacy 전수 로딩·절차 의존이 없고 기존 경로 보존 |
| 4 | 아래 회귀·실패·확장 시험 및 Rule 의미·추적성 대조 | 시험별 기대 결과, 실제 결과, 제한 기록 |
| 5 | 승인된 범위의 일관된 정책 패키지로 활성화하고 적용 경로 확인 | 새 버전이 선택되며 이전 지침이 계속 적용되는지 실제 확인 |
| 6 | 완료 기록과 복구 방법 전달 | 계획·구현·실제 활성화 상태를 구분하여 보고 |

계획 작성 당시에는 문서 검토만 수행했다. 이후 사용자가 운영 반영까지 승인하여 위 단계를 구현·검증했고 운영 1.7.0으로 활성화했다. 최초 전환은 당시 유효한 절차로 검증했으며, 활성화 이후 Astra 일상 작업에 Staging·8단계를 다시 강제하지 않는다. 아래 설계·시험 기준의 미래형 표현은 승인 당시 계획이며 실제 완료 근거는 구현 보고서가 기준이다.

예상 변경 파일은 AGENTS, Rule의 적용 범위 조항, 전용 노드 1개·등록부, manifest/router/codex capability의 필요한 연결, 로더·관련 시험, 관련 traceability와 README다. 새 정책 조항을 정확히 매핑하여 동기화하며 기존 모든 노드를 일괄 재작성하지 않는다.

CLAUDE.md·GEMINI.md, 해당 플랫폼의 전용 어댑터, 모델 구독·설정·권한, 웹 서비스·DB는 이번 구현 범위에서 제외한다. 현재 기존 노드의 전역 등록 구조 때문에 수정이 더 필요하다면 해당 영향의 근거를 확인해 최소 범위로 반영한다. 다른 모델의 절차 의미를 조용히 바꾸는 방식은 사용하지 않는다.

대화 기록기의 검증된 저장 방식과 Git 읽기 보호 도구는 유지한다. 기록기의 신규 기능·Claude 자동 수집 지원을 이 작업에 묶지 않는다. 거버넌스의 Node 검사와 격리 fixture 시험은 Flask 애플리케이션 실행 시험과 구분하며, 이 정책 작업 때문에 Linux 서비스를 재시작할 필요는 없다. commit/push 및 외부 반영은 당시 사용자가 승인한 범위에 있을 때만 수행한다.

## 7. 구현 합격 기준

아래 항목은 후속 구현의 합격 기준이며 이번 계획 작업에서 시험 통과를 주장하는 목록이 아니다.

| 사례 | 기대 결과 |
|---|---|
| 확인된 Codex/GPT-6 Astra | 전용 계약만 적용. legacy Staging·8단계·문서 분리 노드가 자동 주입되지 않음 |
| 다른 Codex 모델 / 현재 Claude·Antigravity 호출 | 기존 선택 결과·제약 유지 |
| 모델 미확인·미등록 / 명시적 비활성 | 이유를 밝히고 기존 경로 선택 |
| Astra 식별 후 전용 노드 누락·손상 | 구성 오류. 성공으로 위장하거나 무음 fallback하지 않음 |
| 중복 매핑·등록부 손상·경로 탈출·순환 | 선택/검증 실패가 구체적이며 사용자 데이터 변경 없음 |
| legacy 일반 context 호출 | 이전 입력/출력 계약과 필수 보호 규칙 유지 |
| 전용 경로의 기술 문서 참조 | 참조만으로 legacy 체인이 재활성화되지 않음 |
| 모델·작업·정책 버전 전환 | 이전 전용 선택이 다른 모델에 남지 않음. 지침 재적용 제한이 있으면 보고 |
| 다른 모델의 하위 작업자 | 부모의 Astra 경로를 자동 상속하지 않음 |
| 지원 플랫폼의 합성 모델 등록 | 로더의 모델 조건문 수정 없이 fixture의 새 노드를 선택 |
| 합성 등록 비활성화 | 해당 항목만 기본 경로로 복귀. 실모델 등록 목록은 Astra 1개 유지 |
| 전체 정책 패키지 불일치 | 유지보수 validate에서 탐지. 오류를 무시하는 옵션으로 통과시키지 않음 |
| 활성화·복구 중단 | 부분 상태 탐지, 일관된 이전 패키지로 복구 가능 |
| 무관한 사용자 diff·비밀·DB | 변경·노출·삭제 없음 |

## 8. 복구와 남은 확인 사항

전용 항목의 의도적인 비활성화는 기존 경로로 복귀시킨다. 전환 자체에 문제가 있으면 AGENTS·Rule·등록·도구·추적성의 관련 변경을 일관된 버전으로 함께 복구한다. 저장소 전체 reset, 다른 작업자의 수정 삭제, 서비스 DB 복원은 사용하지 않는다.

정책 파일의 다중 변경은 단일 파일 쓰기와 달리 중간 상태가 생길 수 있다. 검증된 버전 식별·시작 전후 변경 감지 등으로 혼합 상태를 탐지하고, 실제 파일 교체 방식에 맞는 복구를 확보한다. 단순히 같은 commit이라고 해서 파일시스템에서 원자적으로 교체됐다고 주장하지 않는다.

구현에서 현재 작업의 진행 중 turn_context로 모델·턴·cwd를 확인했다. 운영 CLI에서 gpt-6-astra → dedicated 및 legacyLoaded:false를 실측했다. 매 턴 재선택과 격리된 턴/모델 전환 시험을 적용하되 앱 UI에서 모델을 실제 변경하는 통합 시험과 앱 지침 캐시 강제 삭제는 수행·보장하지 않는다. 미확인 런타임은 추정하지 않고 legacy를 선택한다.

OpenAI Docs 스킬에서 확인한 공식 안내는 모호하거나 충돌하는 지침의 점검과 변경 규모에 맞는 검증을 권한다. 이를 전용 경로의 비상속·검증 책임 분리와 불필요한 반복 방지에 반영했다. 구체적인 등록부와 로더 설계는 이 저장소의 코드에 근거한 설계 판단이다. [공식 모델 지침](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)
