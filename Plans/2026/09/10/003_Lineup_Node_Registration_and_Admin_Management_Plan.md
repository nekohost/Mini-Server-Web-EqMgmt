## 1. 배경과 목적

장비등록 화면은 카테고리·제조사와 기존 라인업 노드·옵션을 조회하지만, `POST /api/lineup_node`를 호출하는 UI가 없어 노드가 없는 조합에서 등록 흐름이 중단된다. 관리자 센터에도 카테고리·제조사 마스터 화면만 있고 라인업 노드의 생성·이동·이름 변경·삭제를 관리할 화면이 없다.

장비등록 과정에서 승인 정책에 맞게 루트 또는 하위 노드를 추가할 수 있게 하고, 관리자가 전체 노드 트리를 안전하게 관리할 수 있는 화면과 백엔드 후보를 Staging에 구성한다.

## 2. 현행 구조 점검 결과

- 데이터 모델은 `categories → lineup_nodes(parent_id 재귀) → equipment_options → equipments` 구조이며 새 테이블이나 컬럼은 필요하지 않다.
- 일반 조회 API는 승인된 노드만 반환한다. 관리자 화면에는 PENDING 상태와 사용량을 포함하는 별도 조회가 필요하다.
- 장비등록 UI는 노드 선택만 지원하며 빈 트리에서는 “관리자에게 문의” 안내만 출력한다.
- 노드 생성 API는 일반 사용자를 PENDING 승인 흐름으로 보내고 관리자는 즉시 APPROVED 처리하므로 이 정책을 재사용할 수 있다.
- 기존 생성 API는 부모 노드와 요청의 카테고리·제조사 일치를 검사하지 않는다.
- 기존 이동 API는 자손 노드의 `depth`를 갱신하지 않고, 대상 형제 중복과 계층 전체 최대 깊이를 충분히 검사하지 않는다.
- 기존 삭제 API는 존재하지 않는 노드에 성공을 반환할 수 있고 내부 예외 문자열을 응답에 포함한다.

## 3. Staging 구현 범위

1. 재사용 가능한 라인업 노드 서비스 후보
   - 식별자·이름 정규화 및 최대 길이 검증
   - 승인된 카테고리·제조사 존재 검증
   - 부모와 루트 조합의 일치 검증
   - 대소문자를 무시한 형제·루트 중복 방지
   - 순환 이동 방지, 자손 깊이 일괄 보정, 전체 최대 깊이 검증
   - 자식·옵션 연결 시 삭제 차단 및 명확한 404
   - 관리자용 전체 트리/상태/사용량 조회
2. 장비등록 화면용 노드 추가 모듈
   - 빈 루트와 각 선택 단계에서 루트·하위 노드 추가
   - 관리자 APPROVED 결과는 캐시 갱신 후 즉시 선택
   - 일반 사용자 PENDING 결과는 승인 대기 안내 후 정식 장비등록에 사용하지 않음
   - 중복 제출 방지, CSRF, 오류·빈 상태 처리
3. 관리자 노드 관리 화면
   - 카테고리·제조사 필터, 트리 탐색, 상태·자식·옵션·장비 사용량 표시
   - 루트/하위 추가, 이름 변경·이동, 안전 삭제
   - 모바일 단일 열과 데스크톱 분할 레이아웃
4. 운영 통합 명세
   - 관리자 메뉴/권한 migration, 페이지 route, API 연결 지점을 정확히 기록
5. 격리 검증
   - 메모리 SQLite 기반 서비스 단위 테스트
   - Python/JavaScript 구문 검사와 템플릿 정적 계약 검사

## 4. 비범위

- 운영 `app.py`, `templates/index.html`, 운영 DB 수정 및 배포
- Proposal 013 DB 백업·복원 기능의 운영 시험 또는 완료 판정
- Proposal 046 점검 모드의 재구현
- 기존 카테고리·제조사 마스터 통폐합 동작 변경

## 5. 수용 기준

- 빈 카테고리·제조사 조합에서도 새 루트 노드를 요청할 수 있다.
- 기존 노드 아래 새 하위 노드를 요청할 수 있다.
- 관리자는 새 노드를 즉시 선택할 수 있고 일반 사용자는 승인 대기 상태를 명확히 확인한다.
- 부모와 다른 카테고리·제조사로 노드를 만들거나 이동할 수 없다.
- 서브트리 이동 후 모든 자손 `depth`가 정합하며 50단계를 넘지 않는다.
- 자식이나 옵션이 연결된 노드는 삭제할 수 없다.
- 관리자 화면에서 전체 상태와 사용량을 확인하고 허용된 CRUD를 수행할 수 있다.
- 실제 운영 DB를 읽거나 쓰지 않고 격리 테스트가 통과한다.

## 6. 롤백과 다음 단계
