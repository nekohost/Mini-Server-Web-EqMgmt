## 2. 공통 계약

- 데이터: 새 필드는 equipments에 추가하고 등록·수정·목록·통계·백업·migration을 한 변경 단위로 검증한다. 기존 ID와 감사 이력을 보존한다.
- 권한: 모든 목록·첨부·CSV·AI 도구는 내 장비/공개 범위를 동일하게 적용한다. 관리 UI는 별도 서버 권한 검사를 갖는다.
- 변경: 기존 CSRF를 재사용하고 DB 쓰기·감사를 같은 트랜잭션에 묶는다. 재시도 가능한 작업은 요청 식별자로 중복을 막는다.
- 운영: Windows Staging 정적 검증 → 운영 소스 → Git → Linux 격리 DB/API → 운영 적용 순으로 진행한다. 업무 데이터 사본은 Git에 넣지 않는다.
- 복구: Up/Down 또는 검증된 파일 복구를 기능별로 제공하며, 신규 데이터가 생긴 뒤 단순 DROP으로 되돌리지 않는다.
- 접근 로그: 관리자가 선택한 본문 저장 정책은 이번 DB 개선에서 변경하지 않는다. 039는 저장 정책 변경 없이 기존 집계 동작만 검증한다.

## 3. 기능별 상세 계획

### 047 — 노드·옵션 관리

현재 utils/lineup_node_service.py와 관리자 Blueprint를 기준으로 한다. 장비 등록에서 루트/자식 생성, 승인 대기 상태, 노드 경로 표시, 옵션 재사용·삭제 참조 수를 통합 시험한다. Node/Option/Equipment ID를 보존하며 사용 중 카탈로그 삭제는 409로 차단한다. Linux 적용과 사용자 확인을 문서상의 소스 반영과 구분한다. 복구는 기능 commit revert이며 기존 카탈로그를 지우지 않는다.

### 046 — 점검 모드

사용자 정상 작동 확인을 완료 근거로 승계한다. NORMAL/DRAINING/RESTORING/RECOVERY와 DB 외부 상태 파일을 유지한다. 로그인 예외·세션 만료·503 응답·예상 종료 시각을 회귀 시험하고, 데이터 복원 진행 중 점검 해제가 불가능해야 한다. 상태 파일 손상 시 fail-closed와 이전 파일 복구 절차를 확인한다.

### 022·033 — 상태와 라이프사이클

ACTIVE 등 기존 저장값을 조사한 뒤 상태 허용 집합과 전이표를 정의한다. 정상·대여·수리·폐기 표시명과 저장 코드를 분리하며 임시 저장 여부는 별도 속성으로 유지한다. 상태 변경 API는 소유자/관리자 권한, 이전 상태 또는 updated_at을 이용한 경합 검사, 사유·시각·행위자 기록을 가진다. 기존 equipments_audit_log를 이력 원장으로 활용할 수 있는지 먼저 검증하고 부족한 구조만 추가한다.

장비 상세에 현재 상태 선택과 시간순 이력을 제공한다. api_dashboard_stats의 '정상' 하드코딩은 e.status와 표시 매핑으로 교체한다. 등록→대여→반납, 수리→정상, 잘못된 전이, 동시 변경, 장비 삭제 후 감사 보존을 시험한다. Down 시 새 상태는 숨기되 값과 이력은 보존한다.

### 023 — 상세 검색

목록 API에 category_id, manufacturer_id, status, purchase_from/to, keyword, page, per_page, sort 허용 목록을 정의한다. 조건은 AND로 조합하고 내/공개 장비의 기본 권한 조건과 분리할 수 없게 한다. 전체 모델명 검색은 노드 경로 해석과 일치해야 한다. 결과에 총건수와 페이지 정보를 제공하고 동일 정렬에는 id를 보조 키로 넣는다.

UI는 필터 초기화·빈 결과·잘못된 날짜 피드백과 URL 상태 보존을 갖는다. SQL은 바인딩하며 정렬 식별자는 허용 목록으로 제한한다. 실제 조건별 EXPLAIN과 대량 fixture로 성능을 검증한다. 기존 배열 응답 사용처를 조사해 버전/점진 전환으로 호환성을 보장한다.

### 002 — 입력 검증

가입·계정 수정·장비·마스터·노드·옵션의 검증 함수를 중앙화한다. 문자열 길이, 객체/배열/bool 구분, 정수 범위, 공백 정규화, 실제 날짜, JSON 크기를 서버에서 확정하고 UI는 같은 메시지를 안내한다. 신규 비밀번호에 채택된 8자 영문/숫자/특수문자 규칙을 적용하며 기존 해시의 로그인은 유지한다. LoginId 허용 문자·대소문자 중복 정책을 기존 사용자 값과 충돌하지 않게 정한다.

경계값과 타입 오류, 유니코드·중복 시리얼, 날짜 역전, 중복 제출을 시험한다. 배포 때 기존 데이터 일괄 수정이나 비밀번호 재설정을 수행하지 않는다. rollback은 새 검증만 제거하며 기존 데이터를 보존한다.

### 007 — 요청 속도 제한

로그인·PIN·비밀번호 재설정 등 인증 API별 정책을 분리하고 계정과 IP의 단일 조합만으로 타인의 영구 잠금을 유발하지 않게 한다. 예시 정책은 5회 실패/15분 일시 제한이지만 기존 이용량을 staging에서 확인해 설정값으로 확정한다. Retry-After와 일반 오류 응답을 제공하며 계정 존재 여부를 드러내지 않는다.

다중 worker를 고려하여 공유 저장소 기반 제한을 우선 검토한다. SQLite에 작은 만료 버킷을 두는 무의존안과 flask-limiter+외부 저장소의 설치·메모리·운영 비용을 비교한 뒤 이 소규모 서버에 적합한 방식을 선택한다. 요청마다 무제한 행을 만들지 않고 만료 정리를 제한한다. 프록시 신뢰 경계를 고정하고 서버 재시작·동시 요청·정상 사용 회복을 시험한다.

### 010 — 장비 첨부

equipment_files에 장비 ID·저장 키·원래 이름·종류·크기·해시·등록자·시각을 기록한다. 저장 키는 서버 생성값이고 실제 파일은 static 외부의 제한된 폴더에 둔다. 다운로드 때마다 장비 열람 권한을 확인한다. 초기 허용은 이미지/PDF와 제한된 용량으로 시작하고 확장자·서명·내용 유형을 교차 검증한다.

임시 업로드→검증→DB 연결→확정 순서로 부분 실패를 복구하며 장비 삭제 뒤 첨부의 보존/정리 정책을 장비 수명주기와 명시적으로 연결한다. DB-only 백업에 파일이 빠지는 문제를 별도 전체 백업 manifest로 해결해야 운영 적용할 수 있다. 경로 순회·위장 파일·부분 업로드·권한 변경·DB/파일 복원 조합을 시험한다. 후퇴 시 파일과 매핑은 보관한다.

### 017 — 감사 로그 고도화

api/audit_logs의 search_field/match_type/keyword/action_filter/start_date/end_date와 audit_log_hidden_columns 저장은 이미 존재한다. 신규 구현으로 중복 계산하지 않고 행위자+행위+기간+페이지 동시 조합, 빈 결과·잘못된 일시, 사용자별 열 선택 격리, 최대 조회 상한을 검증한다. 감사 로그 원문과 독립 이력은 변경하지 않는다. 부족한 검증만 작은 후속 작업으로 분리한다.

### 037 — WebMCP

실제 구현은 document.modelContext 기반 읽기 도구와 사용자가 직접 제출하는 신규 장비 폼이다. 미지원/비보안 환경에서 기존 UI가 유지되는 테스트를 승계한다. 안전한 조회 범위·취소·출력 제한·모델 경로를 시험하고 지원되는 보안 브라우저에서 등록을 확인한다.

초기 로드맵의 변경형 AI 도구·전면 soft-delete는 현재 승인된 제한적 구현과 다르므로 완료 범위로 주장하지 않는다. 변경형 도구 확장은 별도 상태 전이·사용자 확인·CSRF·감사 귀속 설계 후 구현한다. 현재 장비 hard-delete+독립 감사 계약을 암묵적으로 바꾸지 않는다.

### 008 — 보증·교체 기한

equipments에 warranty_end_date와 replacement_due_date를 선택 필드로 추가하고 빈 값은 미설정으로 표시한다. 일자 계산은 Asia/Seoul의 달력 날짜로 통일해 시간대 경계에서 하루가 바뀌지 않게 한다. 카드·상세·검색에서 만료/임박/정상 배지를 제공한다.

이메일 알림은 사용자 수신 동의, 검증된 주소, 일별 중복 방지 원장을 갖추고 단일 예약 작업으로 실행한다. 기존 mailer를 사용하며 설정되지 않은 서버는 UI 기한 표시만 제공한다. 만료 당일·윤년·수정/취소·재실행·메일 실패 재시도를 시험한다. rollback 시 scheduler만 중단하고 기한 데이터는 유지한다.

### 019 — 레이아웃 스킨

user_settings.layout_skin에 standard/edge 두 값만 허용하고 기본값을 standard로 둔다. 하나의 공통 기능·API를 두고 레이아웃 클래스와 제한된 template fragment만 분기한다. 페이지 이동·로그아웃/로그인·모바일 접기/펼치기 상태에서 설정이 유지되는지 확인한다.

공통 버튼·대화상자·검색·장비 선택 동작이 두 스킨에서 같아야 하며 가로 스크롤과 키보드 포커스를 검증한다. 잘못된 저장값은 기본 스킨으로 복구한다. rollback은 분기를 비활성화하고 설정값을 보존한다.

### 038 — 메타데이터

현재 register_dynamic_metadata_routes와 Resources/metadata에 security.txt, robots.txt, llms.txt, WebMCP manifest가 존재한다. 기존 연락처 정책을 유지하고 /.well-known/security.txt와 루트 경로, 잘못된 경로, 중복 route 방지, static 분류를 검증한다. 공개 문서에 비밀 파일·DB가 노출되지 않는지 확인한다. 새로운 자동 스캐너나 백그라운드 수집기는 추가하지 않는다.

### 039 — 에러 IP 분석

기존 /api/access_logs/error_ips와 access_logs_error_ips.html을 기준으로 GROUP BY 집계·4xx/5xx 분리·정렬·상세 링크 전달을 시험한다. 백그라운드 엔진을 추가하지 않고 기존 access_logs 저장 정책을 유지한다. 관리 권한 없는 접근, 로그 0건, 여러 IP·상태 조합, HTML 이스케이프, 조회 비용을 확인한다.

### 026 — CSV 일괄 입출력

첫 범위는 Python 표준 csv 기반 UTF-8 BOM CSV이며 .xlsx 바이너리 지원은 별도 확장으로 둔다. 내 장비 또는 현재 필터 결과만 export하고 셀 시작의 =,+,-,@ 등 스프레드시트 수식 주입을 방어한다. import는 미리보기에서 행 번호별 오류·중복 시리얼·노드/옵션 매핑을 보여주고 명시적 확정 뒤 원자적 적용한다.

라인업은 표시명만으로 임의 연결하지 않고 승인된 경로/옵션 ID의 조합으로 확인한다. 비관리자가 미승인 마스터를 우회 생성할 수 없다. 행 수·파일 크기·문자열 길이를 제한하고 동일 import 요청을 중복 실행하지 않는다. 일부 오류·중복 요청·동시 등록·원복 리허설을 시험한다. 운영 rollback은 import 식별자의 신규 행만 검증 후 되돌리고 변경 전 행과 감사는 보존한다.

## 4. 단계별 완료 게이트

각 새 기능은 독립 Task와 Validation 1~8 보고서, Staging 정적 검사, Linux 격리 회귀, 데이터 보존/복구 리허설을 갖춰야 한다. 위의 구현된 기능은 미구현으로 재개발하지 않고 검증 잔여만 수행한다. 구현/자동 검증/사용자 실사용/주 서버 적용은 서로 다른 상태로 기록한다.

원본 로드맵 15개 묶음 전수 대조와 교차 시나리오(상태+검색, 첨부+백업, 사용자 삭제+권한, CSV+노드 승인, AI+수동 제출)를 각각 한 번 검토했다. 주 서버 SSH 인증 미설정은 문서 계획을 막지 않지만 해당 서버 배포 완료의 근거가 될 수 없다.
