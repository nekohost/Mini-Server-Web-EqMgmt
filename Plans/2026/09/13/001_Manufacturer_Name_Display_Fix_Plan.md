# 제조사명 화면 표시 회귀 수정 계획

상태: 완료. 사용자는 화면 계층만 수정하여 Staging 검증, 운영 반영, Git 커밋·푸시와 백업 Linux 서버 배포까지 연속 수행하도록 명시 승인했고, 해당 범위가 모두 반영됐다.

## 문제와 범위

공식 모델명이 있는 장비는 목록에서 제조사명이 생략된다. API와 DB에는 제조사 데이터가 존재하므로 `app.py`, DB 스키마, 저장 데이터는 변경하지 않는다. 기존 공식 모델명 기능의 후속 회귀 수정으로 처리하며 별도 기능 제안은 만들지 않는다.

작업 대상은 다음과 같다.

- 내 장비·공개 장비·임시저장 목록의 제조사/모델 표시
- 대시보드 복합 조건 결과의 제조사/모델 표시
- 제조사 별칭 중 하나가 공식 모델명 앞에 이미 있는 경우의 중복 방지
- 공식명 미등록, 제조사 미등록, 특수문자 입력에 대한 기존 fallback과 XSS 방어 보존

## 구현 방식

1. 화면 전용 표시 함수가 제조사 한글명·영문명·기본명을 후보 별칭으로 수집한다.
2. 공식 모델명, 전체 분류 경로, 말단 모델명 순으로 표시 모델을 선택한다.
3. 선택된 모델이 제조사 별칭으로 이미 시작하면 그대로 표시하고, 그렇지 않으면 `제조사 / 모델`로 조합한다.
4. 결합 전 원문을 유지하고 최종 DOM 삽입 시 기존 escape 함수로 한 번만 이스케이프한다.
5. 대시보드 API에는 제조사명이 없으므로 사용자가 선택한 제조사 Select의 안전한 표시 문자열을 화면 함수에 전달한다.

## Staging 및 운영 절차

1. 독립 Staging 모듈과 합성 데이터 테스트를 작성한다.
2. Staging에서 누락 제조사, 한글·영문 별칭 중복, 공식명 없음, 특수문자 사례를 검증한다.
3. 적합하면 운영 템플릿과 기존 프런트엔드 회귀 테스트에 동일 로직을 병합한다.
4. 정적 구문 검사, 프런트엔드 테스트, 전체 관련 테스트, governance validate를 수행한다.
5. Staging 임시 산출물을 정리하고 Git 커밋·푸시한다.
6. 백업 Linux 서버에서 pull, 커밋 일치, 테스트, 서비스 재시작, 공개 HTTP 응답을 확인한다.

## 사전 Validation 1~8

1. 거버넌스: recorder ensure, manifest, validate와 전체 context pack 확인 완료. Staging 우선 및 구조화 편집을 사용한다.
2. 사용자 의도: 화면 표시만 수정하며 DB·API·공식 모델명 저장 규칙은 바꾸지 않는다.
3. 정적 논리: 문자열 정규화와 별칭 경계 비교만 사용하고 네트워크·DB 호출을 추가하지 않는다.
4. 운영 영향: 목록과 대시보드 표시만 변경한다. 인증, 권한, 저장 payload에는 영향이 없다.
5. 보안·예외: 최종 문자열은 기존 escape 함수로 처리하며 null·공백·특수문자를 합성 테스트한다.
6. 복구: 단일 커밋 역적용으로 복구 가능하며 DB rollback은 필요하지 않다.
7. 사용자 오류: 관리자가 공식명에 제조사를 포함하거나 생략해도 중복 또는 누락을 최소화한다.
8. AI 메타: 현재 작업자는 Codex이고 Mini-Server가 owner다. 백업 서버 실행은 이 프로젝트 배포의 종속 실행 범위다.
