# 데이터베이스 계약 및 무결성 강화 계획

- 작성일: 2026-09-12
- 상태: 1차 구현·검증·백업 서버 적용 완료 / 주 서버 적용은 SSH 인증 불가
- 기준: 운영 서버 `main@1f19fd30b626`, 운영 DB 읽기 전용 구조 감사 결과

## 1. 분리·병합 판단

이 작업은 신규 통합 계획으로 관리한다. 2026-09-11의 계획 002는 장비 삭제·옵션 관리 수명주기를, 계획 003은 독립 보존형 장비 감사 로그와 제안 013 백업 실패를 이미 해결한 완료 범위다. 이번에 남은 문제는 연결별 외래 키 강제, 마스터 삭제 계약, 스키마 버전과 호환성, 레거시 테이블, 조회 인덱스라는 공통 데이터베이스 계약에 속하므로 완료 계획을 다시 열지 않는다.

`access_logs`와 요청 본문 저장은 관리자가 운영 필요에 따라 구성한 정책으로 확인되었다. 따라서 접근 로그의 저장·보존·삭제·마스킹은 이번 계획의 변경 대상에서 명시적으로 제외한다.

## 2. 확인된 문제

1. 일반 애플리케이션 연결에서 `PRAGMA foreign_keys=ON`이 보장되지 않아 선언된 외래 키가 쓰기 시점에 강제되지 않을 수 있다.
2. 카테고리·제조사 삭제 로직은 연결된 `lineup_nodes`의 NOT NULL 컬럼을 `NULL`로 바꾸려 하므로 실제 참조 노드가 있으면 실패한다.
3. 현재 기능은 `equipments`를 사용하지만 빈 레거시 `equipment` 테이블이 필수 스키마와 하향 마이그레이션 계약에 남아 있다.
4. `PRAGMA user_version=0`인 반면 `sys_migrations`만 별도로 누적되어 정수형 스키마 계약과 호환성 기준이 없다.
5. 신규 생성 DB와 역사적으로 마이그레이션된 DB에서 `users.SessionToken`의 물리적 컬럼 순서가 다르다. 원시 CREATE SQL과 물리 순서를 엄격 비교하면 의미상 동일한 DB도 백업 호환성 검사에서 거부될 수 있다.
6. 장비 목록, 비밀번호 재설정, 승인 요청 등의 주요 조회 일부가 전체 스캔 또는 임시 정렬을 사용한다.

현재 운영 데이터는 `integrity_check=ok`, `foreign_key_check=0건`이다. 따라서 이 계획은 손상 복구가 아니라 앞으로의 쓰기·마이그레이션 안전성을 강화하는 작업이다.

## 3. 목표와 불변조건

- 모든 정상 애플리케이션 DB 연결에서 외래 키 강제를 확인한 뒤 쿼리를 수행한다.
- 독립 보존형 `equipments_audit_log`에는 장비 FK를 다시 추가하지 않는다.
- NOT NULL 참조를 `NULL`로 만드는 삭제 경로를 제거한다.
- 스키마의 의미 계약과 버전을 명시하고 신규 DB와 역사 DB를 같은 기준으로 판정한다.
- 레거시 `equipment`는 사용 중단과 복구 계약 교체를 확인하기 전에는 삭제하지 않는다.
- 인덱스는 실제 쿼리 계획과 측정 결과가 개선되는 경우에만 추가한다.
- 운영 DB에 대한 직접 수동 수정은 하지 않고, 재실행 가능한 migration과 검증 절차만 사용한다.

## 4. 단계별 구현 계획

### 단계 0. 기준선 고정

1. 운영 적용 직전에 SQLite Online Backup API로 복구 사본을 만들고 SHA-256, 파일 크기, `integrity_check`, `foreign_key_check`, 현재 migration 목록과 스키마 지문을 기록한다.
2. 운영 DB 사본을 staging 전용 경로에 두고 모든 schema migration과 데이터 검사를 먼저 수행한다.
3. 선언 FK뿐 아니라 사용자·메뉴·승인·비밀번호 재설정 등 코드 기반 논리 참조의 고아 탐지 쿼리를 기준선에 포함한다.

### 단계 1. 연결 단위 외래 키 강제

1. `open_application_database()`를 중심으로 연결 초기화를 단일화하고 정상 연결마다 `PRAGMA foreign_keys=ON`과 제한된 `busy_timeout`을 적용한다.
2. 연결 직후 `PRAGMA foreign_keys`가 `1`인지 확인하고, 활성화되지 않으면 쓰기를 시작하지 않고 오류를 기록한다.
3. migration·백업·복구 연결도 같은 초기화 함수를 사용한다. 이번 migration은 인덱스와 버전만 전진 변경하므로 외래 키 비활성화가 필요 없다.
4. 장비 삭제 후 감사 기록이 계속 남는 현재 계약을 회귀 테스트한다. 사용자 영구 삭제에서 비밀번호 재설정 토큰을 함께 정리하고, 결재 반려가 사용 중인 옵션·노드를 제거하려는 경우 409와 원자적 rollback으로 대기 상태를 보존한다.

### 단계 2. 카테고리·제조사 삭제 계약 수정

1. 단건 삭제와 일괄 삭제 모두 참조 컬럼을 `NULL`로 바꾸는 로직을 제거한다.
2. 연결된 노드·장비·대기 승인 요청이 있으면 직접 삭제를 차단하고 참조 건수를 관리자에게 표시한다.
3. 필요한 경우 별도의 병합 작업으로 원본 마스터의 노드와 레거시 참조를 승인된 대상 마스터로 옮긴 뒤 원본을 삭제한다.
4. 병합은 `BEGIN IMMEDIATE` 단일 트랜잭션에서 수행하며 원본과 대상의 동일성, 대상 승인 상태, 루트 노드 중복과 이름 충돌을 사전 검사한다.
5. 참조가 0건인 마스터만 직접 삭제할 수 있게 API와 관리자 UI의 계약을 통일한다.

### 단계 3. 스키마 버전과 의미 기반 호환성

1. 애플리케이션의 목표 스키마 정수 버전을 정의하고 `PRAGMA user_version`과 `sys_migrations`를 함께 관리한다. 전자는 현재 구조 버전, 후자는 적용 이력을 담당한다.
2. 신규 DB 생성 DDL과 migration 완료 후의 목표 계약을 하나의 canonical schema 정의에서 파생하거나 교차 검증한다.
3. 백업 호환성 검사는 원시 CREATE SQL 문자열이나 기능과 무관한 물리적 컬럼 순서 대신 컬럼명·형식·NULL·기본값·PK·FK·인덱스의 의미를 비교한다.
4. 컬럼 누락, 제약 변경, 잘못된 FK, 필수 인덱스 누락은 계속 거부한다. `SessionToken`처럼 물리 순서만 다른 경우에만 동등성을 인정한다.
5. 신규 생성 DB와 운영 이력 복제 DB를 서로 백업·복원하는 교차 시험을 추가한다.

### 단계 4. 레거시 `equipment` 단계적 폐기

1. 런타임·백업 검사·migration·`down_migration.py`의 모든 `equipment` 참조를 분류한다.
2. 첫 릴리스에서는 현재 필수 테이블 집합을 `equipments` 중심으로 명시하고, 레거시 테이블은 과도기 호환 대상으로만 둔다.
3. 레거시 테이블이 계속 0건이고 읽기·쓰기가 없으며 새 복구 전략이 검증된 뒤 다음 릴리스에서만 보관 후 제거를 검토한다.
4. `down_migration.py`가 현재 3-Tier 데이터를 레거시 구조로 되돌리는 복구 경로이므로 대체 rollback 계약이 마련되기 전에는 DROP하지 않는다.
5. 실제 DROP은 별도 운영 승인, 검증된 백업, 독립 down/restore 절차가 모두 있을 때만 수행한다.

### 단계 5. 측정 기반 인덱스 개선

staging의 운영 DB 사본에서 대표 파라미터로 `EXPLAIN QUERY PLAN`과 응답 시간을 비교한다. 후보는 다음과 같으며 결과가 없는 인덱스는 추가하지 않는다.

- 내 장비·임시 저장: 실제 OR NULL 조건과 정렬을 고려해 `equipments(user_id, id DESC)` 채택
- 공개 장비: 공개·비임시 조건의 부분 인덱스 또는 동등한 복합 인덱스
- 비밀번호 재설정 최신 조회: `password_resets(UserId, ExpiresAt DESC)`; 두 실제 조회에서 모두 정렬을 활용하고 IsUsed는 잔여 조건으로 검사한다.
- 대기 승인 중복 검사: `approval_requests(RequestType, Status)`; JSON 표현식 인덱스는 데이터량과 SQLite 호환성 확인 후 별도 판단

`audit_logs.AuditId`는 INTEGER PRIMARY KEY의 rowid 순서가 이미 최신순 조회를 지원할 수 있으므로 단순히 SCAN 표기만 보고 중복 인덱스를 만들지 않고 실제 비용을 측정한다.

## 5. 검증 및 staging 게이트

1. 빈 DB 생성, 역사 DB migration, migration 재실행이 모두 성공해야 한다.
2. 모든 정상 연결에서 `foreign_keys=1`이고 선언·논리 참조 고아가 0건이어야 한다.
3. 장비 CRUD, 옵션·노드 관리, 장비 삭제와 독립 감사 로그 보존, 사용자 수명주기, 승인 요청을 회귀 시험한다.
4. 참조가 있는 카테고리·제조사 삭제는 안전하게 차단되고, 병합은 성공·충돌·rollback 시나리오를 모두 통과해야 한다.
5. 신규 DB와 역사 DB의 백업 생성·검사·복원이 양방향으로 성공해야 한다.
6. 후보 인덱스는 대표 조회 계획 또는 지연이 개선되고 쓰기 회귀가 허용 범위 안일 때만 채택한다.
7. migration 전후 행 수·핵심 집계·스키마 지문을 비교하고 `integrity_check=ok`, `foreign_key_check=0건`을 확인한다.
8. staging 보고서에 적용 SQL, 결과, rollback 리허설, 미채택 후보를 남긴 뒤에만 운영 반영을 제안한다.

## 6. 운영 적용 및 중단 조건

- 점검 모드에서 새 쓰기를 차단하고 검증된 백업을 만든 뒤 코드와 migration을 순차 적용한다.
- 기준선 해시 불일치, 외래 키 또는 논리 고아 발견, 예상하지 못한 스키마, 백업 검증 실패, 병합 충돌 미처리, migration 비멱등성이 하나라도 있으면 운영 적용을 중단한다.
- FK 위반이 발견됐다는 이유로 외래 키 강제를 다시 끈 채 서비스를 계속하지 않는다. 데이터를 분류하고 별도 정정 계획으로 분리한다.
- 적용 후 핵심 API, 백업 다운로드, 관리자 마스터 관리, 장비 등록·삭제를 확인한 뒤 점검 모드를 해제한다.

## 7. rollback

- 스키마 변경 전 검증된 DB 사본을 보존하고 코드 rollback과 DB rollback을 구분한다.
- 신규 인덱스와 `user_version` 변경은 명시적 down migration으로 되돌린다.
- 데이터 이동이 포함된 마스터 병합은 트랜잭션 실패 시 자동 rollback하며, 완료된 병합의 운영 취소는 감사 자료와 백업을 이용한 별도 복구 작업으로 취급한다.
- 레거시 테이블 DROP은 이번 1차 구현 범위에 포함하지 않는다. 향후 수행 시 파일 복구가 유일한 안전한 rollback일 수 있음을 명시한다.

## 8. 완료 기준

- 연결 초기화, 마스터 삭제, 스키마 버전·호환성, 레거시 전환, 조회 인덱스의 구현·테스트 문서가 모두 연결된다.
- 신규·역사·운영 복제 DB에서 모든 staging 게이트를 통과한다.
- 운영 적용 전후 무결성 검사와 핵심 기능 smoke test가 통과한다.
- 접근 로그 정책은 변경되지 않는다.
