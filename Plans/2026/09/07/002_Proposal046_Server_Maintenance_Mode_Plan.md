# [수정 구현계획 보고서] 제안-046 서버 점검 모드 및 관리자 전용 접속 통제

작성일: 2026-09-07
상태: 채택 완료, 구현 대기
연관 기능: [제안-013] DB 백업·복원, [제안-018] 세션 강제 만료

## 1. 목표

점검 모드는 Flask 서비스를 계속 실행한 상태에서 일반 사용자의 로그인과 업무 요청을 차단하고, 관리자에게 점검 제어와 DB 백업·복원 화면을 제공한다.

| 상태 | 일반 사용자 | 관리자 | DB 동작 |
| --- | --- | --- | --- |
| `NORMAL` | 정상 사용 | 정상 사용 | 정상 읽기·쓰기 |
| `DRAINING` | 로그인·기존 요청 차단, 점검 안내 | 로그인 및 관리자 메뉴 사용 | 관리자 작업과 백업·후보 검증 허용 |
| `RESTORING` | 점검 안내 | 기존 복원 화면에서 진행 상태 확인 | 복원 작업 외 읽기·쓰기 일시 동결 |
| `RECOVERY` | 계속 차단 | 복원된 DB 계정으로 로그인·검증 | 관리자 검증 작업 허용 |

서버 프로세스를 멈추는 `OFFLINE` 상태와 외부 정적 페이지는 이 계획에서 제외한다.

## 2. 점검 활성화 흐름

1. 관리자 화면에서 점검 코멘트, 시작 시각, 예상 종료 시각을 입력한다.
2. `POST /api/admin/maintenance/enable`은 로그인, 관리자 역할, CSRF, 현재 비밀번호, `MAINTENANCE` 확인 문구를 검증한다.
3. 점검 상태 파일을 `DRAINING`으로 원자적 변경한다. 상태 파일은 복원 대상 DB 밖에 둔다.
4. 중앙 요청 게이트가 일반 사용자의 모든 업무 요청을 503으로 차단한다.
5. [제안-018]의 토큰 갱신 SQL을 내부 공통 함수로 분리하여 `Role != 'admin'`인 모든 계정의 `SessionToken`을 갱신한다.
6. 기존 브라우저는 5초 간격 `/api/check_session` 또는 다음 API 요청에서 점검 상태를 받고 로그인 화면으로 이동한다.
7. 로그인 화면은 설정된 코멘트와 예상 종료 시각을 표시한다. 일반 사용자 로그인은 자격 증명 확인 후 세션 생성 전에 거부하고, 관리자는 로그인시킨다.

## 3. 중앙 요청 게이트

전역 `before_request`에서 점검 상태를 읽고 요청의 세션 Role을 서버 측에서 확인한다. `DRAINING`과 `RECOVERY`에서는 관리자를 허용하고 일반 사용자는 차단한다.

`RESTORING`에서는 DB를 사용하는 새 요청을 관리자 요청까지 잠시 차단한다. 이미 열린 복원 화면이 계속 동작하도록 로그인 GET, 정적 자원, 공개 점검 상태, 복원 작업 상태 조회만 허용한다. 로그인 POST는 DB 복원이 끝나 `RECOVERY`가 된 뒤 다시 허용한다.

HTML 요청은 점검 화면 또는 로그인 화면을 반환하고 API는 503 JSON을 반환한다. 응답에는 `Retry-After`, `Cache-Control: no-store`, 점검 상태 식별 헤더를 포함한다. 회원가입, 이메일 인증, 비밀번호 재설정과 모든 일반 데이터 변경은 점검 중 차단한다.

## 4. 상태 보존

점검 상태는 보호된 JSON 파일에 `state`, 코멘트, 시작·예상 종료 시각, 관리자 식별자, revision을 저장한다. 동일 디렉터리의 임시 파일을 완전히 기록한 뒤 `os.replace`로 교체한다.

상태 파일에는 비밀번호, 세션 토큰, CSRF 토큰을 기록하지 않는다. 예상 종료 시각이 지나도 자동 해제하지 않는다. DB 복원이나 앱 재시작 후에도 `RECOVERY` 또는 `DRAINING` 상태가 유지되고 관리자가 명시적으로 해제해야 한다.

## 5. 관리자 화면

- 관리자 센터에 `서버 점검 관리` 메뉴를 추가한다.
- 점검 코멘트와 예상 종료 시각 입력, 활성화·해제, 현재 상태 및 만료된 비관리자 세션 수를 표시한다.
- 점검이 활성화되면 `데이터베이스 백업 및 복원` 메뉴로 이동할 수 있다.
- DB 복원 중에는 페이지를 떠나지 않도록 경고하고 `draining → snapshotting → restoring → validating → succeeded/rolling_back/failed` 상태를 표시한다.
- 복원 성공으로 세션이 만료되면 후보 DB 관리자 계정으로 다시 로그인하도록 안내한다.

## 6. 점검 해제

`POST /api/admin/maintenance/disable`은 `RECOVERY` 또는 `DRAINING` 상태에서만 허용한다. 관리자 재인증, CSRF, 확인 문구를 요구한다. DB 복원을 수행했다면 무결성 검사와 후보 관리자 로그인 가능성 확인이 성공한 뒤에만 `NORMAL` 전이를 허용한다.

점검 중 만료된 일반 사용자 세션은 되살리지 않는다. 점검 해제 후 사용자는 새로 로그인해야 한다.

## 7. 장애 처리

- 비관리자 토큰 갱신이 실패하면 점검 게이트를 유지하고 부분 실패를 관리자에게 표시한다.
- 복원 작업이 잠금이나 요청 배출 제한 시간을 넘기면 운영 DB를 건드리지 않고 `DRAINING`으로 돌아간다.
- 앱이 `RESTORING` 중 비정상 재시작되면 자동으로 일반 운영을 열지 않고 `RECOVERY` 상태로 시작해 관리자 확인을 요구한다.
- 점검 상태 파일이 없고 미완료 복원 저널도 없으면 최초·정상 기동으로 보고 `NORMAL`을 사용한다. 상태 파일이 손상되었거나 미완료 복원 저널이 있으면 `RECOVERY`로 시작하여 일반 사용자를 차단한다.

## 8. 수용 기준

- 점검 코멘트와 예상 종료 시각이 로그인 화면에 동일하게 표시된다.
- 일반 사용자는 신규 로그인과 기존 세션 요청 모두 차단된다.
- 관리자는 `DRAINING`과 `RECOVERY` 상태에서 로그인하고 관리자 메뉴를 사용할 수 있다.
- 복원 중에도 Flask가 점검 안내와 작업 상태를 제공한다.
- 일반 사용자가 Role 값이나 URL을 조작해 점검 게이트를 우회할 수 없다.
- 점검 상태 변경, 세션 만료, DB 백업·복원 결과가 감사 로그와 외부 작업 저널에 기록된다.
- 관리자 확인 없이 예상 종료 시각만으로 점검이 해제되지 않는다.
