## 1. 사용자 목적

Python을 모르는 사용자가 실제 코드를 읽으면서 다음을 배울 수 있도록 한국어 설명 주석을 보강한다.

- Python 문법과 변수의 입출력
- 함수와 데코레이터의 실행 순서
- Flask 요청에서 응답까지의 흐름
- SQLite 연결, SQL, 트랜잭션과 마이그레이션
- 인증·권한·세션·CSRF 처리
- 오류·예외·롤백 경로
- 백엔드 결과가 템플릿과 사용자 화면에 미치는 영향

설명성보다 더 높은 우선순위는 기존 동작의 완전한 보존이다. 주석을 달기 위해 실행 코드를 개선하거나 정리하지 않는다.

기존 계획의 구조적 문제는 4,568행 파일 전체를 한 페이즈로 취급하고, 소스 변경과 주석 작성을 한 번에 수행했으며, 검증을 마지막에 집중시킨 것이다. 이번 계획은 작은 패킷, 추가 전용 편집, 패킷별 검증, 독립 검토로 이 경로를 차단한다.

손상된 `15bf550`의 주석은 정답 자료로 재사용하지 않는다. 문구를 참고해야 한다면 정상 코드와 다시 대조해 처음부터 검증한다. 특히 측정 근거가 없는 `0%`, `95%`, `100% 보장` 같은 표현은 금지한다.

## 4. 절대 불변조건

모든 패킷에 다음 조건을 동일하게 적용한다.

1. 기준본의 기존 글자, 공백, 개행, 실행문, 문자열, SQL, 데코레이터, 함수 시그니처와 기존 주석을 삭제·수정·이동하지 않는다.
2. 새 내용은 독립된 전체 행 `#` 주석으로만 추가한다.
3. 모든 신규 주석은 `# [학습:<패킷ID>-<일련번호>][<분류>]`로 시작한다.
4. 기존 코드 줄 끝에 인라인 주석을 붙이지 않는다.
5. 새 빈 줄도 기본적으로 추가하지 않는다.
6. 기존 docstring을 수정하지 않고 새 docstring이나 삼중 따옴표 문자열을 만들지 않는다. docstring은 런타임 `__doc__`와 AST를 바꾸므로 이 작업에서는 일반 주석으로 보지 않는다.
7. SQL, HTML, JSON, 이메일 본문 등 모든 다중행 문자열 안에는 주석을 넣지 않는다. 내부 각 행의 의미는 문자열 시작 실행문 앞의 `#` 묶음으로 설명한다.
8. 데코레이터 묶음과 `def` 사이에는 주석을 넣지 않는다. 함수 메타 주석은 첫 데코레이터 위에 둔다.
9. 다중행 괄호·리스트·딕셔너리·함수 인자 중간에는 주석을 넣지 않고, 전체 구문의 직전에 설명한다.
10. `# coding:`, `# type:`, `# noqa`, `# nosec`, `# fmt`, `# pylint`, `# pyright`처럼 도구 동작을 바꾸는 특수 주석은 추가하지 않는다.
11. 자동 포매터, 전체 파일 재출력, 정규식 일괄 치환, 인코딩 변환을 사용하지 않는다.
12. 구조화된 편집 도구만 사용한다. 한 번의 패치는 현재 패킷 범위만 다룬다.
13. 여러 AI가 동일 후보 파일을 동시에 수정하지 않는다. 병렬 작업은 읽기·주석 초안·독립 검토에만 허용한다.
14. 기존 설명이 잘못돼 보여도 현재 패킷에서 고치지 않는다. 위치와 근거를 원장에 기록하고 별도 사용자 결정 대상으로 둔다.
15. PEP 263 해석에 영향을 줄 수 있으므로 기준본의 첫 두 물리 행 앞이나 사이에는 어떤 주석도 추가하지 않는다.

이 조건 중 하나라도 어기면 내용이 좋아도 해당 패킷은 실패다.

주석 추가는 물리 행 번호, 소스 파일 hash·mtime, traceback·coverage·디버거에 보이는 행 번호와 생성되는 `.pyc`를 불가피하게 바꾼다. 이는 실행 토큰을 바꾸지 않는다는 주장과 구분해야 한다. 기준 저장소에는 `inspect`, `linecache`, `co_firstlineno`, `getsourcelines` 등 소스 행 번호에 의존하는 Python 코드가 없음을 선행 검사하되, 저장소 밖 도구의 북마크·브레이크포인트까지 동일하다고 주장하지 않는다. 최종 보고서에는 이 의도된 관찰 가능 변화가 반드시 남아야 한다.

## 5. 교육용 주석 표준

신규 주석 분류는 다음 목록으로 제한한다.

- `[역할]`: 함수·라우트·논리 블록의 목적
- `[입력]`: 요청값, 인자, 세션, DB 조회값이 들어오는 곳
- `[출력]`: 반환값, 응답 JSON, 화면, DB 변경
- `[의존성 관계]`: 호출 함수, 테이블, 템플릿, 전역 상태
- `[변경 시 영향도]`: 이 부분이 바뀌면 함께 확인할 위치
- `[Python]`: 초보자가 알아야 할 문법과 자료형
- `[흐름]`: 실행 순서
- `[분기]`: 조건이 참·거짓일 때의 다음 경로
- `[DB]`: 쿼리 목적, 바인딩 값, commit·rollback·close
- `[보안]`: 인증·권한·CSRF·세션·민감정보 취급
- `[예외]`: 실패 시 반환·복구·정리 경로

예시는 다음과 같다.

```python
# [학습:A03-001][Python] sqlite3.connect()가 반환한 연결 객체를 conn 변수에 저장합니다.
conn = get_db_connection()
# [학습:A03-002][DB] cursor는 SQL을 실행하고 조회 결과를 읽는 작업 창구입니다.
cursor = conn.cursor()
```

주석은 코드에서 직접 증명되는 사실만 서술한다. 추론이 필요하면 사실처럼 적지 않고 패킷의 `확인 필요` 항목으로 보낸다. 쉬운 한국어를 사용하되 실제 Python·Flask·SQLite 용어를 괄호 안에 함께 적는다.

`RULE-4.3.4`의 행별 설명은 다음처럼 안전하게 충족한다.

- 일반 실행문은 바로 앞 주석에서 설명한다.
- 여러 물리 행으로 이어지는 하나의 Python 구문은 시작 전 주석 묶음에서 각 구성 요소를 설명한다.
- 다중행 SQL·문자열은 문자열 밖의 주석 묶음에서 컬럼·조건·바인딩·결과를 설명한다.
- 닫는 괄호와 문법 전용 행은 해당 구문 설명에 포함하고, 위험한 위치에 주석을 억지로 삽입하지 않는다.
- 각 패킷 원장에는 설명 대상과 주석 ID의 대응표를 남겨 누락을 기계적으로 셀 수 있게 한다.
- 기존 주석은 소스를 고쳐 ID를 붙이지 않고 원장에서 `existing:<정규화 원문 hash>`로 식별한다. 이미 충분한 기존 설명을 중복 작성하지 않는다.

## 6. 작업 구조

### 6-1. 준비 아티팩트

실행 모델은 주석보다 먼저 `Staging/app_py_comments/`에 다음 모의 구조를 만든다.

```text
Staging/app_py_comments/
├─ README.md
├─ task.md
├─ packet-manifest.yaml
├─ ledger.md
├─ work-orders/<패킷ID>.md
├─ tools/task-board.mjs
├─ candidate/app.py
├─ proposals/<패킷ID>.md
└─ validation/<패킷ID>.md
```

- `candidate/app.py`: 기준본에서 시작하는 단일 후보 파일
- `packet-manifest.yaml`: 패킷 경계, 앵커, 부모 blob, 상태
- `ledger.md`: 작업자·검증자·결과·보류 사항·다음 패킷
- `proposals/`: 작은 모델이 작성한 추가 주석과 배치 위치
- `validation/`: 자동 검사와 독립 검토 결과

`task.md`는 사용자가 보는 진행판이고 `packet-manifest.yaml`은 AI가 읽는 단일 상태 원본이다. 체크박스를 직접 완료 처리하지 않는다. manifest에서 `checkpointed`인 항목만 동기화 도구가 `[x]`로 렌더링하며, 두 파일이 다르면 어떤 AI도 작업을 시작하지 않는다.

Staging은 실행 환경이 아니다. Windows에서 애플리케이션을 기동하지 않는다.

최초 `candidate/app.py`는 현재 편집기의 재저장이나 PowerShell의 `Get-Content`/`Set-Content` 왕복으로 만들지 않는다. 기준 blob과 일치함이 확인된 `app.py`를 바이트 보존 가능한 구조화 복사 기능으로 복제하거나, 별도 worktree에서 Git이 기준 commit을 직접 물질화하게 한다. 해당 기능이 실제로 확인되지 않으면 정확한 원본·대상·복구 절차를 제시하고 사용자 승인을 받은 파일 복사만 사용한다. 복제 직후 후보의 학습 주석을 0개 제거한 가역성 검사가 기준본과 일치해야 다음으로 간다.

`Staging/app_py_comments/`만을 기록하는 전용 브랜치 `staging/app-py-comments-v2`를 사용한다. 정적 검사와 독립 검토를 통과한 후보는 Linux 전달용 `transport` commit으로 만들 수 있지만 아직 승인본이 아니다. Linux 검증까지 통과한 뒤 검증 증거를 더한 별도 `checkpoint` commit만 `checkpointed`의 복구 가능한 실체로 인정한다. 모든 commit은 해당 하위 경로로 제한하고, 기존 `Staging/`의 다른 사용자 파일은 추가·수정·삭제하지 않는다.

브랜치 전환은 다른 AI가 파일을 쓰지 않는 단독 통합 구간에서만 수행한다. 먼저 `git status`를 기록하고 대상 밖 변경이 있으면 보존한다. 플랫폼이 안전한 분리 worktree를 지원하고 정확한 생성·정리 경로를 승인받았다면 전용 worktree를 우선하며, 확인 없이 현재 작업 트리의 사용자 변경을 stash·reset·clean하지 않는다.

### 6-2. 역할 분리

| 역할 | 허용 작업 | 금지 작업 |
|---|---|---|
| 계획 관리자 | 패킷 발급, 상태 관리, 다음 패킷 개방 | 주석 품질 검토와 작성 결과를 혼자 승인 |
| 작성 AI | 한 패킷의 주석 초안 또는 구조화 패치 작성 | 범위 확대, 코드 수정, 다음 패킷 선행 |
| 통합 AI | 승인된 주석만 후보 파일에 순차 적용 | 문구 즉석 변경, 여러 패킷 동시 적용 |
| 검증 AI | diff·코드·주석 정확성 독립 검토 | 검토 중 직접 수정 |
| 사용자 | 파일 전체가 아닌 대표 스타일과 최종 병합 판단 | 패킷마다 반복 승인할 필요 없음 |

동일 AI가 작성자와 최종 검증자를 겸하지 않는다. 모델 공급자가 달라지면 더 좋지만, 최소 조건은 다른 세션과 독립된 원문 대조다.

### 6-3. 패킷 상태와 재개 계약

상태는 다음 방향으로만 이동한다.

```text
planned → proposed → integrating → static-validated
        → independently-reviewed → linux-pending
        → linux-validated → checkpointed
```

각 패킷은 아래 필드를 반드시 가진다.

- `packet_id`, 부모·하위 패킷 관계
- `base_commit`, `base_blob`, `base_candidate_blob`
- 시작·종료 심볼, 앞뒤 guard와 해당 원문 hash
- 제안 문서 hash, 작성 AI의 실제 모델·플랫폼
- 통합 후 `candidate_blob`
- Node·Python 검사 증거와 독립 검증 AI
- Linux 전달에 사용한 `transport_commit`과 검증한 원격 commit
- 보류·실패 사유, `next_action`, 최종 상태
- `checkpointed` 상태이면 복구 가능한 전용 Staging commit ID

`integrating` 상태에서 세션이 끊기면 부분 후보를 이어 쓰지 않는다. 직전 `checkpointed` 후보를 복원하고 같은 제안 hash로 다시 시작한다. 상태나 blob이 맞지 않으면 추정하여 다음 단계로 이동하지 않는다.

`linux-pending`에서 끊기면 원격 commit과 검증 결과가 모두 확인될 때까지 재전송하거나 통과로 간주하지 않는다. 실패한 transport commit은 기록에서 지우거나 강제 Push로 숨기지 않는다. 실패 증거를 기록하고 후보 파일을 직전 checkpoint와 같게 되돌리는 후속 commit을 만든 뒤 다시 시작한다.

실패 패킷의 아직 승인되지 않은 `[학습:<현재 패킷ID>-...]` 행은 구조화된 역패치로만 제거할 수 있다. 이는 기준본·기존 주석·승인된 앞선 패킷의 삭제를 허용하지 않는다. 역패치 뒤 직전 checkpoint commit의 후보와 바이트 단위로 같아야 한다.

### 6-4. 작업자 capability handshake

첫 패킷 전에 각 AI·플랫폼에 대해 다음 실제 능력을 기록한다.

- 필요한 파일을 정확히 읽을 수 있는가
- 구조화 편집과 사용자가 확인 가능한 diff가 있는가
- Undo 또는 동등한 Git·체크포인트 복구가 검증됐는가
- Node 사전 검증기를 실행할 수 있는가
- Linux·Python 최종 관문을 수행할 별도 환경이 있는가

확인되지 않은 능력을 모델 이름만으로 있다고 가정하지 않는다. 능력이 부족하면 해당 AI에는 읽기 전용 초안이나 검토 역할만 배정한다.

### 6-5. 사용자 번호와 공급자 간 콜드스타트 계약

사용자는 `task.md의 1-4`, `packet-manifest.yaml의 A04`, `task.md의 1번 다음 항목`처럼 파일과 대상을 지정할 수 있다. 사용자 번호 `1-4`와 기계 ID `A04`는 manifest에서 일대일로 매핑한다.

- 하위 번호나 패킷 ID를 지정하면 정확히 그 한 항목만 범위로 삼는다.
- 상위 번호만 지정하면 해당 영역에서 아직 `checkpointed`가 아닌 첫 하위 항목 하나만 선택하고, 한 항목을 마친 뒤 보고한다.
- `전체`가 명시되지 않은 상위 번호를 영역 전체 승인으로 확대하지 않는다.
- 존재하지 않거나 중복된 번호, Task↔manifest 불일치, 선행조건 미충족은 추측하지 않고 차단한다.
- 모든 AI는 같은 대화를 공유한다고 가정하지 않는 콜드스타트 작업자로 취급한다.

현재 예정 작업자는 다음과 같이 manifest에 고정하되, 실제 세션 시작 시 정확한 모델·추론 설정을 스스로 확인한다.

이는 기본 배정이며 사용자의 명시 지시로 역할을 바꿀 수 있다. 단, 같은 패킷의 작성자와 독립 검증자는 달라야 한다. 새 작업자는 플랫폼별 루트 진입점(`AGENTS.md`, `GEMINI.md`, `CLAUDE.md`)을 먼저 따르고, `Staging/app_py_comments/README.md` → `task.md` → `packet-manifest.yaml` 순으로 읽은 뒤 `task-board.mjs validate`와 `resolve <대상>` 결과를 작업 범위로 사용한다.

## 8. 소형 모델용 패킷 계약

전체 계획은 계획 관리자와 통합 AI만 읽는다. 작은 작성 AI에게는 전체 `app.py`와 이 계획 전문을 주지 않고, 필수 규칙을 내장한 아래 축약 패킷만 전달한다.

```text
패킷 ID와 상태
고정 기준 commit·blob
직전 승인 후보 blob
시작·종료 심볼과 앞뒤 10행 원문 guard
소유 코드 조각
직접 호출하거나 참조하는 함수·테이블·템플릿의 짧은 근거 조각
core.kernel, engineering.code-comments, tools.file-editing,
operations.staging 및 해당 영역 보안·데이터 규칙의 축약 원문
추가 가능한 주석 형식과 절대 금지 목록
설명해야 할 코드 행·논리 구문 체크리스트
현재 패킷의 완료 조건과 중지 조건
```

작성 AI의 출력은 다음 네 부분으로 제한한다.

1. 추가할 주석과 고유 앵커
2. 각 주석이 설명하는 기존 원문
3. 근거가 부족해 보류한 항목
4. 범위 밖 변경이 없다는 자체 확인

작은 모델은 전체 파일 요약이나 후속 패킷 계획을 만들지 않는다. 패킷이 컨텍스트 예산을 넘으면 규칙을 생략하지 않고 먼저 하위 패킷으로 나눈다.

## 9. 검증기를 먼저 만드는 0단계

주석 한 줄을 작성하기 전에 다음 두 검증기와 테스트 표본을 Staging에 구현·검증한다.

### 9-1. Windows·Node 사전 검증기

- UTF-8 엄격 디코딩, BOM·NUL·`U+FFFD`·혼합 개행 검사
- 현재 패킷의 허용된 신규 주석 행만 제거한 결과가 직전 checkpoint 후보의 바이트열과 정확히 같은지 검사
- 누적된 모든 허용 신규 주석 행을 제거한 결과가 고정 Git blob에서 물질화한 기준본의 바이트열과 정확히 같은지 검사
- 신규 행이 허용된 `# [학습:<패킷ID>-...]` 형식인지 검사
- 기존 행 삭제·수정·이동과 실행문 중복을 한 건이라도 발견하면 실패
- 현재 패킷 앵커 밖 추가를 실패 처리
- 함수·라우트·마이그레이션·테이블·인덱스 목록을 기준 스냅숏과 비교
- `직전 checkpoint 후보 → 현재 후보`에서 현재 패킷 ID의 주석만 추가됐는지 비교
- `22fcd83 기준본 → 현재 후보`에서 원본 행 전체가 누적 상태에서도 보존됐는지 비교
- 전체 학습 주석 ID와 패킷별 일련번호가 유일한지 검사

두 바이트 비교는 행의 부분 일치나 단순 개수 비교가 아니라 가역성 검사다. 검증기가 직접 허용 태그 행만 제거했을 때 원문 전체가 그대로 복원되어야 하므로, 동일한 원문 행이 여러 번 나오는 경우에도 삭제·이동을 통과시키지 않는다. 기준본과 후보본은 동일한 LF·UTF-8 무 BOM 표준으로 물질화하며, 표준화 과정이 소스 변경을 감추지 않도록 표준화 전 인코딩·개행 검사 결과도 함께 남긴다.

Node 검증기는 텍스트 보존과 범위 통제의 사전 관문이다. Python 토크나이저 없이 다중행 문자열 내부인지 완전하게 판정한다고 주장하지 않는다. Python 문법, 문자열 내부 삽입과 의미 동등성의 최종 판정은 다음 Linux 관문만 담당한다.

### 9-2. Linux·Python 의미 검증기

- 기준본과 후보본을 동일한 미니서버 Python 버전의 `tokenize.tokenize()`로 읽는다.
- `ERRORTOKEN`은 즉시 실패한다.
- 위치 좌표를 제외한 `(exact_type, string)`을 비교한다.
- 새 독립 학습 주석의 `COMMENT`와 그 주석 전용 행의 `NL`만 제외한다.
- 나머지 `NAME`, `OP`, `STRING`, `NUMBER`, `INDENT`, `DEDENT`, `NEWLINE` 등의 순서와 값은 완전히 같아야 한다.
- `ast.parse(..., type_comments=True)` 결과를 `ast.dump(..., include_attributes=False)`로 완전 비교한다.
- 모든 문자열 토큰 원문과 해시 비교
- `python3 -m py_compile app.py`
- 저장소의 Python 코드에서 소스 위치 introspection 의존성이 새로 생기지 않았는지 검사

`py_compile`은 운영 작업 디렉터리에서 직접 실행하지 않는다. 별도 임시 checkout 또는 명시적 임시 bytecode 경로를 사용하고, 생성된 `__pycache__`·`.pyc` 위치와 정리 책임을 검증 기록에 남긴다.

승인된 기존 Linux CI를 사용할 수는 있으나, 이 계획만으로 CI 설정 파일을 새로 만들거나 바꾸지 않는다. CI 구성이 필요하면 `app.py` 단일 파일 범위를 벗어나므로 별도 계획과 승인을 받는다. import·DB 초기화·Flask 기동·smoke test는 `operations.server-execution`에 따라 미니서버에서만 수행한다.

### 9-3. 검증기 자체의 필수 실패 표본

다음 후보를 모두 거부한 뒤에만 주석 작업을 시작한다.

- 실행문 또는 SQL 한 행 삭제
- 함수·라우트·데코레이터 중복
- 다중행 SQL 문자열 안에 `#` 삽입
- 따옴표·괄호·들여쓰기 변경
- 잘린 UTF-8 바이트
- 기존 패킷 주석 삭제
- 파일 일부 재정렬
- docstring 변경
- 허용 범위 밖 주석 추가

정상본 자기 비교와 합법적인 독립 `# [학습:...]` 추가 표본은 통과해야 한다. 과거 손상본 `15bf550:app.py`도 반드시 실패해야 한다.

## 10. 패킷 실행 순서

1. 계획 관리자는 전체 계획을 읽고, 작성 AI에는 해당 패킷용 small-model context pack과 축약 계약만 발급한다.
2. 기준 commit·blob과 직전 승인 후보 blob을 확인한다.
3. 패킷 경계와 앞뒤 guard가 정확히 일치하는지 확인한다.
4. 작성 AI가 Staging 제안만 만든다.
5. 통합 AI가 제안의 허용 형식과 앵커를 확인하고 후보 파일에 구조화 패치로 적용한다.
6. Node 사전 검증기를 실행한다.
7. 다른 AI가 기존 코드와 새 설명을 한 줄씩 대조한다.
8. 승인된 전달 경로가 있는지 확인하고, 후보를 경로 제한 transport commit으로 만든다.
9. 명시적으로 승인된 비운영 Staging 브랜치만 Push하거나 승인된 CI 전달 경로를 사용한다.
10. 미니서버의 격리 checkout에서 정확한 transport commit에 대해 Linux Python 의미 검증과 격리된 `py_compile`을 통과시킨다.
11. 검증 결과, 작업자, 검증자, 후보 blob, transport commit, 보류 항목을 원장에 기록한다.
12. 모든 관문을 통과한 패킷만 검증 증거를 포함한 checkpoint commit으로 남겨 `checkpointed`로 만들고 다음 패킷을 연다.

첫 실행은 짧고 대표적인 A04(`get_db_connection`, `log_audit`)를 스타일 파일럿으로 한다. 파일럿은 자동 검증 뒤 사용자가 표현 수준과 학습 난이도를 한 번 확인한다. 이후에는 모호한 설명이나 차단 조건이 생기지 않는 한 패킷마다 사용자 승인을 요구하지 않는다.

## 13. Linux 전달과 운영 병합

현재 Windows 환경에는 실제 Python 인터프리터가 없으므로 Python 의미 검증을 로컬 성공으로 가장하지 않는다. Linux 검증은 운영 프로세스와 분리된 깨끗한 checkout 또는 승인된 CI에서 수행한다.

### 13-1. 패킷별 Linux 검증 통로

첫 A04 파일럿 전에 사용자가 다음 통로 중 하나를 별도로 승인해야 한다.

1. 기본 통로는 원격 비운영 브랜치 `staging/app-py-comments-v2`다. 이 브랜치에는 `Staging/app_py_comments/`만 올리고 루트 `app.py`나 `main`을 바꾸지 않는다.
2. 대안은 이미 존재하며 사용 승인을 받은 CI다. 이 계획은 새 CI 설정 파일을 만들 권한을 주지 않는다.
3. Git 통로를 사용할 때에는 패킷별 Push 승인을 받거나, 이 브랜치와 검증 명령에만 한정된 일괄 승인을 먼저 받는다. 어느 승인도 없으면 `independently-reviewed`에서 중지한다.
4. 미니서버는 운영 checkout과 다른 명시적 임시 checkout에서 exact transport commit을 fetch한다. `candidate/app.py`를 입력으로 검증기만 실행하며 운영 DB, 포트, 프로세스에 접근하지 않는다.
5. commit 일치, 토큰·AST·문자열·가역성·격리 `py_compile`이 모두 통과해야 `linux-validated`가 된다. 실패하면 직전 checkpoint 복원 commit과 실패 보고서를 남기며 force-push하지 않는다.

이 통로의 Push·미니서버 명령 승인은 주석 작성 승인과 구별한다. 일괄 승인을 받더라도 대상 브랜치, 허용 명령, 임시 checkout 경로, 금지 대상(`main`, 운영 DB, 실행 프로세스)을 원장에 고정한다.

### 13-2. 최종 운영 후보

1. 전체 Staging 후보 완료 후, 사용자에게 종합 보고서와 대표 diff를 제출한다.
2. 기준본과 최종 Staging 후보 사이의 검증 완료 diff를 고정하고 SHA-256을 기록한다.
3. 사용자 병합 승인 뒤 그 동일한 diff만 hash와 앵커를 재검증하여 로컬 운영 후보 브랜치 `docs/app-py-educational-comments-v2`의 `app.py`에 한 번 적용한다. 주석을 다시 생성하거나 문구를 즉석에서 바꾸지 않는다.
4. 적용 결과가 Staging 후보와 바이트 단위로 같은지 확인하고 기준선 대비 전체 정적 검증을 반복한 뒤 로컬 후보 commit을 만든다.
5. 후보 브랜치 Push에 대한 명시 승인을 받은 뒤에만 원격 후보 브랜치로 전송한다.
6. 미니서버의 운영 프로세스와 분리된 깨끗한 checkout에서 후보 commit 일치, 토큰·AST·문자열·`py_compile`, 신규 빈 DB 기동을 검증한다. 운영 `equipment.db`를 시험에 사용하지 않는다.
7. 검증 결과를 보고하고 사용자의 `main` 병합·Push 승인을 별도로 받는다.
8. `main` 반영 후에도 실제 배포와 프로세스 재시작은 별도 승인 범위로 취급한다.
9. 배포 승인 뒤 미니서버에서 `main`을 pull하고 commit, `py_compile`, 백업·복구 경로를 확인한 다음 통제된 재시작을 수행한다.
10. 로그인, 3-Tier 장비, 권한, 접근 로그를 최소 점검한다.

운영 확인 뒤 `ledger.md`와 최종 검증 결과의 영구 보존분을 `Report/`로 먼저 이관한다. 이후 `Staging/app_py_comments/`의 정확한 정리 목록과 복구 가능성을 제시하고 파괴적 정리 승인을 받은 뒤에만 해당 하위 디렉터리를 정리한다. 기존의 다른 `Staging/` 파일은 건드리지 않는다.

Staging transport·checkpoint commit과 운영 후보의 패킷 추적 commit은 안정화가 끝날 때까지 squash하지 않는다. 어느 영역에서 문제가 발생했는지 추적하고 허용 범위 안에서 해당 commit을 `git revert`할 수 있어야 한다.

## 14. 즉시 중지 조건

다음 중 하나라도 발생하면 자동 수정으로 밀어붙이지 않는다.

- 기준 commit·blob·앵커 불일치
- 다른 작업의 `app.py` 변경 발견
- 병합 충돌 또는 패치 문맥 불일치
- 실행문·문자열·기존 주석 변화
- UTF-8·토큰·AST·문자열·컴파일 검사 실패
- 주석이 실제 코드와 모순되거나 근거가 불충분함
- 지정 범위가 모델 컨텍스트 예산을 초과함
- 작성 AI가 현재 역할·패킷·금지사항을 정확히 재진술하지 못함
- 검증 AI와 작성 AI의 결론 불일치

동일 패킷이 두 번 실패하면 더 작은 하위 패킷으로 나누고 상위 모델 검토 대상으로 올린다. 실패 후보 위에 추가 수선 패치를 쌓지 않고 직전 승인 체크포인트로 돌아간다. 병합 충돌에서 자동 `ours`·`theirs` 선택을 금지한다.

## 15. 시간·컨텍스트 운영

이 작업을 하나의 5시간 사용량 창 안에서 끝내려 하지 않는다.

- 한 AI turn은 한 패킷의 작성 또는 한 패킷의 검증 중 하나만 담당한다.
- 각 패킷 종료 시 원장에 다음 시작점이 남으므로 다음 날·다른 모델이 이어받을 수 있다.
- 실제 편집은 순차적이지만, 의존성 조사와 주석 정확성 검토는 병렬화할 수 있다.
- 소형 모델에는 전체 파일이 아니라 패킷 코드, 직접 의존성, 필수 규칙 pack만 준다.
- 출력이 길어지면 주석 품질을 낮추거나 검증 규칙을 빼지 않고 패킷을 더 나눈다.

## 16. 최종 완료 조건

다음이 모두 충족되어야 주석 재구축 완료로 판정한다.

1. 기본 54개 패킷 각각이 `checkpointed` 상태이거나, 대체하도록 선택한 두 하위 패킷이 모두 `checkpointed` 상태다.
2. 함수·라우트 메타 필드와 행별 설명 대응표에 미해결 누락이 없다.
3. 기준본의 모든 기존 행이 내용과 순서를 유지한다.
4. Python 토큰, AST, 모든 문자열, 구조 카운트가 기준본과 동일하다.
5. Linux `py_compile`과 격리 기동, 핵심 smoke test가 성공한다.
6. 검증 1~8단계 종합 보고서가 실제 증거와 일치한다.
7. 사용자가 주석의 학습 난이도와 운영 병합 결과를 승인한다.
8. GitHub와 미니서버 반영은 별도 명시 승인 뒤 수행한다.

이 설계의 핵심은 작은 모델이 `app.py` 전체를 다시 작성하지 못하게 하는 것이다. 각 모델은 제한된 조각의 학습 주석만 제안하고, 기존 실행 토큰이 단 하나도 변하지 않았음을 도구와 독립 검토가 모두 증명해야 다음 단계로 진행할 수 있다.
