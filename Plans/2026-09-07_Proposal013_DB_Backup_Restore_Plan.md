# [수정 구현계획 보고서] 제안-013 웹 기반 DB 데이터 백업 및 복원

작성일: 2026-09-07
상태: 검토 완료, 구현 대기
선행 조건: [제안-046] 서버 점검 모드 및 관리자 전용 접속 통제

## 1. 확정된 운영 원칙

DB 백업과 복원은 모두 관리자 웹 화면에서 수행한다. Flask 프로세스와 웹 서비스는 중지하지 않는다. 점검 모드에서 일반 사용자를 차단하고, 실제 DB 복원 순간에만 새로운 DB 접근과 접근 로그 워커의 쓰기를 잠시 동결한다.

| 단계 | 서비스 상태 | 관리자 | 일반 사용자 |
| --- | --- | --- | --- |
| 점검 준비 | `DRAINING` | 로그인·백업·업로드·검증 가능 | 로그인 및 모든 업무 요청 차단 |
| DB 교체 | `RESTORING` | 이미 열린 복원 화면에서 진행 상태 확인 | 점검 안내만 제공 |
| 교체 검증 | `RECOVERY` | 복원된 DB의 관리자 계정으로 로그인·검증 | 계속 차단 |
| 점검 종료 | `NORMAL` | 정상 사용 | 재로그인 후 정상 사용 |

`RESTORING`은 서버 중지가 아니다. Flask는 점검 안내와 복원 작업 상태를 계속 응답하지만, 데이터베이스를 사용하는 다른 요청은 짧게 차단한다.

## 2. 관리자 화면의 순서

1. 관리자가 점검 사유, 시작 시각, 예상 종료 시각을 입력하고 점검 모드를 활성화한다.
2. 중앙 요청 게이트가 일반 사용자 요청을 차단하고, 기존 [제안-018] 세션 토큰 갱신 로직이 모든 비관리자 세션을 만료시킨다.
3. 관리자는 `데이터베이스 백업 및 복원` 메뉴에 진입한다.
4. `현재 DB 백업 내려받기`를 실행한다. 서버가 SQLite 온라인 백업으로 일관된 `.db` 스냅샷을 만들고 무결성을 검사한 뒤 다운로드한다.
5. 관리자는 보유한 `.db` 파일을 업로드한다. 이 단계에서는 운영 DB를 변경하지 않는다.
6. 서버가 후보 DB의 파일 크기, SQLite 헤더, 무결성, 외래 키, 필수 스키마, 애플리케이션 호환성 및 관리자 계정을 검사한다.
7. 화면에 현재 DB와 후보 DB의 파일 해시, 생성·업로드 시각, 주요 테이블 건수, 스키마 버전 차이를 비교 표시한다.
8. 관리자는 현재 관리자 비밀번호와 복원 후 사용할 후보 DB의 관리자 계정을 각각 검증하고 `RESTORE` 확인 문구를 입력한다.
9. 서버는 복원 직전 현재 DB를 자동 백업하고 `RESTORING`으로 전환한다. 이미 열린 화면은 작업 ID로 진행 상태를 표시한다.
10. 앱이 DB 접근을 동결한 뒤 후보 DB를 SQLite 온라인 백업 API로 운영 DB 연결에 복원한다.
11. 복원된 DB를 즉시 재검증한다. 실패하면 복원 직전 자동 백업을 같은 방식으로 되돌린다.
12. 성공하면 복원 DB의 모든 `SessionToken`을 갱신하고 상태를 `RECOVERY`로 바꾼다. 관리자 화면은 성공 결과를 표시한 뒤 로그인 화면으로 이동한다.
13. 관리자는 앞서 검증한 후보 DB 관리자 계정으로 로그인해 주요 기능을 확인하고 점검 모드를 해제한다.

## 3. 서버 내부 동결과 온라인 복원

현재 `app.py`는 요청별 SQLite 연결과 별도의 접근 로그 워커를 사용한다. 안전한 복원을 위해 다음 조정기가 필요하다.

- 단일 `restore_lock`: 병렬 복원과 중복 클릭을 거부한다.
- 요청 계수기와 조건 변수: `RESTORING` 전환 전에 시작된 DB 요청이 끝날 때까지 제한 시간 내에서 기다린다. 복원 작업 자신과 공개 상태 조회는 제외한다.
- 중앙 요청 게이트: `RESTORING` 이후 신규 DB 사용 요청을 503으로 거부한다. 로그인 GET, 정적 자원, 점검 상태와 복원 작업 상태 조회만 허용한다.
- 접근 로그 워커 일시정지: 새 점검 응답을 DB 큐에 넣지 않고 기존 큐를 배출한 뒤 현재 쓰기 배치가 끝났음을 확인한다.
- 제한 시간: 요청 배출 또는 DB 잠금 확보가 제한 시간 안에 끝나지 않으면 후보 DB를 적용하지 않고 `DRAINING`으로 되돌린다.

복원 직전 `live_conn.backup(before_restore_conn)`으로 자동 백업을 만든다. 후보 DB는 읽기 전용 연결로 열고 `candidate_conn.backup(live_conn)`으로 대상 DB에 적용한다. 완료 뒤 새 연결에서 `integrity_check`, `foreign_key_check`, 필수 객체·버전 검사를 다시 수행한다.

적용 또는 후속 검증이 실패하면 `before_restore_conn.backup(live_conn)`으로 자동 원복하고 원복 DB까지 재검증한다. 원복도 실패하면 점검 상태를 유지하고 관리자에게 자동 점검 해제 금지와 수동 복구 경로를 표시한다.

기술 근거는 SQLite 공식 Online Backup API 문서와 Python `sqlite3.Connection.backup()` 문서다. SQLite는 백업 작업 동안 대상 DB에 쓰기 트랜잭션을 유지하므로, 후보 DB를 운영 DB로 복사하는 구간에는 다른 쓰기를 앱에서 동결해야 한다. 완료된 대상은 복사 시작 시점의 소스 스냅샷이 된다.

## 4. 복원 작업의 비동기 UI

복원 실행 API는 검증된 후보 파일과 일회성 승인 토큰을 받아 작업 ID를 생성하고 백그라운드 복원 작업을 시작한다. 브라우저는 이미 렌더링된 관리자 화면을 유지하면서 전용 상태 API를 폴링한다.

작업 상태는 `queued`, `draining`, `snapshotting`, `restoring`, `validating`, `rolling_back`, `succeeded`, `failed`로 제한한다. 상태 API에는 내부 파일 경로, SQL 오류, 비밀번호를 노출하지 않는다. 작업 ID와 별도의 일회성 모니터 토큰을 요구하여 세션 토큰이 복원 후 만료되어도 최종 결과만 확인할 수 있게 한다.

## 5. 파일·권한·보안 설계

- 페이지와 모든 관리 API에 `login_required`, `admin_required`, `csrf_required`를 목적에 맞게 적용한다.
- 업로드 파일명은 사용하지 않고 서버 UUID로 저장한다. 크기 제한과 실제 바이트 수 제한을 함께 적용한다.
- 업로드·자동 백업 디렉터리는 저장소와 정적 웹 경로 밖에 두고 서비스 계정만 접근하게 한다.
- 후보 DB의 SQLite 헤더만 믿지 않는다. `integrity_check`, `foreign_key_check`, 필수 테이블·컬럼·인덱스, `sys_migrations` 기준을 함께 검사한다.
- 후보 DB에 복원 후 로그인 가능한 `Role='admin'` 계정이 있고 제공한 비밀번호가 맞는지 적용 전에 확인한다.
- 다운로드에는 `Cache-Control: no-store`와 첨부 응답을 사용한다. 백업 파일에 계정 정보와 로그가 포함된다는 안내를 표시한다.
- 점검·백업·후보 검증·복원·원복 결과를 DB 감사 로그와 DB 외부 작업 저널에 함께 남긴다. 복원으로 DB 감사 로그가 과거 상태로 돌아갈 수 있기 때문이다.

## 7. 수용 기준

- 점검 모드 활성화 직후 일반 사용자 로그인과 기존 세션 요청이 차단된다.
- 관리자는 점검 중 현재 DB를 내려받고 후보 DB를 업로드·검증할 수 있다.
- 다운로드한 백업과 복원된 DB가 무결성 및 주요 레코드 비교를 통과한다.
- 복원 중 Flask 프로세스는 살아 있고 로그인·점검·작업 상태 화면을 응답한다.
- `RESTORING` 동안 다른 DB 요청과 접근 로그 쓰기가 발생하지 않는다.
- 손상 파일, 과대 파일, 불일치 스키마, 관리자 계정 부재, 잘못된 비밀번호는 운영 DB 변경 전에 거부된다.
- 병렬 복원, 중복 작업 ID, 재사용된 승인 토큰은 거부된다.
- 적용 후 검증 실패 시 자동 백업으로 원복되고 원복 결과가 다시 검증된다.
- 복원 성공 후 과거 세션은 모두 무효화되며 후보 DB 관리자 계정으로 로그인할 수 있다.
- 관리자가 검증하고 명시적으로 해제하기 전까지 점검 모드는 유지된다.

## 8. 구현·검증 순서

1. [제안-046] 점검 상태 저장소와 중앙 요청 게이트를 Staging에 구현한다.
2. 기존 세션 만료와 접근 로그 워커를 재사용 가능한 내부 함수로 분리한다.
3. 백업 다운로드와 후보 업로드·검증을 구현한다.
4. 요청 배출·DB 쓰기 동결·복원 전 백업·온라인 복원·자동 원복 조정기를 구현한다.
5. 관리자 UI와 비동기 작업 상태 표시를 구현한다.
6. 모의 DB에서 정상 복원, 손상 후보, 잠금 시간 초과, 복원 실패, 검증 실패, 자동 원복 실패를 검증한다.
7. 사용자에게 Staging 검증 결과를 제출한 뒤 운영 병합을 별도로 검토한다.
